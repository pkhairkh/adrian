# Workshop Decision 3: UUID-Primary Identity with SID-as-Attribute and Bidirectional Mapping

## Status

Decided — 2026-08-13

## ORQs resolved

- **ORQ-026: Replace SIDs with UUIDs?** — **No, not entirely. SIDs are not eliminated.** The framework's internal primary key for every security principal is a UUID (UUIDv7, time-ordered for index locality), but every principal *also* carries a SID as a first-class attribute. SIDs are required for AD-interop wire compatibility (ACLs, PACs, audit logs, sIDHistory migration) and are provisioned even in native-only deployments so that a native forest can later be joined to an AD forest via trust without re-issuing identities.
- **ORQ-027: Keep SIDs for AD interop, use UUIDs internally?** — **Yes, with refinements.** SIDs are kept as the wire-format currency for AD interop. UUIDs are the internal primary key. A first-class, bidirectional, cached mapping table (`principal_identities` FDB subspace) is maintained by the directory and exposed to every capability that handles a principal reference — KDC PAC builder, Auth Provider token construction, Policy Engine security filtering, File Gateway ACL evaluator, Client SDK ID-mapping service, and Migration sIDHistory flow. The mapping table is not an afterthought adapter; it is a Tier-1 directory subsystem with its own consistency model, its own monitoring, and its own operational runbook.

## Decision

The Adrian framework SHALL use a **dual-identifier identity model**: a UUIDv7 as the internal primary key for every security principal (user, computer, group, service account, gMSA, trust identity) and a SID as a first-class attribute on every principal. The UUID is the primary key in every internal index, every foreign-key reference, every audit log entry, and every replication operation. The SID is the wire-format currency for AD-interop scenarios (LDAP `objectSid` attribute, Kerberos PAC `GroupIds`/`ExtraSids`, SACL/DACL ACE `Trustee` field, sIDHistory migration, cross-trust access). A first-class bidirectional mapping table — stored in FDB subspace `0x0D` (per Decision 2) — provides O(1) lookup in both directions (UUID → SID, SID → UUID) and is the canonical reference for every cross-capability identity translation.

The mapping table is not a cache that can be rebuilt from the directory (although it *can* be rebuilt if corrupted — see §Trade-offs accepted). It is the authoritative source of truth for the UUID ↔ SID correspondence. Every principal-creation operation writes the mapping row in the same FDB transaction as the principal object; every principal-deletion operation tombstones the mapping row in the same transaction as the principal tombstone; every sIDHistory-add operation (during migration) writes the additional `sid_history` entries atomically. The mapping table's invariants are enforced by FDB's strict serializable transactions (per Decision 2): there is never a window where a principal exists without a mapping row, and there is never a window where a SID is mapped to two UUIDs.

The UUIDv7 choice (over UUIDv4) is deliberate. UUIDv7 is time-ordered (the first 48 bits are a Unix timestamp in milliseconds), which gives the framework two properties that UUIDv4 does not: (1) index locality — principals created in the same time window have adjacent UUIDs, which improves FDB range-scan performance for time-windowed queries (audit logs, recently-created-principal listings); (2) natural sort order — UUIDv7's lexical sort matches chronological order, which simplifies `ORDER BY createdAt` queries. UUIDv7 is specified in RFC 9562 (September 2024) and is supported by the `uuid` Rust crate (≥1.10.0). UUIDv4 remains supported for imported principals (e.g., AD principals migrated via sIDHistory that already have a UUIDv4 `objectGUID` — the framework preserves the AD-assigned `objectGUID` as the principal's UUID on migration, rather than re-issuing a UUIDv7).

The SID format is preserved byte-identically to MS-DTYP §2.4.2 — `S-1-<revision>-<identifier-authority>-<sub-authority-1>-...-<sub-authority-n>`, with the binary representation `S-1-5-21-<domain-sid>-<rid>`. The framework's `adrian-sid` crate (a fresh Rust crate, ~800 lines, MIT/Apache-2.0) parses and emits the SID binary format and provides `Sid`, `SidDomain`, `SidRid` types with `Display`/`FromStr` for the SDDL string form and `AsRef<[u8]>` for the binary form. The crate is independent of the `windows` crate (which is Windows-focused and pulls in a large dependency tree); the framework's `adrian-sid` crate is pure Rust and cross-platform.

For AD-interop mode (per Decision 1), every principal's SID is provisioned at creation time by the RID-pool allocator (the framework's equivalent of AD's RID Master FSMO role — the RID-pool allocator runs on the framework's "schema master" DC and dispenses RID ranges to other DCs in 500-RID batches, matching AD's behaviour). For native mode (per Decision 1), every principal's SID is provisioned at creation time by the local DC (no RID-pool allocator needed because Raft replication serialises principal-creation operations). The SID format is identical in both modes; only the provisioning mechanism differs.

**Concrete specification**:

- Every security principal object (user, computer, group, service account, gMSA, trust identity, inetOrgPerson) SHALL have a UUID as its primary key (`uuid` attribute, UUIDv7 for new principals, UUIDv4 for migrated AD principals).
- Every security principal object SHALL have an `objectSid` attribute (SID, MS-DTYP §2.4.2 binary format) provisioned at creation time. The SID SHALL be unique within the forest.
- Every security principal object MAY have a `sIDHistory` attribute (multi-valued SID set) for migrated principals. `sIDHistory` is preserved on the wire for AD-interop mode (per PC-124); for native mode, `sIDHistory` is preserved but not exposed via PAC (the framework's native PAC includes only the current SID).
- The framework SHALL maintain a bidirectional mapping table in FDB subspace `0x0D` with two indexes:
  - Forward: `(0x0D, 0x01, uuid[0..16]) → (sid_bytes, sid_history_bytes, principal_type, tombstoned_at)`
  - Reverse: `(0x0D, 0x02, sid_bytes) → (uuid[0..16], tombstoned_at)`
- Every principal-creation operation SHALL write both the principal object and the mapping row in the same FDB transaction (atomicity enforced by FDB strict serializable transactions, per Decision 2).
- Every principal-deletion operation SHALL tombstone the mapping row (set `tombstoned_at` to current timestamp) in the same FDB transaction as the principal tombstone. Tombstoned mapping rows are GC'd after `tombstoneLifetime` (default 180 days) — matching the principal tombstone's GC, ensuring that a re-created principal (after delete + wait for GC + re-create) does not collide with the old mapping.
- The framework SHALL expose the mapping table via two internal APIs:
  - `IdentityMapping::lookup_sid(uuid: Uuid) -> Result<Option<Sid>, IdentityError>`
  - `IdentityMapping::lookup_uuid(sid: &Sid) -> Result<Option<Uuid>, IdentityError>`
- The mapping table SHALL be cached in-memory on each DC (an LRU cache, default 100K entries, configurable). Cache misses fall through to FDB. Cache invalidation is via FDB watches on the mapping-row keys (per Decision 2 §Rust implementation implications). The cache hit rate is the dominant operational metric — a 99%+ hit rate is expected for typical deployments (the working set of principal references is much smaller than the total principal count).
- The RID-pool allocator (AD-interop mode only) SHALL dispense RID ranges in 500-RID batches (matching AD's `RIDAllocationPoolSize`). The allocator state is stored in FDB subspace `0x06` with the key `(0x06, domain_sid) → (next_rid, last_allocated_rid, pool_exhaustion_warning_threshold)`. The `next_rid` counter uses FDB's atomic-add operation for lock-free allocation. RID pool exhaustion (when `next_rid` exceeds `last_allocated_rid`) triggers a request to the RID-master DC for a new 500-RID batch.
- For native mode, RID allocation is local (no RID-master DC); each DC maintains its own RID counter at `(0x06, local_dc_id, domain_sid) → next_rid`. The DC's `local_dc_id` is its `invocationId` (per Decision 1), which is unique within the forest.
- The framework's POSIX UID/GID mapping service (Client SDK, per PC-089) SHALL use the mapping table to map SIDs to POSIX UIDs. The mapping is configurable (algorithmic mapping via `author = "rfc2307"` or `algorithmic = "adrian-default"`; or directory-stored via the `uidNumber`/`gidNumber` attributes). The framework's default algorithmic mapping is `uuid_to_uid(uuid) = (uuid_to_u64(uuid) % (2^31 - 65536)) + 65536`, which gives a stable POSIX UID range of 65536..2^31-1 (the same range as Linux `useradd` defaults). This eliminates the SID → UID algorithm that AD/Samba use (which has well-known collision problems — see PC-089).
- For AD-interop mode, the framework SHALL accept AD-issued SIDs on the wire (LDAP `objectSid`, Kerberos PAC `GroupIds`/`ExtraSids`, SACL/DACL ACE `Trustee`) and translate to UUIDs via the mapping table at the directory boundary. ACLs on framework objects are stored with UUID-based trustees internally and translated to SID-based trustees on the wire for AD-interop (and vice versa for incoming AD-interop ACLs).
- The framework's KDC PAC builder (per Decision 1's DrSuapiReplicator compatibility) SHALL emit MS-PAC `GroupIds`/`ExtraSids` with SIDs (not UUIDs) for AD-interop mode. For native mode, the PAC builder SHALL emit `GroupIds`/`ExtraSids` with SIDs (preserving the MS-PAC format) — the framework's native mode still uses SIDs in the PAC because the PAC is a wire format consumed by AD-aware services.
- The framework's audit log (per ADR-060) SHALL record principal references as UUIDs (internal) with a SID snapshot at audit-time (for cross-reference with AD-interop audit logs). The SID snapshot is a denormalised copy that allows the audit log to be queried by SID without consulting the mapping table (which may have changed since the audit event was recorded).
- The framework SHALL support an `adrian-identity` CLI (`adrian-identity show --uuid <uuid>`, `adrian-identity show --sid <sid>`, `adrian-identity map --uuid <uuid> --sid <sid>` for manual mapping fixes) and a `GET /api/v1/identity/lookup` REST endpoint.

## Rationale

SIDs are the interop currency with AD. Every ACL, every PAC, every audit log, every sIDHistory migration, every cross-trust access, every AD-aware application that filters on group membership uses SIDs. Replacing SIDs with UUIDs (Option B) would break every AD-interop scenario — ACLs on migrated objects would reference SIDs that no longer exist, sIDHistory migration (PC-124) would become impossible, and the framework would need a synthetic SID layer to interoperate with AD (which defeats the modernisation goal). UUIDs are the modern equivalent (no RID-pool bottleneck, no SID-collision risk, no 32-bit-sub-authority limitation), but UUIDs alone (Option B) break AD interop. The "both with mapping" answer (Option C) preserves both interop and modernisation; the cost is a mapping layer that touches every capability that handles a principal reference.

The decision is UUID-primary (not SID-primary) because UUIDs are the better internal identifier. UUIDv7's time-ordering gives index locality in FDB (per Decision 2), which improves range-scan performance for time-windowed queries. UUIDs have no RID-pool bottleneck (per PC-015) — every DC can generate UUIDs independently without coordination. UUIDs have no SID-collision risk (UUIDv7's 122 random bits give a collision probability of ~10^-37 at 10^12 UUIDs). UUIDs have no 32-bit-sub-authority limitation (SIDs are theoretically unlimited but practically capped at 2^32 RIDs per domain, which is a real concern for large cloud-scale tenants). SIDs are kept as an attribute (not as the primary key) because they are required for AD-interop wire compatibility but are not the best internal identifier.

The mapping table is first-class (not an afterthought) because it is on the hot path of every capability. The KDC's PAC builder looks up SIDs for UUIDs on every AS-REQ. The File Gateway's ACL evaluator looks up UUIDs for SIDs on every file-open. The Auth Provider's token construction looks up SIDs for UUIDs on every token issuance. The Policy Engine's security filtering looks up SIDs for UUIDs on every policy evaluation. The Client SDK's ID-mapping service looks up UUIDs for SIDs on every `getpwuid` call. The Migration's sIDHistory flow looks up UUIDs for old SIDs (the migrated principal's previous SID) on every migrated object. A 99%+ cache hit rate (typical for a 100K-principal working set in a 10M-principal forest) keeps the lookup cost at <100µs per call; the remaining 1% fall through to FDB at <1ms per call. The mapping table's operational cost is ~1KB of FDB storage per principal (100GB for a 100M-principal forest — well within FDB's capacity) and ~50MB of in-memory cache per DC (for a 100K-entry cache).

The RID-pool allocator is preserved for AD-interop mode because AD's RID-master FSMO role is required for AD-interop wire compatibility (AD DCs expect the framework to allocate SIDs from a RID pool that the RID master dispenses). The RID-pool bottleneck (PC-015) is mitigated by the framework's 500-RID batch allocation (matching AD's `RIDAllocationPoolSize`) and by the framework's automatic RID-pool-creation on domain-controller promotion (no manual `ridpool` operations needed). The RID-pool bottleneck is *not* eliminated for AD-interop mode — it is inherited from AD. For native mode, the RID-pool bottleneck is eliminated (each DC allocates RIDs locally with no coordination), but SIDs are still provisioned (for future AD-interop join if needed).

External evidence supporting this decision: Microsoft Entra ID (Azure AD) uses a dual-identifier model — `objectGUID` (UUID) as the immutable primary key and `onPremisesSecurityIdentifier` (SID) as the AD-interop attribute — and maintains a mapping table for hybrid scenarios. FreeIPA uses a similar dual-identifier model — `ipaUniqueId` (UUID) as the primary key and `ipaSid` (SID) as the Samba-interop attribute. Samba 4 uses `objectGUID` and `objectSid` as dual identifiers (matching AD). The pattern is industry-standard for any identity system that bridges modern (UUID-based) and legacy (SID-based) worlds. The `uuid` Rust crate (MIT/Apache-2.0, maintained by the Rust community, >50M downloads) supports UUIDv7 (RFC 9562) since version 1.10.0; the framework uses the `uuid` crate's `Uuid::now_v7()` for new-principal generation.

Rust-specific considerations drive the `adrian-sid` crate choice. The `windows` crate provides SID handling (via `windows::Win32::Security::Authorization::Sid`), but it is Windows-focused (the SID type is a wrapper around the Win32 `PSID`), pulls in a large dependency tree (`windows` is ~50MB), and is not idiomatic for cross-platform Rust. The `picky` crate (a Rust PKI library) has a SID type but is not focused on the AD SID format. The framework's `adrian-sid` crate (fresh, ~800 lines, MIT/Apache-2.0) is pure Rust, cross-platform, and focused on the MS-DTYP §2.4.2 SID binary format. The crate provides `Sid`, `SidDomain`, `SidRid` types with `Display`/`FromStr` (SDDL string form), `AsRef<[u8]>` (binary form), `Hash`/`Eq`/`Ord` (for use as FDB tuple-layer keys), and `serde::Serialize`/`Deserialize` (for JSON audit logs).

## Trade-offs accepted

The primary trade-off is mapping-table complexity. Every capability that handles a principal reference must consult the mapping table (or its in-memory cache). The mapping table is a new Tier-1 directory subsystem with its own consistency model, its own monitoring, and its own operational runbook. A mapping-table corruption (a UUID mapped to two SIDs, or a SID mapped to two UUIDs) would break ACL evaluation, PAC issuance, and audit log integrity — the failure modes are severe. The mitigation is FDB's strict serializable transactions (per Decision 2), which prevent the corruption at the storage layer; the mapping table's invariants are enforced by FDB unique-index constraints on both the forward and reverse indexes. A reconciliation job (the `adrian-identity-reconcile` CLI, run weekly by the operator) scans the mapping table and the principal objects for divergence and reports any inconsistencies. The reconciliation job is read-only (it does not auto-fix); the operator must manually approve any fix.

The secondary trade-off is storage overhead. The mapping table adds ~1KB of FDB storage per principal (the forward index row + the reverse index row + the `sid_history` bytes for migrated principals). For a 100M-principal forest (cloud-scale), this is ~100GB of FDB storage — well within FDB's capacity (Apple's iCloud FDB deployment is petabyte-scale). For a 1M-principal enterprise forest, this is ~1GB — negligible. The storage overhead is the cost of preserving both interop and modernisation; the framework accepts the cost because the alternative (UUID-only or SID-only) breaks either interop or modernisation.

A third trade-off is the RID-pool bottleneck for AD-interop mode. AD-interop deployments inherit AD's RID-master FSMO role and its 500-RID batch allocation. For deployments that exceed 2^32 RIDs per domain (~4 billion SIDs), the RID pool exhausts and the domain must be split (a multi-week operational project). This is an AD limitation that the framework inherits for AD-interop mode; it is *not* a framework limitation. For native mode, the RID-pool bottleneck is eliminated (each DC allocates RIDs locally with no coordination), and the 2^32 RID limit is per-DC (effectively unlimited). The mitigation for AD-interop mode is documentation — deployments that anticipate exceeding 2^32 RIDs should use native mode.

A fourth trade-off is the dual-identifier cognitive load. Engineers writing framework code must decide whether to use UUIDs or SIDs in each context. The framework's coding guideline is: **UUIDs internally, SIDs on the wire.** Internal APIs (Rust function signatures, FDB key encodings, audit log entries) use UUIDs. Wire APIs (LDAP attributes, Kerberos PAC fields, SACL/DACL ACEs, DRSUAPI replication payloads) use SIDs. The boundary between internal and wire is the `IdentityMapping` trait — every wire-API translation goes through the trait, and every internal-API consumer uses UUIDs directly. The coding guideline is enforced by `clippy` lints (a custom lint that flags `Sid` types in internal-API function signatures).

The final trade-off is the POSIX UID/GID mapping complexity. The framework's default algorithmic mapping (`uuid_to_uid(uuid) = (uuid_to_u64(uuid) % (2^31 - 65536)) + 65536`) is simpler than AD/Samba's SID → UID algorithm but has a small collision risk (two UUIDs mapping to the same UID). The collision probability is ~10^-5 for a 100K-principal deployment (birthday paradox: 2^31 / 100K^2 ≈ 2^31 / 10^10 ≈ 0.2, so ~20% collision probability for 100K principals — *unacceptable*). The framework therefore recommends directory-stored UID/GID (`uidNumber`/`gidNumber` attributes) for deployments >10K principals, with algorithmic mapping as a fallback for smaller deployments. The framework's ID-mapping service (per PC-089) auto-assigns `uidNumber`/`gidNumber` on principal creation if the attributes are not set, using FDB's atomic-add counter for collision-free allocation.

## Rust implementation implications

**Crate selection.** The identity stack comprises four crates, all MIT/Apache-2.0 dual-licensed:

- `adrian-sid` — fresh Rust crate for the MS-DTYP §2.4.2 SID binary format. ~800 lines. Provides `Sid`, `SidDomain`, `SidRid` types with `Display`/`FromStr`, `AsRef<[u8]>`, `Hash`/`Eq`/`Ord`, `serde::Serialize`/`Deserialize`. Pure Rust, no FFI, no `unsafe`.
- `adrian-identity-core` — defines the `IdentityMapping` trait, the `Principal` struct (with `uuid`, `sid`, `sid_history`, `principal_type` fields), the `IdentityError` type, and the RID-pool allocator interface. ~2K lines.
- `adrian-identity-fdb` — FoundationDB implementation of `IdentityMapping`. Stores the mapping table in FDB subspace `0x0D` (forward and reverse indexes), maintains the in-memory LRU cache, and listens to FDB watches for cache invalidation. ~3K lines.
- `adrian-identity-ridpool` — RID-pool allocator (AD-interop mode) and local RID allocator (native mode). ~1K lines.

**Crate maturity.** The `uuid` crate (MIT/Apache-2.0, maintained by the Rust community, >50M downloads) is production-grade and supports UUIDv7 (RFC 9562) since version 1.10.0. The `adrian-sid` crate is fresh (framework-owned) — the framework team will maintain it as a standalone crate on crates.io, with the goal of upstreaming it as a community-maintained crate (similar to how `rasn` and `openraft` are community-maintained). The `adrian-identity-*` crates are framework-internal and not published to crates.io.

**Unsafe code policy.** The identity stack SHALL contain zero `unsafe` blocks. The `uuid` crate is `unsafe`-free (pure Rust). The `adrian-sid` crate is `unsafe`-free (pure Rust). The `adrian-identity-fdb` crate uses the `foundationdb` crate's safe Rust API (per Decision 2) — no direct FFI. The `adrian-identity-ridpool` crate uses FDB's atomic-add counter via the `foundationdb` crate's safe `Transaction::atomic_op` method — no direct FFI.

**Async runtime.** `tokio` (per Decisions 1 and 2). The `IdentityMapping` trait is async (`async fn lookup_sid(&self, uuid: Uuid) -> Result<Option<Sid>, IdentityError>`), takes `&self`, and is `Send + Sync`. The in-memory LRU cache is `tokio::sync::RwLock`-protected (multiple readers, single writer). The FDB watches are `tokio::sync::watch` channels that notify the cache on invalidation.

**Error handling.** `thiserror` for the `IdentityError` type with variants: `MappingNotFound` (the UUID or SID is not in the mapping table — the principal does not exist), `MappingConflict` (two UUIDs map to the same SID, or two SIDs map to the same UUID — a corruption that should never happen given FDB's unique-index constraints), `RidPoolExhausted` (the RID pool is exhausted — AD-interop mode only, requires RID-master intervention), `FdbError` (an FDB error from the underlying `foundationdb` crate). `anyhow` is permitted only in CLI entry points. The `IdentityMapping` trait's methods return `Result<T, IdentityError>`; no panics on the identity path.

**Trait design for pluggability.** The `IdentityMapping` trait is the abstraction that allows the framework's identity stack to be engine-agnostic (per Decision 2). The trait is async, `Send + Sync`, and has two implementations: `FdbIdentityMapping` (production, FDB-backed) and `InMemoryIdentityMapping` (testkit, in-memory `HashMap`-backed). The `IdentityMapping` trait composes with the `DirectoryStore` trait (Decision 2) — `FdbIdentityMapping` uses `FdbDirectoryStore` for FDB access, and `InMemoryIdentityMapping` uses `InMemoryDirectoryStore` for in-memory access. The trait is the v2 seam where a Redis-backed or etcd-backed mapping implementation would slot in (if a future ADR decides to externalise the mapping table).

**UUIDv7 generation.** The `uuid` crate's `Uuid::now_v7()` uses the system clock (with millisecond resolution) and a cryptographically-secure random number generator (`getrandom` crate). For high-throughput principal creation (bulk import during migration), the framework uses the `uuid` crate's `Uuid::from_timestamp_and_context()` API to provide a custom context (the DC's `invocationId`) for additional uniqueness guarantees within the same millisecond. This avoids UUIDv7 collisions when two DCs create principals in the same millisecond (the probability is ~10^-6 per pair per millisecond, which is non-trivial for a 100-DC forest doing bulk import).

Partial ADRs that can now be promoted from PARTIAL to full:

- **ADR-002 (memberOf back-link)** — Open Question on cross-domain move and identity model resolved: cross-domain move rewrites the principal's SID (per this decision), and the link-value store's `backlinkDNT` references the principal's DNT (which is stable — the DNT is the FDB-internal row ID, not the SID). The link-value store is unaffected by SID changes.
- **ADR-053 (key escrow)** — Open Question on principal model resolved: the per-computer recovery key is stored on the computer object keyed by the computer's UUID; the recovery-key ACL references the helpdesk group's SID (translated to UUID via the mapping table for internal ACL evaluation).

## Implementation impact

- **Core Directory**: The `IdentityMapping` trait and the `FdbIdentityMapping` implementation are the bulk of v1 identity engineering. ~5 person-months for the `adrian-sid` crate, the `adrian-identity-core` trait, the `adrian-identity-fdb` implementation, the RID-pool allocator, and the in-memory cache. The principal object schema is unaffected (the `uuid` and `objectSid` attributes are standard LDAP attributes; the mapping table is a separate FDB subspace, not an LDAP attribute).
- **KDC**: KDC's PAC builder reads SIDs for UUIDs via `IdentityMapping::lookup_sid` on every AS-REQ. The KDC's PAC builder is the hottest identity-mapping consumer; the in-memory cache (99%+ hit rate) keeps the lookup cost at <100µs per AS-REQ. The KDC's krbtgt account is itself a principal (UUID + SID); the krbtgt key rotation (per ADR-065) operates on the UUID-keyed principal object.
- **Auth Provider**: Auth Provider's token construction (S4U2Self, S4U2Proxy, RBCD) reads SIDs for UUIDs via `IdentityMapping::lookup_sid`. The Auth Provider's NTLM hash storage (per ORQ-072/074/075) is on the principal object keyed by UUID.
- **Policy Engine**: Policy Engine's security filtering reads SIDs for UUIDs via `IdentityMapping::lookup_sid` to evaluate group-membership-based policy application. The Policy Engine's GPO SD evaluation reads UUIDs for SIDs via `IdentityMapping::lookup_uuid` to evaluate SACL/DACL ACEs on GPO objects.
- **Cert Service**: Cert Service's certificate templates reference principals by UUID (internal) or SID (AD-interop). The `Request.Requester` field stores the requester's UUID; the certificate's `Subject` field stores the requester's SID (for AD-interop compatibility with AD CS tools).
- **Federation Gateway**: Federation Gateway's claims-policy language (per ORQ-135/136/137, Day 2) references principals by UUID (internal) or SID (AD-interop). The SAML/OIDC `NameID` field stores the principal's UUID (modern) or SID (AD-interop); the framework's claim-issuance policy translates between the two via `IdentityMapping`.
- **File Gateway**: File Gateway's share-ACL evaluator reads UUIDs for SIDs via `IdentityMapping::lookup_uuid` on every file-open. The share-ACL evaluator is the second-hottest identity-mapping consumer (after the KDC PAC builder); the in-memory cache keeps the lookup cost at <100µs per file-open.
- **Client SDK**: Client SDK's ID-mapping service (per PC-089) reads UUIDs for SIDs on every `getpwuid`/`getgrgid` call. The ID-mapping service is a daemon on each client host that caches the mapping table locally (refreshed via FDB watches or via LDAP queries against the directory).
- **Cross-Platform Parity**: Cross-platform parity is identity-agnostic except for the POSIX UID/GID mapping (PC-089, resolved by this decision).
- **Operations**: The `adrian-identity` CLI and the `GET /api/v1/identity/lookup` REST endpoint are new Operations surfaces. The `adrian-identity-reconcile` weekly job is a new operational task; the operator runs it automatically and reports inconsistencies via the framework's alerting stack.
- **Security**: PC-120 (sIDHistory abuse) threat model can now be written. The per-trust filtering policy on the mapping table is the sIDHistory-abuse mitigation; the KDC's PAC builder applies the filtering at PAC-issuance time, and the File Gateway's ACL evaluator applies the filtering at ACL-evaluation time. PC-117 (DCSync, secondary effect) is unaffected by this decision — DCSync is a DrSuapiReplicator concern (per Decision 1), not an identity concern.
- **Migration**: PC-124 (sIDHistory migration), PC-126 (parallel-run switchover), and PC-127 (password hash migration) are now fully specified. The migration tool reads AD's `objectGUID` (preserved as the framework UUID), `objectSid` (preserved as the framework SID), `sIDHistory` (preserved as the framework sIDHistory), and `unicodePwd` (preserved as the framework password hash) in a single bulk-load transaction per principal.

## Cross-capability dependencies

This decision **depends on** Decision 2 (storage engine). The mapping table is stored in FDB subspace `0x0D` (per Decision 2); FDB's strict serializable transactions enforce the mapping table's invariants (one UUID per SID, one SID per UUID) via unique-index constraints. FDB's atomic-add counter (for RID-pool allocation) provides lock-free RID allocation. FDB's watches (for cache invalidation) provide the in-memory cache's consistency. If Decision 2 had chosen RocksDB (single-node), the mapping table's invariants would need a custom lock-based protocol (because RocksDB does not have FDB's strict serializable transactions across multiple keys), and the RID-pool allocator would need a distributed lock (because RocksDB does not have FDB's atomic-add counter). The FoundationDB decision makes this identity-model decision viable.

This decision **depends on** Decision 1 (replication protocol). The mapping table replicates via DrSuapiReplicator (AD-interop mode) or RaftReplicator (native mode); both modes use the same internal representation (per Decision 1's `Replicator` trait). The RID-pool allocator's state (`next_rid`, `last_allocated_rid`) replicates via DrSuapiReplicator (AD-interop mode, matching AD's RID-master replication) or RaftReplicator (native mode, with each DC's local RID counter being DC-local state, not replicated).

This decision **influences** the schema model decision (ORQ-030/031, Day 1 PM session). The hybrid schema (LDAP schema + typed projection, per ORQ-030 Option C) is the natural fit for this identity model — the LDAP schema preserves `objectSid`, `sIDHistory`, `objectGUID` as wire-format attributes; the typed projection exposes `Principal { uuid: Uuid, sid: Sid, sid_history: Vec<Sid> }` as a Rust type. The schema model decision can proceed independently but should align with this decision's typed projection.

This decision **influences** the KDC implementation decision (ORQ-042/043/044, Day 2). The KDC's PAC builder uses `IdentityMapping::lookup_sid` to translate UUID group memberships to SID `GroupIds`/`ExtraSids` in the MS-PAC. The KDC implementation choice (Samba Heimdal vs. MIT + plugin vs. fresh) does not depend on this decision, but the KDC's PAC-generation code must call `IdentityMapping::lookup_sid` — this is a small but non-trivial integration point.

This decision **influences** the NTLM decision (ORQ-072/074/075, Day 2). NTLM's pass-the-hash attack surface is independent of the identity model, but the NTLM hash storage is on the principal object keyed by UUID. The NTLM decision's threat model must account for the mapping table (an attacker who can corrupt the mapping table can redirect NTLM authentication to a different principal — a new attack vector that AD does not have, because AD uses SIDs as the primary key and has no mapping table).

This decision **influences** the federation layer decision (ORQ-132/133/134, Day 2). The Federation Gateway's claim-issuance policy translates between UUID (internal) and SID (AD-interop) via `IdentityMapping`. The federation layer decision can proceed independently, but the claim-issuance policy language (Rego vs. Cedar vs. per-IdP plugins, per ORQ-135/136/137) must support both UUID and SID principal references.

This decision **influences** the Client SDK architecture decision (ORQ-169/170/175/176, Day 2). The Client SDK's ID-mapping service (per PC-089) is a daemon on each client host that caches the mapping table locally. The Client SDK architecture choice (Rust core with C FFI bindings, per Spike 7's expected recommendation) must expose the `IdentityMapping` trait via the C FFI so that the ID-mapping daemon can be implemented in any language. The Client SDK decision can proceed independently, but the FFI design must include `identity_mapping_lookup_sid` and `identity_mapping_lookup_uuid` functions.
