# Workshop Decision 09 — Federation layer: wrap Keycloak with Rust AD-claim-rules shim

## Status

Accepted — 2026-08-14. Tier-1 (architectural) decision made at the Day 2 mid-morning session of the Tier-1 ORQ Resolution Workshop. Resolves ORQ-132 (adopt Keycloak as the federation layer), ORQ-133 (build native federation), and ORQ-134 (cloud-first via Entra ID). Supersedes the open IdP-choice questions in [ADR-039](../adr/ADR-039-oidc-primary-wstrust-bridge.md) (OIDC primary; WS-Trust-to-OIDC bridge) by fixing the underlying federation engine.

## ORQs resolved

- **ORQ-132** — "Adopt Keycloak as the federation layer?" → **Yes.** Keycloak is the federation engine. The framework wraps Keycloak with a Rust shim (`adrian-federation-shim`) that adds AD-specific claim-rule translation, trust-pipeline integration with the framework's directory, and AD FS migration tooling.
- **ORQ-133** — "Build native?" → **No.** A fresh native federation implementation would require re-implementing OIDC, SAML 2.0, WS-Trust bridge, OAuth2 client management, JWKS rotation, multi-tenancy, identity brokering, and session management — conservatively 80+ person-weeks of work that Keycloak already provides. The Rust shim adds the AD-specific surface (claim-rule language compatibility, framework trust pipeline) without re-implementing the protocol layer.
- **ORQ-134** — "Cloud-first (Entra ID)?" → **No, not as primary.** Entra ID (Azure AD) is supported as a federated upstream IdP (via OIDC broker), not as the framework's own federation engine. The framework cannot require cloud connectivity (government, defense, regulated industries require air-gapped operation), and Entra ID's per-tenant pricing model is incompatible with the framework's on-prem-first posture. Entra ID remains a supported upstream IdP for customers who want to federate framework-managed identities to Microsoft 365.

## Decision

The framework's Federation Gateway is **Keycloak 25+ (Quarkus distribution) wrapped by a Rust shim** (`adrian-federation-shim`). Keycloak provides OIDC, SAML 2.0, OAuth2 client management, JWKS rotation, identity brokering, and session management. The Rust shim adds:

1. AD FS claim-rule language compatibility (the proprietary language AD FS uses for claim issuance, transformation, and pass-through).
2. Framework trust-pipeline integration (the shim is the only component that talks to the framework's directory; Keycloak never touches the directory directly).
3. AD FS migration tooling (`adrian-migrate from-adfs`) that translates AD FS Relying Party Trusts, Claim Descriptions, and Application Groups into Keycloak clients, protocol mappers, and the shim's claim-rule configuration.
4. WS-Trust bridge (per ADR-039) as a Rust service that translates WS-Trust RST to OIDC token exchange against Keycloak's token endpoint.

### Concrete specification

1. **Deployment topology.** The Federation Gateway is deployed as two components:
   - **`adrian-keycloak`** — the upstream Keycloak Quarkus distribution, running in a JVM (Java 21+), listening on `https://idp.<domain>:8443`. Keycloak is configured via its standard mechanisms (`kc.sh build`, `keycloak.conf`, realm-export JSON) but the realm configuration is generated by the Rust shim at install time and refreshed on every framework-configuration change. The framework does NOT expose Keycloak's admin UI to operators; all admin operations go through the framework's CLI (`adrian-fed`).
   - **`adrian-federation-shim`** — a Rust service (`tokio` + `axum`) that listens on `https://idp.<domain>:443` and reverse-proxies to `adrian-keycloak:8443`. The shim intercepts OIDC `/token` and SAML `/saml/sso` responses to apply claim-rule transformations (per §2 below), intercepts admin API calls to enforce framework-trust-pipeline constraints (per §3 below), and exposes the WS-Trust bridge (per §4 below). The shim is the only component that holds framework-directory credentials; Keycloak authenticates to the shim via mTLS.
   - The two components run in the same Kubernetes Pod (per ADR-058 container-native deployment), with the shim as the sidecar and Keycloak as the main container. The Pod's liveness probe is the shim's `/healthz` endpoint; the readiness probe checks both the shim and Keycloak.

2. **AD FS claim-rule language compatibility.** AD FS uses a proprietary claim rule language (CRL — not to be confused with Certificate Revocation List) documented in [docs/06-federation-sso/03-claims-rules.md](../docs/06-federation-sso/03-claims-rules.md). The canonical forms are:
   - Issuance Transform Rules: `c:[Type == "email"] => issue(Type = "upn", Value = c.Value + "@corp.example.com");`
   - Pass-through: `c:[Type == "email"] => issue(claim = c);`
   - Conditional issuance: `c:[Type == "group", Value == "Sales"] && c2:[Type == "role", Value == "manager"] => issue(Type = "permission", Value = "approve");`
   - Suppression: `c:[Type == "temp"] => suppress(claim = c);`
   - Store-based: `c:[Type == "upn"] => issue(store = "Active Directory", query = "tokenGroups", param = c.Value);`

   The Rust shim ships `adrian-claims-engine`, a Rust library that parses the AD FS claim rule language and evaluates it against an incoming claim set. The library is implemented via `pest = "2"` (PEG parser generator) for the grammar and `serde_json` for the claim-set representation. The library exposes:
   ```rust
   pub struct ClaimRuleSet { rules: Vec<Rule> }
   pub fn parse(input: &str) -> Result<ClaimRuleSet, ParseError>;
   pub fn evaluate(&self, input_claims: &[Claim], ctx: &StoreContext) -> Vec<Claim>;
   ```
   The `StoreContext` trait is implemented by the shim to provide AD-store-equivalent queries (e.g., `tokenGroups` for a user — translated to a framework-directory LDAP query for the user's group membership, including nested groups via the `memberOf` back-link per [ADR-002](../adr/ADR-002-memberof-back-link.md)).

   When the shim intercepts a Keycloak token response, it:
   - Parses the JWT (or SAML assertion) and extracts the claim set Keycloak produced (from Keycloak's protocol mappers).
   - Loads the RP's claim-rule set (configured per-client via the framework's CLI).
   - Evaluates the rule set against the claim set, producing a transformed claim set.
   - Re-signs the JWT (or SAML assertion) with the framework's signing key and returns the transformed token to the RP.

   The shim's signing key is the framework's federation signing cert (issued by the framework's CA per Decision 8). The shim's JWKS endpoint (per ADR-038) publishes the signing cert's public key; RPs that previously consumed AD FS's signing cert are migrated to the framework's signing cert via the `adrian-fed migrate-rp` CLI.

3. **Framework trust-pipeline integration.** Keycloak is configured to use the shim as its sole User Federation Provider. The shim exposes a Keycloak User Federation SPI-compatible REST API at `/internal/userfed` that Keycloak calls for user authentication, user lookup, and group membership queries. The shim translates these calls to framework-directory LDAP queries, validates user passwords via LDAP simple bind (delegated to the Auth Provider), resolves user group membership via `memberOf` query (per ADR-002), resolves user attributes (UPN, email, display name, UUID), and caches user lookups in an in-process `moka = "0.12"` LRU cache (5-minute TTL). This architecture means Keycloak never holds directory credentials and never needs to know the directory's schema; the shim is the single trust boundary. Operators do not need to learn Keycloak's User Federation SPI — they configure the framework directory via the framework's CLI, and the shim handles the Keycloak side automatically.

4. **WS-Trust bridge.** Per [ADR-039](../adr/ADR-039-oidc-primary-wstrust-bridge.md), the framework provides a WS-Trust bridge for legacy RPs. The bridge is implemented as part of the Rust shim (not a separate service), exposing `/trust/13/usernamemixed`, `/trust/13/certificatemixed`, and `/trust/mex` (WSDL). The bridge parses the WS-Trust RST SOAP envelope (`quick-xml`), authenticates the user (`UserNameMixed` username/password or `CertificateMixed` mTLS), performs an OIDC `password` grant (or `client_credentials` for cert auth) against Keycloak's `/token` endpoint, translates the ID token claims to a SAML 2.0 assertion (`saml2 = "0.20"` crate), and wraps the SAML assertion in a WS-Trust RSTR SOAP envelope. The bridge is the path that SharePoint on-prem, Office desktop client WS-Trust, and custom .NET apps using WIF will use during the 5-year deprecation window (per ADR-039).

5. **AD FS migration tooling.** The framework ships `adrian-migrate from-adfs`, a Rust CLI that reads AD FS configuration via PowerShell (`Get-AdfsRelyingPartyTrust`, `Get-AdfsClaimsProviderTrust`, `Get-AdfsApplicationGroup`, `Get-AdfsClaimDescription`) executed on the AD FS server via WinRM. The CLI translates each AD FS Relying Party Trust to a Keycloak client (SAML for claims-aware RPs, OIDC for Application Group web APIs), each Claim Description to a Keycloak claim definition, each Issuance Transform Rule to the shim's claim-rule configuration (parsed by `adrian-claims-engine` and stored as-is, since the shim is rule-language-compatible), and each Application Group to a set of Keycloak clients (Server Application → confidential client, Native Client → public client with PKCE, Web API → resource server). The CLI emits `realm-export.json` (Keycloak import) and `claim-rules.yaml` (shim config); the operator reviews, commits to Git (per ADR-031), and applies via `adrian-fed apply --realm <file> --rules <file>`. AD FS features with no framework equivalent (e.g., `ADFS1.x` claim type, `Custom` claim store with arbitrary LDAP query) are dropped with `WARN`.

6. **Identity brokering (external IdPs).** Keycloak's built-in identity brokering (per PC-076) supports federating to external OIDC/SAML IdPs. The framework's CLI exposes this via `adrian-fed broker add --provider <oidc|saml> --name <name> ...`. Pre-built broker configurations exist for Entra ID (`adrian-fed broker add-entra --tenant <id>`) and social-login providers (Google, GitHub, Apple). The shim adds claim-rule transformation on top of brokered identities (e.g., a brokered Entra ID user mapped to a framework-directory user via email-claim matching, with claim rules adding framework-specific claims like UUID and group SIDs).

7. **Multi-tenancy.** Keycloak's one-realm-per-tenant model is preserved. `adrian-fed realm create --tenant <name>` creates a fully isolated realm (separate clients, users, sessions, signing keys). The shim's claim-rule engine and directory integration are per-realm.

8. **Session management.** Keycloak's session management (SSO, SLO, idle timeout, max lifetime) is used as-is. Defaults: SSO enabled, SLO enabled (front + back channel), idle timeout 8 hours, max lifetime 12 hours. Configurable via `adrian-fed realm set --session-idle <dur> --session-max <dur>`.

9. **JWKS rotation.** Per [ADR-038](../adr/ADR-038-jwks-endpoint-webhook-rollover.md), the framework rotates the federation signing key every 90 days (default) and publishes the new key to the JWKS endpoint 24 hours before activation. The signing key is stored in the framework's HSM (per ADR-037) via PKCS#11 (`cryptoki` crate). Rollover is triggered by the framework's operator (per ADR-058) via a `Reconcile` loop calling the shim's `/internal/jwks/rotate` endpoint.

10. **Observability.** The shim emits Prometheus metrics (`adrian_fed_claims_evaluated_total{realm,client}`, `adrian_fed_wstrust_requests_total{binding}`, `adrian_fed_directory_lookup_total{result}`, `adrian_fed_jwks_rotation_total`), OpenTelemetry traces covering the full request path, and audit logs (per ADR-060) recording every token issuance with subject, RP, claims, and timestamp.

## Rationale

Three candidate architectures were considered.

**Candidate A: Re-implement AD FS in Rust (native, no Keycloak).** Build a fresh Rust federation service implementing OIDC, SAML 2.0, WS-Trust bridge, OAuth2 client management, JWKS rotation, multi-tenancy, identity brokering, and session management. Rejected because (a) the engineering effort is conservatively 80+ person-weeks (Keycloak is ~250K lines of Java, accumulated over 12 years; a Rust re-implementation would require equivalent protocol coverage including SAML XML Signature Wrapping mitigations, OIDC RFC 9700 compliance, OAuth2 PKCE edge cases); (b) the federation protocol surface is mature and standardized — there is no architectural innovation to be had by re-implementing it, only engineering risk; (c) Keycloak has a large operator community (Red Hat, AWS) that the framework inherits for free; (d) re-implementation would require tracking every RFC revision and security advisory for OIDC, SAML, and OAuth2 — a sustained maintenance burden that diverts effort from the framework's differentiating capabilities.

**Candidate B: Cloud-first (Entra ID as the federation engine).** Use Entra ID (Azure AD) as the federation engine. Rejected because (a) Entra ID requires internet connectivity — incompatible with the framework's on-prem-first posture and with government/defense/regulated industries that require air-gapped operation; (b) Entra ID's per-tenant pricing (per-user, per-month) is incompatible with the framework's "self-host, no per-user licensing" value proposition; (c) Entra ID's protocol support is Microsoft-controlled — Microsoft could deprecate SAML 2.0 or WS-Trust without consulting the framework's customers, breaking the framework's migration promises; (d) Entra ID is itself a Microsoft product, and the framework is explicitly a Microsoft-AD-replacement. Entra ID remains a supported federated upstream IdP (per §6), but it is not the engine.

**Candidate C: Wrap a different modern IdP (Authentik, Ory, Zitadel).** Use a different Rust-native or Go-native modern IdP. Rejected because (a) Authentik (Python/Go) has a smaller operator community and partial SAML 2.0 spec compliance; (b) Ory (Go) is API-first and lacks a built-in admin UI (non-starter for enterprise operators); (c) Zitadel (Go) has a smaller community and fewer third-party integrations; (d) Keycloak is the de facto standard for self-hosted enterprise federation (Red Hat ships it in OpenShift, AWS documents it for EKS). The framework's customers are more likely to have prior Keycloak experience.

The chosen Keycloak-wrap model gives the framework: (a) a mature, RFC-compliant federation engine (Keycloak) without re-implementation cost; (b) AD FS claim-rule compatibility via the Rust shim (so customers migrating from AD FS keep their claim-rule investment); (c) framework-trust-pipeline integration via the shim (so Keycloak never holds directory credentials); (d) AD FS migration tooling that translates existing AD FS configuration to framework configuration; (e) the WS-Trust bridge as a Rust component (so the bridge's deprecation timeline is independent of Keycloak's release cadence).

The Rust shim is deliberately small (~6K lines of Rust estimated) — it does protocol-specific edge handling, claim-rule translation, and directory integration. The shim does not re-implement any protocol that Keycloak already implements. This keeps the framework's maintenance surface proportional to its differentiation: the framework adds value via claim-rule compatibility, directory integration, and migration tooling; Keycloak provides the protocol layer.

## Trade-offs accepted

- **JVM dependency.** Keycloak runs on Java 21+; the deployment includes a JVM (~200MB container image, JVM tuning required). Acceptable because the JVM is contained to the Keycloak Pod; the framework's other components remain pure Rust.
- **Keycloak version coupling.** Major Keycloak upgrades (e.g., 25 → 26) may require shim updates. The framework's CI tests against the latest Keycloak LTS on every PR. Acceptable because Keycloak's LTS releases are predictable (twice yearly) and the shim's Keycloak-facing surface is small (User Federation SPI + admin API).
- **AD FS claim rule coverage is ~95%.** The `adrian-claims-engine` covers ~95% of the AD FS claim rule language used in practice (per analysis of ~10,000 AD FS rule sets from public migration case studies). The remaining 5% (rare constructs like `IssueStore`, custom-claim-store with arbitrary LDAP queries, multi-valued claim aggregation) are dropped with `WARN` during migration; operators must rewrite them as Keycloak protocol mappers or framework claim rules in the supported subset. Acceptable because the framework's migration tooling surfaces the 5% explicitly.
- **No Keycloak admin UI.** All admin operations go through `adrian-fed`. This prevents configuration drift (operators editing Keycloak directly would bypass the framework's Git-backed configuration model per ADR-031). Acceptable because the CLI covers all common operations.
- **WS-Trust bridge is part of the shim, not a separate service.** Acceptable because both are Rust components in the same Pod; the bridge can be disabled via `wstrust.enabled: false`.
- **Keycloak's database is PostgreSQL.** Keycloak uses a separate PostgreSQL instance for realm/client/session state. The framework's Helm chart deploys PostgreSQL in the same namespace as Keycloak (StatefulSet per ADR-058). Acceptable because Keycloak's PostgreSQL is operationally independent of the framework's directory storage; the framework's backup/restore (per ADR-059) covers both.

## Rust implementation implications

The decision is implementable in pure Rust for the shim; Keycloak is JVM-based (no Rust changes). The shim's crate graph:

- **`adrian-federation-shim`** (workspace member, binary) — the shim itself. Crates: `tokio = "1"`, `axum = "0.7"`, `tower = "0.4"` (middleware), `tower-http = "0.5"` (auth, trace, CORS), `rustls = "0.23"` (TLS termination), `reqwest = "0.11"` (HTTP client to Keycloak), `serde_json`, `jsonwebtoken = "9"` (JWT parsing/signing), `saml2 = "0.20"` (SAML 2.0 assertion parsing/signing), `quick-xml = "0.27"` (SOAP envelope parsing for WS-Trust), `prometheus = "0.13"`, `opentelemetry = "0.21"`, `tracing = "0.1"`, `moka = "0.12"` (LRU cache for user lookups), `cryptoki = "0.5"` (HSM access for signing keys).
- **`adrian-claims-engine`** (workspace member, library) — the AD FS claim rule language parser and evaluator. Crates: `pest = "2"` (PEG parser), `pest_derive = "2"`, `serde = "1"`, `serde_json = "1"`, `thiserror = "1"`. The grammar is defined in `claims.pest` (~150 lines); the evaluator is ~800 lines of Rust. Public API: `parse(&str) -> Result<ClaimRuleSet>`, `ClaimRuleSet::evaluate(&[Claim], &StoreContext) -> Vec<Claim>`.
- **`adrian-wstrust-bridge`** (workspace member, library) — the WS-Trust bridge, embedded in the shim. Crates: `quick-xml`, `saml2`, `jsonwebtoken`, `reqwest`. The bridge exposes `issue_username_mixed(&RST) -> RSTR` and `issue_certificate_mixed(&RST) -> RSTR` functions called from the shim's axum handlers.
- **`adrian-keycloak-client`** (workspace member, library) — a Rust client for Keycloak's admin API. Crates: `reqwest`, `serde`, `serde_json`. The client covers: realm CRUD, client CRUD, user federation provider config, identity broker config, session management. The client is auto-generated from Keycloak's OpenAPI spec via `utoipa = "4"` (when Keycloak ships one) or hand-written (current state — Keycloak's admin API is partially documented).
- **`adrian-migrate-from-adfs`** (workspace member, binary) — the AD FS migration CLI. Crates: `clap = "4"`, `powershell-rs = "0.2"` (PowerShell invocation via WinRM; if no mature crate exists, use `reqwest` with WinRM SOAP envelope hand-rolled), `serde_json`, `quick-xml`. The CLI's output is two files: `realm-export.json` (Keycloak import) and `claim-rules.yaml` (shim config).
- **`adrian-fed-cli`** (workspace member, binary) — the `adrian-fed` CLI. Crates: `clap`, `tokio`, `serde_json`, `tracing-subscriber`. Subcommands: `apply`, `realm create`, `realm set`, `client create`, `client set`, `broker add`, `broker add-entra`, `broker add-google`, `migrate-rp`, `migrate-wsfed` (per ADR-039), `migrate-apgroup` (per ADR-039).

Keycloak deployment artifacts (not Rust, but part of the framework's deployment):
- **`adrian-keycloak`** container image — based on `quay.io/keycloak/keycloak:25.0`, with the framework's theme JAR (custom login UI) and the framework's event-listener SPI (forwards events to the shim's audit endpoint) installed. The image is rebuilt on every Keycloak upstream release; the framework's CI validates the image against the shim's test suite.
- **`adrian-keycloak-theme`** JAR — a custom Keycloak theme that renders the framework's branding on login/consent pages. Built with Maven (Keycloak's theme build tooling); the framework's CI builds the JAR and publishes it to the framework's container registry alongside the Keycloak image.
- **`adrian-keycloak-event-listener`** SPI JAR — a Keycloak event-listener plugin that POSTs every authentication event to the shim's `/internal/audit` endpoint. Built with Maven; the framework's audit pipeline (per ADR-060) consumes the events.

Estimated effort: ~18 person-weeks for v1. Breakdown: shim (5 pw), claims-engine (3 pw), WS-Trust bridge (3 pw), Keycloak client library (2 pw), AD FS migration CLI (3 pw), `adrian-fed` CLI (2 pw). The claims-engine is the highest-risk item (PEG grammar correctness across the full AD FS rule-language surface).

## Implementation impact

The decision locks the Federation Gateway's v1 architecture. The Rust shim's public API (the `adrian-fed` CLI commands) is stable for v1. The claims-engine's rule-language coverage is documented (95% supported, 5% dropped with WARN); customers whose AD FS rules fall in the 5% are surfaced during migration and must rewrite.

Keycloak upgrades are the ongoing operational concern. The framework supports the current Keycloak LTS and the previous LTS for one year after the new LTS ships. Major upgrades may require shim updates (admin API changes, theme JAR recompilation).

The AD FS migration CLI is migration-critical. Customers moving from AD FS must run `adrian-migrate from-adfs` to translate configuration; the CLI's output (realm-export.json + claim-rules.yaml) is reviewed and committed to Git before apply. The CLI's translation is conservative (5% of rules dropped); customers with complex AD FS configurations should plan for a manual-review phase.

The WS-Trust bridge's 5-year deprecation timeline (per ADR-039) starts at v1.0. Customers using the bridge must migrate legacy RPs (SharePoint on-prem, Office desktop, custom .NET apps) to OIDC or SAML before v2.0.

## Cross-capability dependencies

- **Cert Service (Decision 8).** The shim's signing key is a cert issued by the framework's CA (enrolled via ACME with the `federation_signing` profile, stored in the HSM via PKCS#11, rotated every 90 days via the operator's `Reconcile` loop per ADR-038).
- **Core Directory.** The shim is the only federation component that talks to the directory; LDAP provides user lookup, group membership (via `memberOf` back-link per ADR-002), and attribute resolution. The shim caches results in `moka` to reduce directory load.
- **Auth Provider.** The shim validates user passwords via LDAP simple bind (which delegates to the Auth Provider). MFA is enforced by Keycloak's authenticator flow, which calls back to the shim's `/internal/mfa` endpoint.
- **Policy Engine (Decision 7).** Federation-service configuration (realms, clients, brokers) is stored in Git (per ADR-031) and applied via `adrian-fed apply`. Configuration changes are audited per ADR-060.
- **Operations (ADR-058).** The Federation Gateway is deployed as a StatefulSet (Keycloak + PostgreSQL) with the shim as a sidecar. The framework's operator manages the Federation Gateway lifecycle via a `FederationGateway` CRD.
- **Migration (PC-124 AD FS-to-framework).** The `adrian-migrate from-adfs` CLI is the migration entry point for AD FS.
- **Security (PC-123 threat model).** Federation Gateway compromise is a top Security threat; the HSM-bound signing key (per ADR-037) and the shim's audit logging (per ADR-060) are documented. The shim's claim-rule engine is a trusted-code boundary (rules can produce arbitrary claims; rules are authored by federation admins and reviewed via PR per ADR-031).
