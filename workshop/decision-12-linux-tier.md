# Workshop Decision 12 — Linux tier: SSSD primary + FreeIPA alt; Winbind deprecated; PBIS unsupported

## Status

Accepted — 2026-08-14. Tier-1 (architectural) decision made at the Day 2 final session of the Tier-1 ORQ Resolution Workshop. Resolves ORQ-202 (adopt FreeIPA as the Linux tier) and ORQ-203 (build native IPA-equivalent in the framework). Supersedes the open Linux-tier questions in ADR-050 (authselect standard PAM) and ADR-051 (KCM Linux API + macOS cache abstraction).

## ORQs resolved

- **ORQ-202** — "Adopt FreeIPA as the Linux tier?" → **Yes, as a supported alternative.** SSSD is the framework's primary Linux integration; FreeIPA is a supported alternative for customers who want a full Linux domain controller (with FreeIPA's own CA, DNS, and HBAC). The framework's Client SDK (per Decision 11) provides the framework-native Linux integration that bypasses both SSSD and FreeIPA where customers want the framework's native experience; SSSD and FreeIPA are the compatibility-and-familiarity paths.
- **ORQ-203** — "Build native IPA-equivalent in the framework?" → **No.** The framework does not build a Linux-domain-controller-equivalent (FreeIPA-clone) as a first-class component. The framework's Client SDK (per Decision 11) provides the framework-native Linux integration (PAM/NSS, Kerberos, cert enrollment, policy) that replaces FreeIPA's client-side functionality for framework-managed hosts; FreeIPA as a Linux domain controller is supported as an alternative for customers who want FreeIPA's server-side functionality (DNS, CA, HBAC, idoverride) integrated with the framework via cross-realm trust.

## Decision

The framework's Linux tier strategy is: **SSSD as the primary Linux integration** (with Rust-based enhancements via the framework's Client SDK); **FreeIPA as a supported alternative** for customers who want a full Linux domain controller; **Winbind is deprecated** (migration path to SSSD); **PBIS is unsupported** (already EOL by BeyondTrust).

### Concrete specification

1. **SSSD as primary Linux integration.** The framework's reference Linux deployment uses SSSD (`sssd-ad` provider) as the PAM/NSS/Kerberos integration layer. SSSD's `ad` provider is configured to use the framework's directory (via LDAP), the framework's KDC (via Kerberos), and the framework's CA (via the trust-manager per ADR-036). The framework's Client SDK (per Decision 11) is installed alongside SSSD on every Linux host; the SDK provides the framework's policy enforcement (`adrian-policy-daemon`), cert enrollment (`adrian-cert-agent`), and federation integration that SSSD does not provide.

   SSSD's configuration is generated by the framework's `adrian-cli join` command (per Decision 11) and written to `/etc/sssd/sssd.conf` with the framework's recommended settings:
   - `domains = adrian`
   - `config_file_version = 2`
   - `services = nss, pam, ifp` (`ifp` is the InfoPipe responder, used by the framework's SDK for fast user/group lookups via D-Bus)
   - `[domain/adrian]`:
     - `id_provider = ad`
     - `auth_provider = ad`
     - `chpass_provider = ad`
     - `access_provider = ad` (GPO-based access control, expanded per §2 below)
     - `ldap_schema = ad`
     - `ldap_uri = ldap://<dc>.<domain>`
     - `krb5_server = <dc>.<domain>`
     - `krb5_realm = <REALM>`
     - `ad_domain = <domain>`
     - `ad_server = <dc>.<domain>`
     - `use_fully_qualified_names = false` (the framework's directory uses short names by default; operators can opt-in to FQDNs)
     - `fallback_homedir = /home/%u`
     - `default_shell = /bin/bash`
     - `ldap_id_mapping = false` (the framework's directory uses POSIX UIDs/GIDs directly, per Day 1 identity-model decision; SSSD's id-mapping is disabled)
     - `ldap_user_principal = nosuchattr` (the framework's directory does not expose `userPrincipalName` for SSSD's principal-extraction; the framework uses `krb5_principal` directly)
     - `dyndns_update = true` (SSSD updates DNS for the host on join, per the framework's DNS strategy)
     - `dyndns_ttl = 3600`
     - `krb5_ccachedir = /run/user/%u` (per ADR-051 KCM Linux API)
     - `krb5_ccname_template = KCM:%u` (KCM cache, per ADR-051)
     - `gpo_access_enforcement = permissive` (default; see §2 for the framework's GPO access-control enhancements)

2. **Rust-based SSSD GPO access-control enhancements.** SSSD's `ad_gpo.c` implements only the Security CSE subset (`[Privilege Rights]` from `GptTmpl.inf`), per [docs/09-linux-equivalents/03-sssd-gpo-access.md](../docs/09-linux-equivalents/03-sssd-gpo-access.md). The framework ships `adrian-sssd-gpo` — a Rust library that extends SSSD's GPO access-control to cover the full `Security` PolicyArea (per Decision 7's PolicyArea enum). The library is loaded by SSSD via the `gpo_access_provider = adrian` configuration directive (a new SSSD access provider that the framework contributes upstream to SSSD). The library implements:
   - `adrian_access_check(user, host, policy_doc) -> AccessDecision` — evaluates the policy's `Security` area against the user and host, returning `Allow`, `Deny`, or `PermitWithLogonHours`.
   - `LogonHours` enforcement — the framework's `Security` area's `PermitLogonHours` setting is enforced by the library, replacing SSSD's lack of logon-hours support.
   - `HostAccessControl` (HAC) — the framework's `Security` area's `PermitHosts` setting is enforced by the library, replacing SSSD's lack of host-based access control (other than via `simple` access provider's `simple_allow_hosts`, which does not integrate with GPO).
   - `GroupPolicyAccessControl` — the framework's `Security` area's `PermitGroups` setting is enforced by the library, replacing SSSD's `simple_allow_groups`.

   The library uses the framework's Client SDK (per Decision 11) to fetch the policy document via the WebSocket push (per ADR-028) instead of SSSD's existing GPO-fetch-over-SMB path; this gives the library real-time policy updates (vs. SSSD's 90-minute background refresh). The library is ~2K lines of Rust, exposed to SSSD via a C ABI (`libadrian_sssd_gpo.so`).

3. **FreeIPA as supported alternative.** Customers who want a full Linux domain controller (with FreeIPA's CA, DNS, HBAC, and `idoverride` integration) deploy FreeIPA alongside the framework, with a cross-realm trust between FreeIPA and the framework's directory. The framework's `adrian-cli trust establish --peer freeipa --realm <freeipa-realm>` command configures the cross-realm trust:
   - Creates the trust object in the framework's directory (per [docs/03-directory-schema/04-trusts-topology.md](../docs/03-directory-schema/04-trusts-topology.md)).
   - Configures the framework's KDC to issue cross-realm TGTs (per [ADR-013](../adr/ADR-013-cross-realm-tgt-referral.md)).
   - Configures the framework's directory to expose the FreeIPA realm's users/groups via the `altSecurityIdentities` attribute (so framework-managed Windows/macOS hosts can resolve FreeIPA users when needed).
   - Configures FreeIPA's `idoverride` to map FreeIPA users to framework-directory users (via the framework's UUID, exposed in the `ipaAnchorUUID` attribute).

   FreeIPA-managed Linux hosts use FreeIPA's own client tooling (`ipa-client-install`, `sssd-ipa` provider) for PAM/NSS/Kerberos; they do not use the framework's Client SDK directly. The framework's policy and cert services are accessible to FreeIPA-managed hosts via the framework's REST/gRPC API (per ADR-061), but the native FreeIPA client experience is preserved.

4. **Winbind deprecation.** Winbind (Samba's `winbindd` daemon, used as a PAM/NSS provider for AD integration on Linux) is deprecated. The framework's documentation explicitly recommends migrating from Winbind to SSSD; the framework's `adrian-cli migrate from-winbind` command:
   - Reads the existing `/etc/samba/smb.conf` and `/etc/krb5.conf` configuration.
   - Generates `/etc/sssd/sssd.conf` with the equivalent settings (translating `winbind`'s `idmap` configuration to SSSD's `ldap_id_mapping` settings; the framework's directory uses POSIX UIDs/GIDs directly so id-mapping is disabled, but the translation preserves existing UID/GID assignments where possible via the framework's id-mapping migration tooling per Day 1 identity-model decision).
   - Generates the new `/etc/krb5.conf` for the framework's KDC.
   - Runs `authselect select adrian-with-sudo --force` (per ADR-050) to switch PAM/NSS to the framework's authselect profile.
   - Restarts `sssd.service` and disables `winbind.service`.

   Winbind is not uninstalled (Samba may still be needed for SMB-client functionality); only `winbindd` as a PAM/NSS provider is deprecated. Customers who need Winbind for legacy reasons (e.g., NTLM-only appliances) can continue to use it, but the framework does not test or support Winbind configurations.

5. **PBIS unsupported.** BeyondTrust PBIS (formerly Likewise) is unsupported. PBIS was EOL'd by BeyondTrust in 2023; the framework's documentation explicitly lists PBIS as unsupported and recommends the same `adrian-cli migrate from-winbind` path for PBIS-to-SSSD migration (PBIS uses a Winbind-equivalent PAM/NSS stack that can be migrated via the same tooling).

6. **HBAC vs URA access-control model.** AD uses URA (User Rights Assignment) for logon-rights access control (per `GptTmpl.inf`'s `[Privilege Rights]` section: `SeAllowLogonLocally`, `SeDenyLogonLocally`, `SeAllowLogonThroughTerminalServices`, etc.). FreeIPA uses HBAC (Host-Based Access Control) for logon-rights access control (per FreeIPA's `hbacrule` object: `host`, `hostgroup`, `service`, `servicegroup`, `user`, `usergroup`). The two models differ: URA is policy-driven (GPO-defined, applied to all hosts in the OU); HBAC is rule-driven (defined centrally, evaluated per-host).

   The framework supports both:
   - **URA (default for SSSD primary tier)** — the framework's `Security` PolicyArea (per Decision 7) defines URA-equivalent settings (`PermitLogonLocally`, `DenyLogonLocally`, etc.). The framework's `adrian-sssd-gpo` library (per §2) enforces these settings on SSSD-primary Linux hosts. The `adrian-policy-daemon` (per Decision 11) enforces the same settings on framework-SDK-native Linux hosts.
   - **HBAC (default for FreeIPA alternative tier)** — when a customer deploys FreeIPA alongside the framework, FreeIPA's HBAC rules apply to FreeIPA-managed Linux hosts. The framework's directory exposes the HBAC-equivalent rules (per `Security` PolicyArea's `PermitHosts` and `PermitGroups` settings) to FreeIPA via the cross-realm trust's `altSecurityIdentities` attribute, so FreeIPA can import framework-defined rules into HBAC if the customer chooses. The `adrian-cli trust sync-hbac` command syncs the framework's `Security` area's `PermitHosts`/`PermitGroups` to FreeIPA's HBAC rules.

7. **Selective authentication.** AD's selective authentication (per [PC-121](../catalog/11-security-threat-model.md)) is rarely used because it requires per-host `Allowed-To-Authenticate` permission on the user object, which is operationally complex. The framework replaces selective authentication with HBAC-equivalent rules (per §6): the framework's `Security` PolicyArea's `PermitHosts` setting (per Decision 7) controls which hosts a user can authenticate to, evaluated at logon time by the `adrian-sssd-gpo` library or the `adrian-policy-daemon`. This is simpler than AD's selective authentication (no per-user `Allowed-To-Authenticate` permission to manage) and more flexible (the rule is policy-driven, not directory-attribute-driven).

8. **KCM cache (per ADR-051).** All Linux hosts use KCM (Kerberos Cache Manager) as the Kerberos credential cache, per [ADR-051](../adr/ADR-051-kcm-linux-api-macos-cache-abstraction.md). KCM is a per-user daemon (`kcm` service) that stores Kerberos tickets in memory (or in a configurable backing store), accessed via a UNIX socket. The framework's `adrian-cli join` configures KCM via `krb5_ccname_template = KCM:%u` in `/etc/sssd/sssd.conf` and `default_ccache_name = KCM:%u` in `/etc/krb5.conf`. The framework's Client SDK (per Decision 11) reads tickets from KCM (via the `kcm-client` library) for framework-application Kerberos operations.

9. **`authselect` profile.** Per [ADR-050](../adr/ADR-050-authselect-standard-pam.md), the framework ships a custom `authselect` profile (`adrian-with-sudo`) that configures PAM to use `pam_adrian.so` (the framework's PAM module per Decision 11) for authentication and `pam_sss.so` (SSSD's PAM module) as a fallback (for compatibility during migration). The profile also configures `pam_sudo.so` for sudo via SSSD's sudo rules (or the framework's `Security` PolicyArea's `Sudoers` setting, per Decision 7). The framework's `adrian-cli join` runs `authselect select adrian-with-sudo --force` to apply the profile.

10. **POSIX UID/GID assignment.** Per Day 1 identity-model decision, the framework's directory uses POSIX UIDs/GIDs directly (assigned by the directory at user/group creation time), not SSSD's id-mapping (which derives UIDs/GIDs from Windows SIDs via a slice algorithm). SSSD's `ldap_id_mapping = false` setting (per §1) reflects this. The framework's `adrian-cli migrate from-ad` command preserves existing UIDs/GIDs during migration (via the framework's id-mapping migration tooling that reads the existing AD `uidNumber`/`gidNumber` attributes and writes them to the framework's directory). Customers who used SSSD's id-mapping in their existing AD deployment can choose to either (a) preserve the id-mapped UIDs/GIDs (the framework writes the id-mapped values to `uidNumber`/`gidNumber` in its directory, so SSSD's id-mapping is no longer needed) or (b) reassign UIDs/GIDs (the framework generates new UIDs/GIDs, requiring a file-system UID/GID migration). Option (a) is the default; option (b) is for customers who want to consolidate UID/GID ranges.

11. **Container-native Linux deployment.** Per [ADR-058](../adr/ADR-058-container-native-dcs-operator.md), the framework's DCs run as containers on Kubernetes. The framework's Linux client (SSSD + Client SDK) runs as a DaemonSet on every Kubernetes node that hosts framework-aware pods; framework-aware pods mount the SSSD socket (`/var/run/secrets/adrian/sssd.sock`) and the KCM socket (`/var/run/secrets/adrian/kcm.sock`) as volumes, and `pam_adrian.so` / `nss_adrian.so.2` are available in the pod's container image (via a shared base image `adrian-base:1.0` that includes the framework's PAM/NSS modules and the Rust core library). Framework-unaware pods (third-party images) can use SSSD's `infopipe` D-Bus interface for user/group lookups without the framework's PAM/NSS modules in the image.

## Rationale

Three candidate architectures were considered.

**Candidate A: FreeIPA as the sole Linux tier.** Adopt FreeIPA as the framework's Linux identity platform; the framework's directory trusts FreeIPA, and Linux hosts join FreeIPA (not the framework). Rejected because (a) FreeIPA is a separate Linux domain controller with its own CA (Dogtag), DNS (Bind), and HBAC — adopting FreeIPA as the sole Linux tier means the framework's directory is not the source of truth for Linux identity, which breaks the framework's "one directory, one identity" model. (b) FreeIPA's directory schema (`ipa*` object classes, `ipaConfigString` attribute, `cn=etc,<suffix>` configuration container) is incompatible with the framework's directory schema (per Day 1 schema decision); the framework would have to maintain FreeIPA-specific schema elements in its own directory or maintain a parallel FreeIPA directory. (c) FreeIPA's release cadence is controlled by the FreeIPA project (Red Hat), not by the framework; the framework cannot ship Linux-tier fixes without waiting for the next FreeIPA release. (d) FreeIPA's client is Python, requiring a Python interpreter on every Linux host; for embedded / minimal Linux deployments (containers, IoT), this is a non-starter. (e) FreeIPA does not support Windows or macOS at all, so the framework would still need separate Windows and macOS clients — same three-codebase problem.

**Candidate B: Framework-native Linux client (no SSSD, no FreeIPA).** Use the framework's Client SDK (per Decision 11) as the sole Linux integration; `pam_adrian.so` + `nss_adrian.so.2` replace SSSD entirely. Rejected because (a) SSSD is the de facto standard for Linux-AD integration, with a large operator community, extensive documentation, and broad distro support (RHEL, Ubuntu, SUSE, Debian all ship SSSD). Customers expect SSSD as the Linux integration path; requiring them to use the framework's PAM/NSS modules exclusively is a non-starter for adoption. (b) SSSD's `ifp` (InfoPipe) responder provides D-Bus-based user/group lookups that the framework's SDK can consume (per §1), avoiding the need to re-implement SSSD's caching, offline support, and `be_ptask` scheduler. (c) SSSD's `ad` provider is mature, with extensive testing against AD; the framework's directory is AD-compatible (per Day 1 schema decision), so SSSD's `ad` provider works against the framework's directory with minimal configuration. (d) The framework's PAM/NSS modules (per Decision 11) are available as an alternative for customers who want the framework-native experience; the framework does not need to force them on customers who prefer SSSD.

**Candidate C: Winbind as the primary Linux tier.** Use Samba's `winbindd` as the framework's Linux integration. Rejected because (a) Winbind is a Samba component, and the framework does not adopt Samba (per Decision 10's rejection of Samba's `smbd`). Using `winbindd` would require shipping Samba (or at least the Winbind subset), which is GPLv3 and creates the same license conflict as Decision 10 rejected. (b) SSSD is strictly better than Winbind for AD integration (better caching, better offline support, better GPO support, better performance) — Red Hat deprecated Winbind in favor of SSSD in RHEL 6 (2010), and the industry has followed. (c) Winbind's `idmap` configuration is complex and error-prone (the `idmap_rid`, `idmap_ad`, `idmap_autorid` backends have different semantics and produce different UID/GID assignments for the same SID); SSSD's `ldap_id_mapping` is simpler. (d) Winbind is coupled to Samba's `smbd` and `nmbd` (it shares Samba's `passdb` and `secrets.tdb`); using Winbind without `smbd` requires extracting Winbind from Samba, which is non-trivial.

The chosen SSSD-primary + FreeIPA-alternative model gives the framework: (a) SSSD as the de-facto-standard Linux integration path (familiar to operators, mature, well-tested); (b) FreeIPA as a supported alternative for customers who want a full Linux domain controller (preserving FreeIPA's CA, DNS, HBAC, and `idoverride` investment); (c) the framework's Client SDK (per Decision 11) as the framework-native path for customers who want the framework's native experience; (d) Winbind and PBIS deprecation (migration path to SSSD), aligning with the industry direction; (e) the framework's Rust-based SSSD enhancements (`adrian-sssd-gpo`) that close SSSD's GPO access-control gaps without requiring customers to abandon SSSD.

The Rust-based SSSD enhancements are the framework's key differentiator. SSSD's `ad_gpo.c` covers only the Security CSE subset (`[Privilege Rights]`); the framework's `adrian-sssd-gpo` library extends coverage to the full `Security` PolicyArea (logon hours, host access control, group policy access control) via a new SSSD access provider (`gpo_access_provider = adrian`) that the framework contributes upstream to SSSD. This gives SSSD customers the framework's enhanced access control without requiring them to use the framework's PAM/NSS modules.

## Trade-offs accepted

- **SSSD is C, not Rust.** SSSD is a C codebase; the framework's Rust-based enhancements are loaded as a shared library (`libadrian_sssd_gpo.so`) via a C ABI, but SSSD itself remains C. Memory-safety bugs in SSSD's C code are outside the framework's control. Acceptable because SSSD is mature, well-tested, and actively maintained by Red Hat; the framework's threat model treats SSSD as trusted infrastructure (like `glibc` or `openssl`). The framework's Rust-based PAM/NSS modules (`pam_adrian.so`, `nss_adrian.so.2`, per Decision 11) are an alternative for customers who want end-to-end Rust.
- **FreeIPA is Java + Python + C.** FreeIPA's server is Java (Dogtag CA), Python (FreeIPA framework), and C (Bind DNS, SSSD). Customers choosing the FreeIPA alternative tier inherit this stack. Acceptable because FreeIPA is the customer's choice, not the framework's default; the framework's documentation explains the trade-offs.
- **SSSD upstream contribution required.** The `adrian-sssd-gpo` library's SSSD integration (the new `gpo_access_provider = adrian` directive) requires a new SSSD access-provider plugin API, which the framework must contribute upstream to SSSD. The upstream contribution may take months to merge (SSSD's review cadence is slow). Until the contribution merges, the framework ships `adrian-sssd-gpo` as a side-loaded library that hooks into SSSD's existing `gpo_access_provider = simple` via a configuration override (a temporary measure documented as such). Acceptable because the side-loaded library is functionally equivalent to the upstream contribution; the upstream contribution is a long-term maintainability improvement.
- **Cross-realm trust with FreeIPA adds complexity.** Customers choosing the FreeIPA alternative tier must operate a cross-realm trust between FreeIPA and the framework's directory, with the operational complexity that implies (trust password rotation per [ADR-062](../adr/ADR-062-trust-password-auto-rotation.md), Kerberos capaths per [ADR-069](../adr/ADR-069-cross-realm-capaths.md), name-suffix routing). Acceptable because the framework's documentation explains the trade-offs and the framework's tooling automates trust setup.
- **Winbind customers must migrate.** Customers with existing Winbind deployments must migrate to SSSD (or the framework's PAM/NSS modules). The migration tooling (`adrian-cli migrate from-winbind`) handles the configuration translation, but the operational transition (testing, user communication, rollback plan) is the customer's responsibility. Acceptable because Winbind is already deprecated by Red Hat and SUSE; the framework's deprecation aligns with industry direction.
- **No PBIS support.** Customers with existing PBIS deployments must migrate to SSSD (PBIS uses a Winbind-equivalent stack that the Winbind migration tooling handles). BeyondTrust PBIS is already EOL, so this is not a new deprecation; the framework explicitly does not provide PBIS migration support beyond the Winbind tooling. Acceptable because PBIS customers have known about the EOL since 2023.

## Rust implementation implications

The decision is implementable in pure Rust for the framework's components; SSSD and FreeIPA are C/Java/Python (no Rust changes for them). The crate graph:

- **`adrian-sssd-gpo`** (workspace member, `cdylib`) — the SSSD GPO access-control enhancement library. Crates: `tokio = "1"`, `serde = "1"`, `serde_json = "1"`, `ldap3 = "0.11"` (for direct directory queries when the SDK's WebSocket push is unavailable), `adrian-sdk` (for policy retrieval via WebSocket push per ADR-028), `tracing = "0.1"`. The library exposes a C ABI (`libadrian_sssd_gpo.so`) with functions like `adrian_sssd_gpo_check_access(const char* user, const char* host, const char* policy_json) -> int32_t`. The library is loaded by SSSD via the `gpo_access_provider = adrian` configuration directive (or, until the upstream contribution merges, via a side-loaded library that hooks into SSSD's `simple` access provider). ~2K lines of Rust.
- **`adrian-cli migrate-from-winbind`** (workspace member, subcommand of `adrian-cli`) — the Winbind-to-SSSD migration tool. Crates: `clap = "4"`, `tokio`, `serde`, `serde_json`. The tool reads `/etc/samba/smb.conf` and `/etc/krb5.conf`, generates `/etc/sssd/sssd.conf` and a new `/etc/krb5.conf`, runs `authselect select adrian-with-sudo --force`, restarts `sssd.service`, and disables `winbind.service`. ~800 lines of Rust.
- **`adrian-cli trust-establish-freeipa`** (workspace member, subcommand of `adrian-cli`) — the FreeIPA cross-realm trust setup tool. Crates: `clap`, `tokio`, `ldap3` (for directory trust-object creation), `gss-api` (for Kerberos cross-realm configuration). The tool creates the trust object in the framework's directory, configures the framework's KDC for cross-realm TGTs (per ADR-013), and configures FreeIPA's `idoverride` mapping (via FreeIPA's JSON-RPC API, called via `reqwest`). ~1.2K lines of Rust.
- **`adrian-cli trust-sync-hbac`** (workspace member, subcommand of `adrian-cli`) — syncs the framework's `Security` PolicyArea's `PermitHosts`/`PermitGroups` to FreeIPA's HBAC rules. Crates: `clap`, `tokio`, `reqwest` (for FreeIPA's JSON-RPC API), `serde_json`. ~600 lines of Rust.
- **`adrian-authselect-profile`** (workspace member, data) — the `adrian-with-sudo` authselect profile. This is a set of PAM/NSS configuration files (not Rust) installed under `/usr/share/authselect/default/adrian-with-sudo/`. The profile's PAM stack uses `pam_adrian.so` (the framework's PAM module per Decision 11) for authentication and `pam_sss.so` as a fallback.
- **`adrian-base-container`** (workspace member, container image) — the shared base image for framework-aware Kubernetes pods. Built from `ubuntu:22.04` (or `redhat/ubi9:latest`), with `pam_adrian.so`, `nss_adrian.so.2`, the Rust core library, and the framework's SSSD configuration installed. The image is published to the framework's container registry as `adrian-base:1.0`.

The framework's `adrian-cli join` command (per Decision 11) is the Linux host's primary integration entry point. On Linux, `adrian-cli join` performs:
1. Generates the host's machine keypair (in TPM2 if available; otherwise in `/etc/krb5.keytab`).
2. Creates the host object in the framework's directory via LDAP.
3. Registers the host's SPNs (`host/<fqdn>`, `cifs/<fqdn>`, `HTTP/<fqdn>`, `ldap/<fqdn>`).
4. Writes the machine key to `/etc/krb5.keytab` (or TPM2).
5. Generates `/etc/sssd/sssd.conf` with the framework's recommended settings (per §1).
6. Generates `/etc/krb5.conf` for the framework's KDC (with KCM cache per ADR-051).
7. Runs `authselect select adrian-with-sudo --force` (per ADR-050).
8. Enables and starts `sssd.service`, `kcm.service`, `adrian-policy-daemon.service`, `adrian-cert-agent.service`.
9. Triggers the initial policy pull (via WebSocket per ADR-028).
10. Triggers the initial cert enrollment (per Decision 8).

Estimated effort: ~12 person-weeks for v1. Breakdown: `adrian-sssd-gpo` library (4 pw, highest-risk due to SSSD integration), Winbind migration tooling (1 pw), FreeIPA trust setup + HBAC sync (2 pw), authselect profile (1 pw), `adrian-cli join` Linux path (2 pw), `adrian-base-container` image (1 pw), SSSD upstream contribution (1 pw, ongoing). The `adrian-sssd-gpo` library is the critical-path item; the framework's CI runs SSSD's GPO access-control test suite against the library on every PR.

## Implementation impact

The decision locks the Linux tier's v1 architecture. SSSD-primary is the default; FreeIPA-alternative is opt-in; Winbind and PBIS are deprecated/unsupported. The framework's `adrian-cli join` is the sole Linux-join path; the `adrian-cli migrate from-winbind` tool handles Winbind-to-SSSD migration.

The `adrian-sssd-gpo` library is the highest-risk implementation item. The library's SSSD integration requires either (a) a new SSSD access-provider plugin API (upstream contribution, slow) or (b) a side-loaded library that hooks into SSSD's existing `simple` access provider (faster, less clean). The framework ships option (b) for v1 and works toward option (a) for v2 (or as soon as the upstream contribution merges). The library's CI runs SSSD's GPO access-control test suite on every PR.

The FreeIPA cross-realm trust setup is the second-highest-risk item. Cross-realm trust is operationally complex (trust password rotation, Kerberos capaths, name-suffix routing); the framework's tooling automates the setup, but customers must understand the operational implications. The framework's documentation includes a "FreeIPA cross-realm trust operations guide" that explains the trust lifecycle, troubleshooting, and rollback.

The Winbind migration tooling is well-understood (Winbind-to-SSSD migration is a Red Hat-documented procedure); the framework's tooling automates the procedure with the framework-specific configuration translation. The tooling's CI runs on RHEL 8, RHEL 9, Ubuntu 20.04, Ubuntu 22.04, Debian 11, and Debian 12 to validate distro compatibility.

## Cross-capability dependencies

- **Core Directory.** SSSD's `ad` provider queries the framework's directory via LDAP; the directory's AD-compatible schema (per Day 1 schema decision) makes this work. The directory's `memberOf` back-link (per ADR-002) is used for group-membership resolution. The directory's POSIX UID/GID attributes (`uidNumber`, `gidNumber`) are used directly (no id-mapping).
- **KDC.** SSSD's `ad` provider uses the framework's KDC for Kerberos authentication. The KDC's cross-realm TGT referral (per ADR-013) is used for the FreeIPA cross-realm trust.
- **Auth Provider.** SSSD's PAM module (`pam_sss.so`) delegates password validation to the Auth Provider via LDAP simple bind. The framework's `pam_adrian.so` (per Decision 11) is an alternative for customers who want end-to-end Rust.
- **Policy Engine (Decision 7).** The `adrian-sssd-gpo` library retrieves the framework's `Security` PolicyArea policy via the WebSocket push (per ADR-028) and enforces it during PAM `pam_sm_acct_mgmt`. The framework's `adrian-policy-daemon` (per Decision 11) is the host-side policy daemon.
- **Cert Service (Decision 8).** The `adrian-cert-agent` (per Decision 11) is the host-side cert enrollment agent, replacing FreeIPA's `certmonger` for framework-managed hosts. FreeIPA-managed hosts continue to use `certmonger` against FreeIPA's Dogtag CA.
- **Federation Gateway (Decision 9).** Not a direct dependency; Linux hosts access the federation gateway via standard OIDC/SAML clients (not via SSSD or the SDK's federation module).
- **Operations (ADR-058).** The framework's Linux client (SSSD + Client SDK) runs as a DaemonSet on Kubernetes nodes for container-native deployments (per §11).
- **Migration (PC-127).** The `adrian-cli migrate from-winbind` tool is the migration entry point for Winbind customers. The `adrian-cli join` command is the entry point for new Linux hosts. The framework's documentation includes a "Linux tier migration guide" covering AD-with-SSSD → framework-with-SSSD, AD-with-Winbind → framework-with-SSSD, AD-with-PBIS → framework-with-SSSD (unsupported; same as Winbind path), and standalone-OpenLDAP → framework-with-SSSD.
- **Security (PC-123 threat model).** SSSD is treated as trusted infrastructure (mature, well-tested, actively maintained). The framework's `adrian-sssd-gpo` library is the security-relevant code path (it enforces access control); the library's Rust memory safety and the audit logging (per ADR-060) are documented in the Security threat model. The FreeIPA cross-realm trust is documented as an additional attack surface (cross-realm ticket forgery, name-suffix routing bypass) with mitigations per ADR-013 and ADR-069.
