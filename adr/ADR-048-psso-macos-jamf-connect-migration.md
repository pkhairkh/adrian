# ADR-048: PSSO Extension as Modern macOS Path; Jamf Connect Migration

## Status

Accepted — 2026-08-13

## Context

Jamf Connect is two cooperating binaries: `Jamf Connect Login` (a `SecurityAgentPlugins` bundle at `/Library/Security/SecurityAgentPlugins/JamfConnectLogin.bundle` that replaces the `loginwindow:login` mechanism in `AuthorizationDB`'s `system.login.console` right with `jamf_connect_login:login`) and `Jamf Connect Menu Bar` (a user LaunchAgent at `com.jamf.connect.menubar` that maintains an OIDC refresh token in the user's keychain and optionally drives the Apple Kerberos SSO Extension for on-prem AD Kerberos). The login mechanism opens a WKWebView pointed at the IdP `authorize` endpoint with `response_type=code`, `scope=openid profile email offline_access`, `code_challenge=<S256>`, and `code_challenge_method=S256` (PKCE per RFC 8252). After the IdP redirects back to `com.jamf.connect://callback/auth`, Jamf Connect Login exchanges the authorization code for tokens at the IdP `token` endpoint and decodes the `id_token` JWT to extract `sub`/`email`/`preferred_username` for local account creation, per [docs/08-macos-equivalents/03-jamf-connect-pro.md](../docs/08-macos-equivalents/03-jamf-connect-pro.md).

The fragile path is the password sync agent (`com.jamf.connect.sync` LaunchAgent, runs every 15 minutes by default). The agent: (a) calls PAM with the user's current password against `pam_jamfconnect` (a custom PAM module installed in `/usr/lib/pam/`), (b) `pam_jamfconnect` checks the password against the local ShadowHash (PBKDF2-SHA512 in the user's plist at `/var/db/dslocal/nodes/Default/users/<short>.plist`), (c) the agent issues an OIDC ROPG (Resource Owner Password Grant) token request with the same password at the IdP's `token` endpoint with `grant_type=password`, (d) if the IdP rejects (HTTP 401 because the user changed their password at the IdP directly, bypassing Jamf Connect), the agent surfaces a "Password Sync Required" notification and prompts the user to enter the new password, (e) the agent writes the new ShadowHash via `opendirectoryd`. During the divergence window — between the IdP password change and the user entering the new password in Jamf Connect — FileVault unlock uses the OLD password (because FileVault unlock happens at boot, before the user session starts and before the sync agent runs). If the user has forgotten the old password (because they changed it remotely), they are locked out of FileVault.

This pattern is structurally identical to the one Enterprise Connect used (PAM-based password sync) and to NoMAD's `LocalPasswordSync = true` mode, both of which Jamf deprecated in favor of PSSO Hardware_Bound mode (which eliminates password sync entirely by using SEP-bound keys for IdP auth), per [docs/08-macos-equivalents/06-enterprise-connect-nomad.md](../docs/08-macos-equivalents/06-enterprise-connect-nomad.md). Jamf support data shows ~5-8% of Jamf Connect deployments experience at least one FileVault lockout per year due to password sync divergence, requiring a recovery key unlock + Jamf Connect re-enrollment. The cost per incident is ~30 minutes of helpdesk time plus user productivity loss; for a 10,000-Mac fleet, this is ~500-800 incidents per year, or roughly 250-400 hours of helpdesk time.

The framework cannot recommend Jamf Connect as the macOS SSO path. The ROPG password sync design is structurally fragile — the divergence window is unavoidable as long as the IdP password can be changed outside Jamf Connect (which it always can: IdP web UI, IdP admin tools, IdP self-service password reset). PSSO Hardware_Bound mode eliminates the problem entirely by using a SEP-bound ECDSA P-256 key that signs IdP token requests; the user's password never travels to the IdP, and password changes do not invalidate the SEP key. Per [PC-087](../catalog/08-client-sdk.md#pc-087--macos-jamf-connect--ropg-password-sync-is-fragile-during-idp-password-change)'s constraints, the framework must support PSSO Hardware_Bound mode (no password sync needed because the SEP key never changes on password rotation), support password-derived fallback for Intel Macs without T2 (cannot use Hardware_Bound), provide a migration tool that detects existing Jamf Connect deployments (`com.jamf.connect.login.plist` presence), installs the PSSO profile, and removes Jamf Connect on next reboot, and handle the FileVault recovery scenario (recovery key escrow flow that re-derives the FileVault key from a helpdesk-issued token, per PC-097 / ADR-053).

## Decision

The framework's macOS client will adopt Platform SSO (PSSO) Extension as the modern authentication path for macOS 13+, with Hardware_Bound mode (SEP-bound ECDSA P-256 key) as the default for T2/Apple Silicon Macs and Password-derived mode as the fallback for Intel Macs without T2. The framework will document Jamf Connect as deprecated and provide an automated migration tool (`framework-migrate-jamf-connect`) that detects existing Jamf Connect deployments, installs the PSSO profile via MDM, and schedules Jamf Connect removal on next reboot. The framework's macOS client will use `AuthorizationCopyRightEx` with `kAuthorizationCredentialTypeSSO` to retrieve IdP tokens for calling applications, interoperate with the keychain-backed `API:Initialdefaultcache` ticket cache (per ADR-051), and route Kerberos sub-payload configuration via `sso_util configure`.

**Concrete specification**:

- The framework's macOS client MUST ship an MDM profile template for `com.apple.configuration-ext.platform-sso` with `AuthenticationMethod: Hardware_Bound` as the default for T2/Apple Silicon Macs. The profile MUST include the framework's IdP `AuthenticationClient` dict with `Type: Kerberos` (for on-prem AD) and `Type: OIDC` (for cloud IdP), per [docs/08-macos-equivalents/04-platform-sso-extension.md](../docs/08-macos-equivalents/04-platform-sso-extension.md).
- The framework's macOS client MUST ship an MDM profile template for `com.apple.KerberosSSO` (the Kerberos sub-payload) with `Realm`, `Domains`, `SiteCode`, `UseSiteAutoDiscovery`, and `ManagementPrincipal` keys populated from the framework's directory configuration. The profile MUST be co-deployed with the PSSO profile.
- The framework's macOS client MUST fall back to PSSO `AuthenticationMethod: Password` (password-derived mode) on Intel Macs without T2. The installer MUST detect the Mac model (`sysctl hw.model` and `ioreg -l | grep -i "secure-enclave"`) and select the appropriate PSSO mode automatically. Password-derived mode MUST be documented as less secure than Hardware_Bound mode (the password-derived key is recoverable if the user's macOS password is compromised).
- The framework's macOS client MUST use `sso_util configure -a <IdP-type> -r <RelyingParty-URL> -k <ClientID>` for PSSO configuration and `sso_util configure -r <REALM> -u <user>` for Kerberos sub-payload configuration on first enrollment. The installer MUST run `sso_util configure` automatically when the MDM profile is installed; manual `sso_util` invocation is supported for troubleshooting.
- The framework's macOS client MUST interoperate with the keychain-backed `API:Initialdefaultcache` ticket cache (per ADR-051). The framework's macOS client MUST NOT set `KRB5CCNAME=FILE:...` to override the cache type; doing so breaks PSSO Extension's auto-renewal at 75% of TGT lifetime.
- The framework's macOS client MUST provide an `AuthorizationCopyRightEx` wrapper that retrieves IdP tokens via `kAuthorizationCredentialTypeSSO` for calling applications. The wrapper MUST return the token, the token's expiry timestamp, and the refresh token (if available) to the calling application.
- The framework MUST ship `framework-migrate-jamf-connect`, a migration tool that: (a) detects existing Jamf Connect deployments by checking for `/Library/Security/SecurityAgentPlugins/JamfConnectLogin.bundle` and `com.jamf.connect.login.plist`, (b) reads the existing Jamf Connect configuration (IdP `ClientID`, `RelyingParty-URL`, Kerberos `Realm`) from the plist, (c) generates a PSSO + Kerberos sub-payload MDM profile from the Jamf Connect configuration, (d) installs the PSSO profile via `profiles install -path <profile.mobileconfig>`, (e) schedules Jamf Connect removal on next reboot by writing a LaunchDaemon that runs `rm -rf /Library/Security/SecurityAgentPlugins/JamfConnectLogin.bundle` and removes the `com.jamf.connect.login` AuthorizationDB mechanism, (f) verifies PSSO is functional by running `sso_util cache -l` and asserting a valid ticket is returned, (g) writes a migration-completion log to `/var/log/framework-migrate-jamf-connect.log`.
- The framework MUST support the FileVault recovery scenario (per PC-097 / ADR-053): if the user is locked out of FileVault after a Jamf Connect → PSSO migration, the framework's macOS client MUST support a recovery key escrow flow that re-derives the FileVault key from a helpdesk-issued token via the framework directory's `recoveryKey` attribute.
- The framework's macOS client MUST document Enterprise Connect (removed in macOS 10.15) and NoMAD (community-maintained, EOL after Jamf acquired Orchard & Grove in May 2021) as out of scope; customers on Enterprise Connect must upgrade to macOS 13+ for PSSO support, and customers on NoMAD must migrate to PSSO via the framework's migration tool (NoMAD's configuration is structurally similar to Jamf Connect's, so the migration tool supports both).
- The framework's automated test suite MUST include a PSSO end-to-end test on macOS 13+: enroll a test Mac via the framework's MDM profile, verify `sso_util cache -l` returns a valid ticket, verify `AuthorizationCopyRightEx` returns a valid IdP token, verify FileVault unlock succeeds with the user's macOS password (no password sync divergence), verify Kerberos TGS-REQ to a framework-hosted SMB share succeeds via the `API:Initialdefaultcache` ticket cache.
- The framework's automated test suite MUST include a Jamf Connect migration test: deploy Jamf Connect on a test Mac, run `framework-migrate-jamf-connect`, verify Jamf Connect is removed on reboot, verify PSSO is functional, verify the user's FileVault unlock continues to work after migration.

## Rationale

The decision is forced by the structural fragility of the ROPG password sync design. As long as the IdP password can be changed outside the sync agent (web UI, admin tools, self-service reset), the divergence window is unavoidable, and FileVault lockouts will occur at a measurable rate (5-8% per year per Jamf support data). PSSO Hardware_Bound mode eliminates the divergence window by decoupling the IdP authentication from the user's password: the SEP-bound ECDSA P-256 key signs IdP token requests, and password changes do not invalidate the key. This is a structural fix, not a workaround; the framework cannot justify recommending a known-fragile pattern when a robust alternative exists.

The decision is also forced by Apple's deprecation timeline. Enterprise Connect was removed in macOS 10.15; NoMAD is community-maintained only (Orchard & Grove was acquired by Jamf in May 2021, ending active development); Jamf Connect delegates Kerberos to the Kerberos SSO Extension and is itself moving toward PSSO for passwordless. The framework's recommendation aligns with Apple's direction rather than fighting it. PSSO is the only first-party passwordless path on macOS 13+; earlier macOS versions (10.15-12.x) have the Kerberos SSO Extension but not full PSSO and are documented as out of scope for passwordless (the framework supports them via Kerberos SSO Extension + Jamf Connect compat mode for migration customers, but new deployments require macOS 13+).

The decision to ship a migration tool (rather than just documentation) is forced by the operational reality of Jamf Connect deployments. Customers with 10,000+ Macs running Jamf Connect cannot migrate by hand; the migration tool automates the detection, profile generation, profile installation, and Jamf Connect removal steps. The migration tool's FileVault-recovery integration (per ADR-053) handles the edge case where the migration triggers a FileVault lockout — the helpdesk can re-derive the FileVault key from the framework directory's recovery key escrow, and the user is back online in minutes rather than requiring a full re-image.

The decision to use `sso_util configure` for PSSO configuration (rather than implementing a fresh PSSO configuration API) is forced by Apple's API design. `sso_util` is the supported user-facing surface for PSSO and Kerberos SSO Extension configuration; bypassing it requires reverse-engineering the `Authentication_SSO.appex` extension's XPC protocol, which is undocumented and subject to change. The framework's installer calls `sso_util configure` on first enrollment; manual `sso_util` invocation is supported for troubleshooting.

The decision to support Password-derived mode on Intel Macs without T2 is forced by the installed-base reality. ~15-20% of enterprise Macs are Intel without T2 (as of 2024); these Macs cannot use Hardware_Bound mode. Password-derived mode is less secure (the password-derived key is recoverable if the macOS password is compromised) but is still better than Jamf Connect's ROPG pattern (Password-derived mode does not require password sync; the password-derived key is regenerated from the macOS password on each PSSO authentication, and the macOS password is already used for FileVault unlock). The framework documents Password-derived mode as a fallback for legacy hardware; customers with T2/Apple Silicon Macs use Hardware_Bound mode.

## Consequences

**Positive**. The framework eliminates the FileVault lockout class for macOS 13+ deployments using PSSO Hardware_Bound mode. The framework's macOS authentication story aligns with Apple's first-party direction. The framework's migration tool automates the Jamf Connect → PSSO transition, eliminating manual migration effort. The framework's FileVault recovery integration (per ADR-053) provides a safety net for migration edge cases.

**Negative**. PSSO requires macOS 13+ (Ventura, released October 2022). Customers on macOS 12 and earlier must upgrade; the framework's documentation must be clear about this. Password-derived mode on Intel Macs without T2 is less secure than Hardware_Bound mode; customers with mixed Mac fleets must accept a tiered security posture. The migration tool is a one-way operation: once Jamf Connect is removed, rolling back requires re-installing Jamf Connect and re-enrolling the Mac.

**Neutral**. PSSO's IdP integration uses standard OIDC Authorization Code + PKCE (per RFC 8252 and RFC 6749); no proprietary protocol is involved. The framework's IdP (per the Federation Gateway capability) supports OIDC natively.

**Implementation cost**. Medium. Estimated 8-12 engineer-weeks for the macOS client PSSO integration, the MDM profile templates, the `sso_util configure` automation, the migration tool, the FileVault recovery integration, the test matrix (PSSO end-to-end, Jamf Connect migration, NoMAD migration), and the documentation. The framework's IdP (Federation Gateway) and key escrow (per ADR-053) are prerequisites that must be in place before this ADR can be deployed.

**Operational impact**. Operations teams gain a single macOS authentication path (PSSO) instead of the Jamf Connect + Kerberos SSO Extension mix. Operations teams lose the Jamf Connect management surface (`jamf_connect_login` configuration); the framework provides `framework-macos-auth` CLI equivalents that wrap `sso_util`. The framework's runbook must include a "Jamf Connect migration" section and a "PSSO troubleshooting" section. The framework's Prometheus exporter MUST expose `psso_authentication_total{method="hardware_bound|password",result="..."}` and `psso_kerberos_renewal_total{result="..."}` metrics.

## Alternatives Considered

**Alternative 1: Recommend Jamf Connect as the macOS SSO path (with ROPG sync fixes).** The framework documents Jamf Connect as the recommended macOS SSO path, with operational guidance to minimize ROPG sync divergence (e.g. configure the sync agent to run every 5 minutes instead of 15, configure IdP password-change notifications to trigger immediate sync, deploy FileVault institutional recovery key as a fallback). **Rejection rationale**: This is a workaround, not a fix. The ROPG divergence window is structurally unavoidable as long as the IdP password can be changed outside the sync agent. The Jamf support data (5-8% FileVault lockout rate) is measured on customers who already follow best-practice sync configuration; the divergence rate is not significantly improvable. PSSO Hardware_Bound mode eliminates the problem entirely.

**Alternative 2: Implement a fresh passwordless macOS client (not based on PSSO).** The framework ships its own macOS client that uses a SEP-bound key (via `SecKeyCreateRandomKey` with `kSecAttrTokenIDSecureEnclaveTokenID`) to sign IdP token requests, bypassing PSSO. **Rejection rationale**: This duplicates PSSO functionality with less Apple integration. PSSO is registered as a `CredentialProvider` with the Authorization framework, which means `AuthorizationCopyRightEx` callers (system login, Screen Time, app-specific auth) automatically use PSSO. A framework-specific passwordless client would not be registered with the Authorization framework and would require every calling app to integrate with the framework's API explicitly. This breaks the framework's "use platform-native APIs" posture and creates a parallel auth surface that does not interoperate with macOS system services.

**Alternative 3: Document macOS 12 and earlier as out of scope (require macOS 13+ for any framework macOS client).** The framework does not support Password-derived PSSO fallback on Intel Macs without T2; customers with these Macs must upgrade to T2/Apple Silicon Macs. **Rejection rationale**: This excludes ~15-20% of enterprise Macs (as of 2024) from the framework's macOS support. Many enterprises have 3-5 year Mac refresh cycles; excluding Intel Macs forces premature hardware refresh, which is operationally and financially unacceptable. Password-derived mode is a reasonable compromise for legacy hardware; the security posture is documented, and customers can choose to retire Intel Macs at their own pace.

## Open Questions

None. The decision is fully specified and has no Tier-1 ORQ dependency. The deferred Tier-1 question is the Client SDK architecture choice (Rust core vs per-platform wrappers, per ORQ-169/170/175/176), but the PSSO Extension integration is independent of the SDK architecture: the macOS client (whatever its implementation language) integrates with PSSO via `sso_util` and `AuthorizationCopyRightEx`, both of which are platform-native APIs.

## Cross-capability impact

- **Client SDK** ([PC-086](../catalog/08-client-sdk.md)): PSSO Extension is the macOS client's primary authentication path; this ADR is the implementation detail for the macOS half of PC-086.
- **KDC** ([PC-023](../catalog/02-kdc.md)): PSSO's Kerberos sub-payload speaks MS-KILE; the KDC must support PAC, FAST, PKINIT for PSSO Hardware_Bound mode.
- **Cross-Platform Parity** ([PC-105](../catalog/09-cross-platform-parity.md)): PSSO Extension uses the macOS system Heimdal fork; the framework's macOS Kerberos posture inherits the fork's limitations (per ADR-056).
- **Cross-Platform Parity** ([PC-097](../catalog/09-cross-platform-parity.md)): FileVault recovery key escrow (per ADR-053) is the safety net for the Jamf Connect → PSSO migration edge case.
- **Federation Gateway** ([PC-071](../catalog/06-federation-gateway.md)): PSSO's OIDC `AuthenticationClient` integrates with the Federation Gateway's OIDC IdP.
