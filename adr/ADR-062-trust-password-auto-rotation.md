# ADR-062: Auto-Rotate Trust Passwords + Auto-Reset on Desync

## Status

Accepted — 2026-08-13

## Context

Trust passwords rotate every 30 days by default in AD. The rotation is performed by the trusting domain's PDC emulator via `netlogon.dll!I_NetServerPasswordSet2`. The `trustAuthBlob` attribute on the `trustedDomain` object holds both the current and the previous password (for overlap, so a replication-lagged DC can still authenticate using the old password). The `LastUpdateTime` field on each `LSA_AUTH_INFORMATION` entry in the blob records when each password was set.

If the PDC emulator is offline during the rotation window (e.g. PDC seized during the 30-day cycle, or replication is broken for >30 days), the trust can desync: one side has the new password, the other still has the old. Symptoms: `nltest /verify` returns "Trust verification failed"; cross-trust Kerberos referrals fail with `KDC_ERR_S_PRINCIPAL_UNKNOWN (6)` or `KRB_AP_ERR_MODIFIED (41)`. Detection is manual (`nltest /verify` run by an admin) or implicit (user complains about cross-domain auth failures). Fix is `netdom trust <trusting> /d:<trusted> /reset /pd /po /ud:admin /pd:*` which sets both sides to a new shared password.

The framework gap: trust password rotation is operationally fragile. The framework should automate (a) health-check (continuous `nltest /verify` equivalent, alert on desync), (b) auto-reset on detection (no admin intervention), (c) per-trust rotation policy (some trusts need 7-day rotation, others 90-day). The overlap-window design (current + previous password) should be preserved; ideally extended to current + previous + next (3 passwords) to handle longer replication lag.

The constraint set: support dual-password overlap (current + previous); support automated health check (continuously verify trust); support automated reset on desync detection; support per-trust rotation policy (custom intervals).

## Decision

The framework's operator runs a `TrustHealthController` reconcile loop on every DC that hosts a trust. The loop performs three functions: (1) continuous trust verification (every 5 minutes, equivalent to `nltest /verify`); (2) automated rotation per the per-trust rotation policy (default 30 days, configurable per trust from 1 day to 365 days); (3) automated reset on desync detection (no admin intervention). The `trustAuthBlob` structure is extended to hold three passwords: current, previous, and next (pre-rotated). The next-password slot enables zero-downtime rotation: the new password is pre-staged on both sides, then atomically promoted to current; the previous current becomes previous; the previous previous is dropped. This three-password overlap tolerates up to one rotation-cycle of replication lag.

Per-trust rotation policy is configured via the `Trust` CRD (`spec.rotationIntervalDays`, `spec.rotationPolicy: [automatic | manual | disabled]`, `spec.alertOnDesync: [true | false]`, `spec.autoReset: [true | false]`). The default is `rotationIntervalDays: 30`, `rotationPolicy: automatic`, `alertOnDesync: true`, `autoReset: true`.

Desync detection triggers an immediate reset: both sides are re-seeded with a new shared password (generated by the framework's CSPRNG, 256 bits). The reset is logged as an audit event (per ADR-060) with MITRE ATT&CK T1486 (Resource Hijacking) indicator if the desync coincides with other suspicious signals.

**Concrete specification**:

- The `TrustHealthController` MUST run on every DC that hosts a trust and execute the verify-rotate-reset loop every 5 minutes (configurable).
- Trust verification MUST use the framework's equivalent of `nltest /verify`: query the trusted domain's PDC emulator for the current `trustAuthBlob`, compare with the local `trustAuthBlob`, and report desync if the current passwords do not match.
- Trust rotation MUST occur when `LastUpdateTime + rotationIntervalDays < now`, where `LastUpdateTime` is the timestamp on the current password entry.
- Trust rotation MUST use the three-password-overlap protocol:
  1. Generate a new password (256-bit CSPRNG).
  2. Write the new password to the `next` slot on both sides via DRSUAPI replication (or the framework's replication protocol).
  3. Wait for replication confirmation from the partner side (timeout: 5 minutes).
  4. Atomically promote: `current → previous`, `next → current`, `previous → dropped`.
  5. Replicate the promotion to the partner side.
- The three-password overlap MUST tolerate up to one rotation cycle of replication lag without desync.
- Desync detection MUST trigger an immediate reset: generate a new 256-bit password, write to both sides (using both `current` and `previous` slots to handle in-flight requests), confirm via re-verification.
- The reset MUST be logged as an OTel audit event (per ADR-060) with attributes `adrian.trust.partner`, `adrian.trust.direction`, `adrian.trust.reset_reason: [desync | manual | scheduled]`, `adrian.trust.reset_initiated_by`.
- The `Trust` CRD MUST support `spec.rotationIntervalDays` (1–365), `spec.rotationPolicy` (`automatic` | `manual` | `disabled`), `spec.alertOnDesync` (bool), `spec.autoReset` (bool).
- The default `spec.rotationIntervalDays` MUST be 30.
- The default `spec.rotationPolicy` MUST be `automatic`.
- The default `spec.autoReset` MUST be `true`.
- The `TrustHealthController` MUST emit a Prometheus metric `adrian_trust_health{partner,direction}` (gauge, 1=healthy, 0=desync) per [ADR-057](./ADR-057-prometheus-otel-observability.md).
- The `TrustHealthController` MUST emit a Prometheus metric `adrian_trust_password_age_seconds{partner,direction}` (gauge).
- The `TrustHealthController` MUST emit a Prometheus metric `adrian_trust_resets_total{partner,direction,reason}` (counter).
- The framework MUST ship a default alert rule: `adrian_trust_health == 0 for >5m` triggers a critical alert.
- For AD-interop trusts (the framework's DC participates in an AD forest), the framework MUST participate in AD's `I_NetServerPasswordSet2` rotation; the framework's DC must accept the rotated password from the AD PDC.
- For AD-interop trusts, the three-password overlap MAY be reduced to two-password overlap (matching AD's behaviour) if the AD side does not support the third slot.

## Rationale

Trust password rotation is a low-frequency, high-impact operation. When it desyncs, every cross-domain auth fails. The 30-day default rotation interval means most organisations encounter desync only rarely, so manual remediation seems acceptable — but when it does fail (typically during a separate incident that involves PDC seizure or replication breakage), the manual fix adds hours to the outage. Automation eliminates this entire class of incident.

The three-password overlap protocol is a strict improvement over AD's two-password overlap. With two passwords (current + previous), a replication lag of more than one rotation cycle desyncs the trust. With three passwords (current + previous + next), a replication lag of up to one rotation cycle is tolerated: the lagged DC still has the previous password, the partner has rotated to the next (which is now current), and on replication the lagged DC catches up by promoting its `next` slot. Three passwords is the minimum that achieves this tolerance; four adds no additional benefit.

Per-trust rotation policy is necessary because different trusts have different risk profiles. A forest trust to a development forest may rotate every 90 days; a cross-forest trust to an acquisition's forest may rotate every 7 days during the integration period. The CRD's `rotationIntervalDays` field makes this configurable.

Automated reset on desync is the key safety net. The framework detects desync via the verify loop and immediately resets — no admin intervention. This is the same pattern as BGP route-reflector auto-recovery: the protocol self-heals. The risk of false-positive reset (reset when the trust was not actually desynced) is bounded by the verify loop's false-positive rate, which is near-zero (the verify is a direct password comparison, not a heuristic).

The MITRE ATT&CK T1486 indicator on desync + suspicious signals is a defensive measure: if an attacker is trying to manipulate the trust (e.g. by tampering with the `trustAuthBlob`), the desync detection will catch it and the alert will include the MITRE tag for SIEM correlation.

## Consequences

**Positive**: Trust desync incidents are eliminated. Cross-domain auth reliability improves. Per-trust rotation policy enables tighter security for high-risk trusts and looser policy for low-risk trusts. Three-password overlap tolerates replication lag without desync.

**Negative**: The `trustAuthBlob` structure is framework-specific (three-password overlap) and may not interop with AD's two-password structure for non-AD-interop trusts. For AD-interop trusts, the framework falls back to two-password overlap. The auto-reset feature can mask underlying replication problems (if replication is consistently broken, the trust will be reset weekly, hiding the root cause). The `TrustHealthController` adds a small CPU and replication load (every 5 minutes, every DC).

**Neutral**: The framework's trust rotation is backwards-compatible with AD's `I_NetServerPasswordSet2` for AD-interop; the framework's DC accepts rotated passwords from an AD PDC. The framework's own rotation protocol (three-password overlap) is used only between two framework DCs.

**Implementation cost**: ~2 person-months for the `TrustHealthController` and the three-password overlap protocol; ~1 person-month for the CRD and the operator integration; ~1 person-month for the alert rules and audit event emission. Total: ~4 person-months for v1.

**Operational impact**: Trust desync incidents drop from "weekly fire drill" to "never". SREs see trust health as a Prometheus gauge; SOC analysts see trust resets as audit events. Per-trust rotation policy is set in the CRD and modified via GitOps.

## Alternatives Considered

**Alternative A: Manual rotation only, with improved monitoring.** Keep rotation manual but add the verify loop and alerting. Rejected because (a) manual rotation is the root cause of desync incidents — operators forget, get distracted, or run the wrong command; (b) auto-reset on desync is the actual safety net, and it requires the framework to manage the trust password anyway.

**Alternative B: Shorter rotation interval (7 days) with two-password overlap.** Reduce the rotation interval to 7 days to reduce the desync window. Rejected because (a) shorter intervals increase the chance of hitting a desync during replication lag (more rotations = more opportunities for failure), (b) the three-password overlap achieves the same tolerance without increasing rotation frequency.

**Alternative C: Public-key-based trust (no shared password).** Replace the shared password with a public-key pair; each side signs challenges with its private key. Rejected for v1 because (a) it breaks AD-interop (AD trusts use shared passwords), (b) it requires a PKI for trust-key issuance, adding a dependency on the deferred federation layer (ORQ-132/133/134), (c) the operational benefit over three-password overlap is marginal. Public-key-based trust may be added in v2 for framework-to-framework trusts.

**Alternative D: External secret manager (Vault, AWS Secrets Manager).** Store the trust password in an external secret manager; the framework pulls on demand. Rejected because (a) the trust password must be on both sides of the trust; storing it in one external manager does not solve the dual-write problem, (b) it adds a hard dependency on the secret manager's availability, (c) it does not improve on the three-password overlap protocol's replication-lag tolerance.

## Open Questions

None — this is an ADR-ELIGIBLE decision. The replication protocol choice (PC-001 / Tier-1 ORQ-001/002) does not gate this decision: the three-password overlap protocol works with any replication model that supports atomic multi-object writes.

## Cross-capability impact

- **Core Directory (PC-001 through PC-022)**: DRSUAPI replication (PC-001) must support the three-password overlap write (atomic across two objects: the trust on each side).
- **KDC (PC-028)**: Cross-realm TGT referral (PC-028) uses the trust key; ADR-069 (cross-realm capaths) depends on stable trust passwords.
- **Operations (PC-106)**: ADR-057 (Prometheus + OTel) — trust health and password age become Prometheus metrics.
- **Operations (PC-111)**: ADR-060 (audit logs) — trust reset events emit OTel log records with MITRE ATT&CK mapping.
- **Operations (PC-115)**: ADR-063 (unified CLI) — exposes `trust verify`, `trust rotate`, `trust reset` commands.
- **Migration (PC-126)**: Client switchover (PC-126, deferred) depends on stable trust between AD and the framework; this ADR ensures the trust does not desync during the migration window.
- **Migration (PC-129)**: ADR-069 (cross-realm capaths) — the trust setup created by ADR-069's CLI is managed by this ADR's controller.
- **Security (PC-120)**: sIDHistory abuse (PC-120, deferred) is mitigated in part by trust-password integrity — a desync'd trust is harder for an attacker to exploit because cross-trust auth fails.
