# Security Architecture

## Threat model overview

Adrian's threat model enumerates eight attack classes that constitute the dominant AD compromise surface as documented in [`catalog/11-security-threat-model.md`](../catalog/11-security-threat-model.md). Each is classified under STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege), mapped to MITRE ATT&CK techniques, and addressed by a default-on mitigation backed by a specific ADR. The eight classes are: **Kerberoasting** (PC-116, Information disclosure + Elevation of privilege, MITRE T1558.003), **DCSync** (PC-117, Information disclosure + Elevation of privilege, MITRE T1003.003), **golden ticket** (PC-118, Spoofing + Elevation of privilege, MITRE T1558.001), **silver ticket** (PC-119, Spoofing + Elevation of privilege, MITRE T1558.004), **NTLM relay / pass-the-hash** (PC-037/PC-038, MITRE T1550.001/T1550.004), **sIDHistory injection** (PC-120, Elevation of privilege + Spoofing, MITRE T1178), **supply chain compromise** (PC-123, Tampering + Elevation of privilege, MITRE T1195.002), and **privileged-access ACL drift** (PC-122, Tampering + Elevation of privilege). Two further operational gaps — selective authentication pain (PC-121) and AdminSDHolder opacity (PC-122) — round out the security catalog.

The framework's security posture is *default-on and explicit*: every mitigation ships enabled, every exception is audit-logged, and the threat model document is updated quarterly against new MITRE ATT&CK techniques. This inverts the AD posture, where mitigations are scattered across GPO settings (`Network security: Configure encryption types allowed for Kerberos`), ACLs on the domain NC head (`DS-Replication-Get-Changes-All`), registry keys (`VerifyPacAuthenticators`), and one-off procedures (`Reset-KrbtgtAccountPassword.ps1`). AD's mitigations are *available*; Adrian's are *enforced*. Where AD-interop mode (mixed forests) requires preserving an AD-style surface for compatibility — e.g. DRSUAPI `EXOP_REPL_SECRETS` for legacy Windows DCs — the framework inherits the surface but adds per-call audit (ADR-060), HSM-bound break-glass (ADR-122), and SIEM detection rules keyed on `adrian.replication.ulExtendedOp` and `adrian.replication.caller_sid`.

The threat model is grounded in Mandiant M-Trends data: Kerberoasting is the #1 initial-access vector against AD (≈80% of AD compromises involve PtH or Kerberoasting in the lateral-movement phase); DCSync is the typical post-Domain-Admin escalation; golden ticket is the persistence mechanism of choice. The framework's mitigations target the *mechanism*, not the *symptom* — eliminating RC4 (ADR-011), HSM-binding the krbtgt key (ADR-015/ADR-065), refusing NTLM server-side (ADR-085), and requiring `PAC_BUFFER_TICKET_CHECKSUM` validation (ADR-123) remove the attack surface at the protocol level rather than relying on operator-configured detection. Detection (ADR-060 structured audit, MITRE ATT&CK mapping) is the second layer for residual risk; supply-chain hardening (ADR-067 Sigstore + Rekor + SLSA L3) is the third layer for the build-and-distribute path.

## Kerberoasting mitigation

Kerberoasting (PC-116, blocker) is the dominant AD attack vector. Any authenticated domain user can pull a TGS for every SPN-bearing account, then offline-brute-force the ticket's `enc-part` against a dictionary at 10⁸ guesses/sec on a modern GPU when the ticket is RC4-HMAC-encrypted (etype 0x17). AES-encrypted tickets (etype 0x12, AES-256-CTS-HMAC-SHA1-96) require PBKDF2-HMAC-SHA1 with 4096 iterations per RFC 3962/8009, slowing the attack by ~10⁵× — making AES-encrypted tickets with 25+ char random passwords effectively uncrackable. The framework mitigates by *eliminating RC4* and *enforcing AES-only at the KDC*, per [ADR-064](../adr/ADR-064-kerberoasting-aes-migration.md) (blocker) and [ADR-011](../adr/ADR-011-rc4-deprecation-aes-default.md) (blocker, KDC etype policy). The fresh Rust KDC (Decision 5, `crates/adrian-kdc/src/etype.rs`) defaults to AES-only for all TGS issuance: `aes256-cts-hmac-sha1-96` (etype 0x12) preferred, `aes128-cts-hmac-sha1-96` (etype 0x11) as fallback, RC4-HMAC (etype 0x17) disabled unless explicitly enabled in AD-interop mode. Service accounts must declare `msDS-SupportedEncryptionTypes = 0x30` (AES128 | AES256); accounts with the attribute unset are refused TGS issuance and flagged for migration via `adrian-cli migrate-aes`.

The second layer is **gMSA with HSM-bound KDS root key**, per [ADR-020](../adr/ADR-020-gmsa-kds-rotation.md). New service accounts default to gMSA (`msDS-GroupMSAMembership` populated, password managed by the KDS root key). The KDS root key is generated inside an HSM via PKCS#11 (`cryptoki` crate) and never leaves it; the 240-character random password is regenerated every 30 days by the KDC's `src/mskile/gmsa.rs` module through an HSM round-trip. The KDS root key itself rotates every 90 days. gMSA passwords cannot be Kerberoasted because they are never transmitted to the KDC's plaintext memory — the password derivation uses the HSM-bound KDS root key as the HMAC key over the account SID. The fresh Rust KDC enforces this by refusing to compute the gMSA password outside the HSM: `gmsa_password(sid, interval) -> Result<[u8; 240]>` is a single HSM call. The third layer is **detection**: the audit pipeline (ADR-060) emits `adrian.kerberos.tgs.request` with `adrian.kerberos.etype` for every TGS-REQ; default rules alert on etype 0x17 (RC4), on >5 unique SPNs requested by one user in 5 minutes (Kerberoast storm), and on TGS-REQ for an SPN whose owning account password is older than 365 days. These rules ship in the framework's default SIEM ruleset (`adrian-audit-events.json`), mapped to MITRE ATT&CK T1558.003.

## Golden ticket mitigation

Golden ticket (PC-118, blocker) is the persistence mechanism: an attacker who has the krbtgt hash (typically obtained via DCSync, PC-117) can forge TGTs locally using `ticketer.py -nthash <krbtgt_hash>` with arbitrary user identity, group memberships, and validity windows up to 10 years. The KDC, decrypting the forged TGT with the krbtgt key, validates everything and issues service tickets as if the attacker were the claimed principal. AD's only mitigation is krbtgt password rotation (`Set-ADAccountPassword krbtgt`, repeated twice with a 10-hour gap equal to the TGT lifetime to flush in-flight TGTs). Adrian eliminates the *extraction* attack by HSM-binding the krbtgt key, per [ADR-015](../adr/ADR-015-krbtgt-hsm-rotation.md) (blocker, KDC) and [ADR-065](../adr/ADR-065-krbtgt-hsm-rotation.md) (blocker, Security framing). The krbtgt key is generated inside an HSM via PKCS#11 v3.0 (`cryptoki` crate), never exported in plaintext, and every TGT signing operation (`PAC_PRIVSVR_CHECKSUM`, `EncTicketPart` encryption, `PAC_FULL_CHECKSUM`) is a single HSM round-trip (`≤5 ms` per signing operation, typical PKCS#11 latency). DCSync — even if it succeeds against the framework's AD-interop mode — returns a key blob that cannot be decrypted without HSM presence. HSM binding closes the extraction attack; rotation closes the *retention* window if the HSM is ever compromised.

Rotation is **automatic, 30-day interval, 2-key overlap**, per ADR-015. The KDC maintains `current_krbtgt_key` and `previous_krbtgt_key` simultaneously; TGTs issued with the previous key remain valid for one TGT lifetime (10 hours default) after rotation, then expire. Rotation is a single CLI command (`adrian-cli rotate-krbtgt`) or operator-action via the `DomainController` CRD; no manual sequencing. The KDC emits `adrian.kerberos.kvno_mismatch` audit events (per ADR-023/ADR-060) whenever a TGT is presented that was encrypted with an older key version than current-key-minus-one — a strong indicator of either golden ticket activity or a lagged client. SIEM rules alert on any `kvno < current_kvno - 1`. Microsoft's IR guidance (KB 3011620: rotate krbtgt *twice* with a gap equal to max TGT lifetime) is automated by the framework's `rotate-krbtgt --twice` flag, which schedules the second rotation 10 hours after the first. HSM breach — the residual risk — is addressed by the audit trail: every HSM call is logged (HSM vendor event log + framework audit event `adrian.hsm.krbtgt_sign`), so a hypothetical HSM compromise produces forensic evidence in the framework's audit pipeline.

## Silver ticket mitigation

Silver ticket (PC-119, high) is the service-account analog of golden ticket: an attacker who has a service account's long-term key (obtained via Kerberoasting PC-116, DCSync PC-117, or LSASS dump on the service host) forges a TGS service ticket locally using `ticketer.py -nthash <service_hash> -spn cifs/file01.example.com`. The forged ticket is presented directly to the service via AP-REQ; the service decrypts it with its own key — succeeds — and extracts the forged PAC. No KDC interaction occurs, making detection very hard. AD introduced `PAC_BUFFER_TICKET_CHECKSUM` (PAC buffer type 0x0E) in Windows Server 2012: the KDC signs the entire `Ticket.enc-part` with the krbtgt key and embeds the signature in the PAC. A service that opts in to validation (registry key `VerifyPacAuthenticators = 1`) re-verifies the signature by calling the KDC's PAC validation RPC (`NetrLogonSamLogonEx`). The problem: most services do not opt in, because the perf cost is one RPC roundtrip per AP-REQ.

Adrian flips the default: **the KDC always emits `PAC_BUFFER_TICKET_CHECKSUM` and services validate by default**, per [ADR-123](../adr/ADR-123-silver-ticket-mitigation.md). The fresh Rust KDC's PAC builder (`crates/adrian-kdc/src/pac.rs`, ADR-082) emits the ticket checksum on every TGS-REP for which the service's `msDS-SupportedEncryptionTypes` includes AES — that is, every TGS in native mode and in AD-interop mode where AES is negotiated. The signature is computed via the HSM-bound krbtgt key (same round-trip as the TGT signing, marginal cost ≤1 ms). On the service side, the framework's unified PAC validator (`libframework_pac_validator.{so,dylib,dll}` per ADR-049) verifies the ticket checksum by default; an opt-out exists (`pac_ticket_checksum_mode = "audit"` or `"disabled"`) for perf-critical services, but opt-out is audit-logged and surfaced in `adrian-cli audit-silver-ticket-coverage`. The validation path uses the two-layer model from [ADR-083](../adr/ADR-083-pac-validation-rpc.md): local Ed25519 signature verification (≤50 µs, zero DC roundtrip) using the HSM-derived krbtgt public key published via the directory's `krbtgtPublicKey` attribute, plus a legacy `NetrLogonSamLogonEx` (MS-NRPC opnum 45) RPC path for AD-interop with Windows services that opt in via `VerifyPacAuthenticators=1/2`. A 5-second verdict cache (per-caller rate-limit default 100/sec) protects the KDC from validation-storm DoS.

## DCSync mitigation

DCSync (PC-117, blocker) is full-domain-compromise-by-any-Domain-Admin: any principal holding `DS-Replication-Get-Changes` (GUID `1131f6aa-9c07-11d1-f79f-00c04fc2dcd2`) and `DS-Replication-Get-Changes-All` (GUID `1131f6ad-9c07-11d1-f79f-00c04fc2dcd2`) on the domain NC head can call `DRSGetNCChanges` (DRSUAPI opnum 3) with `ulExtendedOp = EXOP_REPL_SECRETS` and pull `unicodePwd`, `supplementalCredentials`, `lmPwdHistory`, `ntPwdHistory` for every user. impacket's `secretsdump.py -just-dc` extracts the entire directory in 5–30 minutes for a 100K-user domain. Adrian mitigates at the protocol layer: **native mode eliminates `EXOP_REPL_SECRETS` entirely**, per [ADR-122](../adr/ADR-122-dcsync-mitigation.md). In native mode the framework uses `openraft` (Decision 1) for replication; the `RaftReplicator` (ADR-071) replicates committed log entries peer-to-peer without any RPC for "secrets extraction" — there is no opnum to abuse. The framework's DRSUAPI server (`adrian-drsuapi` crate, ADR-070) is present only in AD-interop mode for mixed-forest compatibility with Windows DCs. Native-mode DCs refuse DRSUAPI `DRSGetNCChanges` with `EXOP_REPL_SECRETS` from non-AD-interop callers.

AD-interop mode inherits the DRSUAPI surface (the framework must serve `DRSGetNCChanges` to legacy Windows DCs to keep replication working). Adrian's mitigation in AD-interop mode is **per-call audit + HSM-bound break-glass**, per ADR-122. Every `DRSGetNCChanges` call is logged as an OTel event per [ADR-060](../adr/ADR-060-structured-audit-logs-otel.md) with attributes `adrian.replication.ulExtendedOp`, `adrian.replication.caller_sid`, `adrian.replication.nc_dn`, `adrian.replication.cmax_objects`. SIEM rules alert on (a) any caller whose SID is not a registered `nTDSDSA` object (i.e. not a real DC), (b) any `EXOP_REPL_SECRETS` operation scoped to the entire NC (full-domain dump), (c) any caller whose `DS-Replication-Get-Changes-All` right was granted within the last 24 hours (possible attacker escalation). The break-glass path for incident response (operator needs to extract secrets from a dead DC's backup) uses an HSM-bound key: the operator presents an HSM token, the framework's `adrian-cli breakglass-secrets-extract --hsm-token <token> --dc <dead-dc>` decrypts the directory's PEK (Password Encryption Key) inside the HSM and extracts the requested secrets. The break-glass operation is two-person-ruled (HSM quorum), audit-logged at HSM vendor level, and time-boxed to a 15-minute window.

## NTLM relay mitigation

NTLM relay (PC-037, blocker) and pass-the-hash (PC-038, blocker) are the lateral-movement vectors: PetitPotam (`MS-EFSRPC` coercion), ShadowCoerce (`MS-RPRN` coercion), and PrinterBug (`MS-RPRN` callback) all coerce a target host into authenticating to an attacker-controlled NTLM acceptor, which relays the authentication to a downstream service (typically LDAPS on a DC) to issue a cert or modify an object. Pass-the-hash (PtH) reuses a stolen NT hash to authenticate as the user without the password. Both attacks require an NTLM acceptor as the relay target. Adrian eliminates the entire attack class against framework infrastructure by **refusing to host an NTLM acceptor on any framework service**, per [ADR-085](../adr/ADR-085-ntlm-client-only-rust-crate.md) and Decision 6. The KDC, LDAP server, REST/gRPC API, SMB server, cert service, federation gateway, and all HTTP services reject NTLM tokens with `strongAuthRequired (8)` (LDAP), `401 Unauthorized` with `WWW-Authenticate: Negotiate, Kerberos` (HTTP), or the protocol-equivalent on other surfaces. PetitPotam-style coercion against a framework DC fails at the relay step because the framework DC does not accept NTLM. There is no target.

The framework does maintain an NTLM *client* (`crates/adrian-ntlm-client`, ADR-085, ~3K lines) for connecting framework-managed clients to legacy services that still require NTLM — the compat surface. The client is NTLMv2-only (NTLMv1 disabled unconditionally), uses RFC 5929 channel binding (`MsvAvChannelBindings` AV_PAIR ID 0x000B, SHA-256 of `tls-server-end-point`) when layered under TLS, sets the EPA `EPHEMERAL` flag (`AvFlags & 0x04`) for non-delegatable sessions, and stores the NT hash in the platform's secure credential store (Linux `keyctl`/`systemd-creds`, macOS Keychain, Windows DPAPI / Credential Guard). NT hashes are never cached in plaintext; the client fetches the hash on every authentication. PtH against the framework's AD-interop users (the only users with NT hashes — framework-native users have AES keys only, per ADR-011) is further mitigated by HSM-bound PEK encryption (ADR-086): `unicodePwd` is encrypted with a Password Encryption Key that is HSM-bound (same HSM as krbtgt) and never replicated between DCs. ADR-086 also mandates `Zeroizing<Vec<u8>>` (via the `zeroize` crate) for all NT hash memory in framework processes. The combined posture is strictly stronger than AD's Credential Guard (bypassable via CVE-2020-1017, CVE-2022-37966) because the framework's NTLM server is *absent*, not merely protected.

## sIDHistory injection mitigation

sIDHistory injection (PC-120, high) is the forest-escalation attack: an attacker with Domain Admin in a child domain injects an arbitrary SID (e.g. `S-1-5-21-<forest-root-domain-sid>-519` = Enterprise Admins of the forest root) into a user's `sIDHistory` via `DRSAddSidHistory` (DRSUAPI opnum 20, requires `SeEnableDelegationPrivilege` held by child-domain DAs). The next TGT issued by the child KDC includes the injected SID in the PAC's `ExtraSids`; traversing the within-forest trust, the forest-root KDC preserves the `ExtraSids` (within-forest trusts do not filter sIDHistory by default), and the attacker's token on a forest-root DC includes Enterprise Admins. AD's mitigation is SID Filter Quarantine on external/forest trusts (default since Server 2003/2008), but within-forest trusts do *not* filter — to support migration — leaving the attack open in every multi-domain forest.

Adrian defaults to **sIDHistory filtering on ALL trusts**, per [ADR-124](../adr/ADR-124-sidhistory-injection-mitigation.md). Within-forest trusts receive the same `TRUST_ATTRIBUTE_QUARANTINED = 0x4` filtering that AD reserves for external trusts: the KDC strips any `ExtraSids` entry whose SID prefix does not match the trusted domain's SID prefix. The framework's KDC enforces this in `crates/adrian-kdc/src/trusts.rs` at TGS-REF construction time. PIM trust semantics (Server 2016+, `TRUST_ATTRIBUTE_PIM_TRUST = 0x200`) are supported for deployments that need user-level isolation within-forest. sIDHistory writes are audit-logged per ADR-060 (`adrian.trust.sidhistory_write` with attributes `adrian.trust.target_object`, `adrian.trust.injected_sid`, `adrian.trust.actor_sid`) and SIEM rules alert on any sIDHistory write outside a designated migration window.

The migration-window exception, [ADR-126](../adr/ADR-126-sidhistory-migration.md), provides a **time-limited passthrough window** for the AD-to-framework migration case: during a documented migration window (default 30 days, max 180), the operator can enable `sidhistory_passthrough = true` on a specific trust, audit-logged per-write. Outside the window the flag auto-reverts to `false` and the KDC resumes filtering. The framework provides a claims-based migration alternative (`adrian-cli migrate-claims`) that translates sIDHistory references into the framework's native claims model, eliminating the sIDHistory dependency for new deployments. The combined posture — default filtering + time-boxed exception + claims alternative — closes the sIDHistory injection attack at the protocol layer while preserving migration operability.

## Supply chain security

Supply chain compromise (PC-123, medium) is the SolarWinds-class attack: an attacker compromises the framework's build pipeline (CI/CD), injects malicious code into a release, signs the malicious release with the framework's legitimate signing cert (because the CI/CD pipeline has signing access), and the signed malicious release ships to every customer DC. WSUS compromise in AD is the analogous attack. Adrian mitigates by **Sigstore keyless signing + Rekor transparency log + SLSA L3 build provenance**, per [ADR-067](../adr/ADR-067-sigstore-supply-chain.md). Every release artifact — container images (the framework's DC, KDC, SMB server, operator sidecars), static binaries (`adrian-cli` per platform), Rust crate packages published to crates.io, and policy bundles — is signed via Sigstore `cosign sign --keyless` using OIDC-federated short-lived certificates (no long-lived signing key to compromise). Every signing event is recorded in the public Rekor transparency log; customers verify with `cosign verify --certificate-identity <framework-ci-oidc> --certificate-oidc-issuer <github-actions> --rekor-url https://rekor.sigstore.dev`. The framework publishes its OIDC identity and Rekor URL in `SECURITY.md` and in the operator's default policy.

The operator-side policy is **deny-by-default**, per ADR-067. The framework's `adrian-operator` (ADR-058) refuses to install any artifact whose signature is not in the configured allowlist AND whose signing event is not in Rekor. The allowlist is a CRD (`FrameworkReleasePolicy`) that pins `release: <semver>`, `digest: <sha256>`, `signer_identity: <oidc-subject>`, `rekor_entry: <uuid>`. Reproducible builds (SLSA L3) allow third-party verification that the published binary matches the source: the framework's CI runs `cargo build --locked` in a hermetic container; the build provenance attestation (in-toto SLSA L3) records the source commit, the build environment hash, and the dependency lockfile. Customers can independently reproduce the build from the public source repository and verify the resulting binary's hash matches the published artifact's hash. The framework's `Cargo.lock` is committed and verified via `cargo audit` on every PR; `cargo vet` is used to audit the dependency tree against the framework's vet policy. Cross-platform: Linux packages are GPG-signed via the distro's native mechanism (apt/dnf/zypper), macOS binaries are `codesign`-ed with Apple Developer ID and notarised, Windows binaries are Authenticode-signed — but the Sigstore+Rekor layer is applied *on top* on all platforms, providing a unified verification story independent of the platform-native mechanism.

## AdminSDHolder / privileged access

AD's AdminSDHolder + SDPROP mechanism (`CN=AdminSDHolder,CN=System,...` template applied to all protected groups every 60 minutes) silently reverts custom ACEs on protected objects, breaks inheritance, and is a persistence vector for attackers (modify AdminSDHolder → propagate Full Control to all privileged groups). Adrian replaces this with **declarative RBAC**, per [ADR-066](../adr/ADR-066-adminsdholder-declarative-rbac.md) (medium). Protected-group ACLs are authored as a declarative policy (`adrian-rbac.yaml`) that defines which principals can read, modify, or manage each protected group; the framework's RBAC engine evaluates the policy at write-time and rejects unauthorised modifications immediately, rather than reverting them 60 minutes later. The policy is GitOps-managed (PR review required), audit-logged per ADR-060, and versioned with the framework. SDPROP-equivalent propagation is replaced by the policy engine's reactive evaluation: there is no periodic revert cycle, no 60-minute window for an attacker to exploit a temporarily-modified ACL, and no surprise for operators who place a custom ACE. The framework defaults to the Microsoft **Tier Model** (Tier 0 = DCs and Domain Admins; Tier 1 = servers; Tier 2 = workstations) with strict credential isolation between tiers — Tier 0 credentials never touch Tier 1/2 hosts. Tier-0 admin sessions are time-boxed via the framework's PIM (Privileged Identity Management) integration: an admin requests a Tier-0 role activation, the framework grants it for a configurable window (default 4 hours), and the activation is audit-logged with MFA evidence.

## Audit and observability

Adrian's audit pipeline is **OpenTelemetry-native from day one**, per [ADR-023](../adr/ADR-023-kerberos-audit-events.md) (Kerberos audit OTel) and [ADR-060](../adr/ADR-060-structured-audit-logs-otel.md) (structured audit log OTel). Every security event — AS-REQ, TGS-REQ, pre-auth failure, TGT renewal, old-key TGT usage, AS-REP-without-preauth, RC4 TGS-REQ, NTLM client auth, DRSUAPI `EXOP_REPL_SECRETS`, sIDHistory write, AdminSDHolder revert, krbtgt rotation, trust password rotation, schema migration, certificate issuance, OCSP response — is emitted as an OTel log record with: framework event name (e.g. `adrian.kerberos.tgs.request`), Windows Event ID for AD-interop SIEM compat (e.g. `4769`), MITRE ATT&CK technique IDs (e.g. `["T1558.003"]`), structured attributes (user, source IP, SPN, etype, result code), trace ID and span ID (joining the per-request trace from ADR-057), and nanosecond-precision timestamp. The OTLP/gRPC export path feeds the `adrian-observability-sidecar` (ADR-057), which fans out to (a) a Prometheus scrape endpoint, (b) a configurable OTLP upstream collector, and (c) a local structured-log file in JSON Lines for the audit pipeline. A Windows Event Log forwarder translates OTel records back into Windows Event Log XML format for mixed-mode SIEM compat — bidirectional mapping is published as a stable table (`adrian-audit-events.json`).

The MITRE ATT&CK mapping is **explicit per event**: every audit event carries an `adrian.event.mitre_attack` attribute (array of technique IDs, empty if N/A). The framework ships default detection rules in the audit pipeline for every MITRE technique that maps to a framework event: T1558.001 (golden ticket) → `adrian.kerberos.kvno_mismatch`; T1558.003 (Kerberoasting) → `adrian.kerberos.etype = 0x17`; T1558.004 (silver ticket) → `adrian.kerberos.ticket_checksum_validation_failed`; T1003.003 (DCSync) → `adrian.replication.ulExtendedOp = EXOP_REPL_SECRETS` from non-DC caller; T1550.001 (PtH) → `adrian.auth.ntlm_client_auth` with `adrian.auth.ntlm_version = 1`; T1178 (sIDHistory injection) → `adrian.trust.sidhistory_write` outside migration window; T1195.002 (supply chain compromise) → `adrian.operator.image_signature_verification_failed`. The detection rules are versioned with the framework and ship as a JSON schema file consumable by SIEM vendors (Splunk, Elastic, Datadog, Chronicle, Microsoft Sentinel). The framework's audit taxonomy is the *contract* between the framework and the SIEM: any change to event names, attributes, or MITRE mappings is a breaking change requiring a major-version bump.

## Crypto policy

Adrian's crypto policy is **conservative, modern, and uniform across all platforms**. The default Kerberos etype is AES-256-CTS-HMAC-SHA1-96 (etype 0x12, RFC 3962/8009); the preferred etype is AES-256-CTS-HMAC-SHA384-192 (etype 0x13, ADR-014) where both endpoints support it. RC4-HMAC (etype 0x17) is disabled by default and audit-logged when explicitly enabled in AD-interop mode (ADR-011). DES etypes (0x01, 0x02, 0x03) are unconditionally disabled. MD5 is not used in any new code path (NTLMv2's HMAC-MD5 is the only legacy exception, in the NTLM client crate where required for wire compat). The crypto primitives come from `ring` (HMAC, AES, key derivation), `aes` (AES-CTS — RFC 3962 §5 with ciphertext stealing), `sha1` (HMAC-SHA1-96 for etype 0x12), `sha2` (SHA-256 for channel binding, SHA-384 for etype 0x13), `pbkdf2` (RFC 8009 §1, 4096 iterations of HMAC-SHA1), and `md4` (NT hash derivation, AD-interop RC4 audit path only). The TLS stack is `rustls` (no OpenSSL) — RFC 8446 TLS 1.3 default, TLS 1.2 supported for compat, channel binding via RFC 5929 `tls-server-end-point`. Ed25519 (`ring::signature::Ed25519KeyPair`) is used for the PAC validator's asymmetric signature path (ADR-083). All NT hash memory in framework processes is wrapped in `Zeroizing<Vec<u8>>` (via the `zeroize` crate, ADR-086). The framework's `cargo audit` and `cargo vet` policies block any PR that introduces a CVE-affected crypto primitive or an unvetted crypto dependency.

## HSM integration

Adrian integrates with HSMs via PKCS#11 v3.0 using the `cryptoki` Rust crate (MIT/Apache-2.0). HSM-bound keys are required for five high-value secrets: (1) the **krbtgt key** (ADR-015/ADR-065) — signs TGTs, signs `PAC_PRIVSVR_CHECKSUM` and `PAC_FULL_CHECKSUM`, never exported; (2) the **KDS root key** (ADR-020) — derives gMSA passwords via HMAC over the account SID, never exported; (3) the **CA private key** (ADR-037 two-tier CA) — signs issued certificates, never exported; (4) the **KRA (Key Recovery Agent) key** (ADR-032) — decrypts archived private keys, Shamir-shared M-of-N across HSM slots; (5) the **token-signing key** for the federation gateway (ADR-038) — signs OIDC/SAML tokens, never exported. The framework's `crates/adrian-hsm` module provides a unified `HsmClient` trait over `cryptoki::Session`, with `sign_mechanism`, `decrypt_mechanism`, and `derive_mechanism` operations. All HSM calls are audit-logged (`adrian.hsm.<operation>` events per ADR-060) with attributes `adrian.hsm.slot`, `adrian.hsm.key_label`, `adrian.hsm.mechanism`, `adrian.hsm.caller_pid`. Supported HSM vendors in v1: SoftHSM2 (development), YubiHSM2 (small deployments), Thales Luna (enterprise), Entrust nShield (enterprise). The framework's HSM quorum model (ADR-032) supports M-of-N officer cards for break-glass operations — krbtgt rotation, CA key rotation, KRA key use — requiring two officers to physically present their cards. HSM HA clustering (vendor-specific) is documented in the operations runbook; the framework's `HsmClient` transparently retries across cluster nodes.
