# Capability Deep Dives — 12 Capabilities × ~400 Words Each

This section drills into each of the 12 framework capabilities defined in [`catalog/00-framework-capabilities.md`](../catalog/00-framework-capabilities.md). Every capability is sized to ~400 words: a one-paragraph responsibility statement, the 3–5 most load-bearing ADRs with one-line summaries, the Rust crates that implement it, the design decisions that synthesise the ADRs into a coherent story, and a triaged implementation backlog (MVP / v1 / v2). The 130 catalog problems resolve to 130 ADRs (ADR-001 through ADR-130) across these 12 capabilities; the deep dive cites the ADRs that an architect must read first to understand each capability's shape. Where an ADR was promoted from PARTIAL by a Workshop Decision, the unblocking decision is named. Cross-capability coupling is called out inline — most capabilities have at least one ADR that another capability also cites, because the framework's twelve capabilities are not twelve silos but a tightly-coupled graph anchored on Core Directory and the KDC.

## 1. Core Directory Service (22 ADRs)

The Core Directory Service is the framework's substrate: it stores every object, attribute, link-value, security descriptor, and tombstone; serves LDAP and LDAPS; replicates between DCs; runs the schema cache; and exposes the DSA surface that every other capability consumes. It is the 1 of the 1-to-12 dependency graph — KDC, Policy Engine, Cert Service, Federation, File Gateway, Client SDK, and Migration all consume its APIs. The capability carries 22 ADRs (ADR-001–010, ADR-070–081) and resolves 4 of the framework's 23 blockers (PC-001 DRSUAPI replication, PC-002 USN/UTD vector, PC-004 member/memberOf back-link, PC-007 ESE storage replacement).

**Key ADRs.**
- **ADR-070** — Fresh Rust DRSUAPI server (`adrian-drsuapi`, ~12K lines) implementing MS-DRSR opnums 0x00/01/03/04/05/06/07/08/0C/0E/11/15 with `EXOP_REPL_SECRETS` ACL-gated for AD-interop.
- **ADR-071** — Hybrid `Replicator` trait (`adrian-repl-core`) with `DrSuapiReplicator` + `RaftReplicator` (openraft); single Raft group in v1, UTD vector synthesised from Raft log for diagnostics.
- **ADR-073** — FoundationDB 7.3.x as sole v1 storage engine (`adrian-storage-fdb`); 13 subspaces (`0x01`–`0x0D`); `DirectoryStore` trait abstraction; promotes ADR-010 (backup) from PARTIAL via native `backup_agent` + `fastrestore` PITR.
- **ADR-076** — All 5 FSMO roles eliminated in native mode (Schema Master via FDB OCC, Domain Naming Master via FDB atomic tx, PDC Emulator via Raft leader + chrony, RID Master via per-DC local counter, Infrastructure Master via identity mapping table); emulated in AD-interop.
- **ADR-078** — Hybrid schema: LDAP `attributeSchema`/`classSchema` is authoritative at wire/storage; `adrian-schema-compiler` produces typed Rust projection at boot, regenerates on `schemaUpdateNow` in ≤500 ms.

**Rust crates.** `adrian-storage-core`, `adrian-storage-fdb`, `adrian-repl-core`, `adrian-drsuapi`, `adrian-raft`, `adrian-directory-service`, `adrian-sid`, `adrian-schema-compiler`, `adrian-schema-traits`, `adrian-repl-health`. External: `foundationdb`, `openraft`, `rasn`, `rasn-kerberos`, `tokio`, `thiserror`, `tracing`.

**Key design decisions.** The 22 ADRs collapse to two binary choices plus their consequences. First, the framework is AD-interop on the wire for forests that need it (DRSUAPI replication, byte-identical `REPLVALINF_V3` and `PROPERTY_META_DATA_EXT`) and Raft-strict-serializable for native forests; the same FDB on-disk representation serves both, with UTD vector synthesis in native mode purely for `repadmin /showutdvec` diagnostics. Second, the LDAP schema is the source of truth and a typed Rust projection is code-generated at boot — AD-aware clients see `schemaModifyRequest` honoured, framework-native code gets compile-time-checked `obj.cn()` accessors at ≤50 ns. Everything else follows: tombstone lifetime 180 days (ADR-074), cross-domain move via UUID-stable identity (ADR-075), GC as FDB projection or PAS-replicated AD-interop view (ADR-072), RID pool replaced by per-DC local counter for UUID-primary identities (ADR-077), tombstones in subspace `0x07` with two-stage Recycle Bin delete, multi-tenancy via FDB subspaces (ADR-081), instanceType/systemFlags bitmasks preserved for AD-interop (ADR-080), DNS zones in FDB (ADR-079).

**Implementation priorities.** MVP: FDB storage, `DirectoryStore` trait, LDAP server, schema cache COW, DRSUAPI replication in AD-interop mode (opnums 0x00/01/03/04/05), tombstone GC, basic Prometheus metrics. v1: RaftReplicator (native mode), schema compiler with typed projection, GC projection, cross-domain move, FSMO emulation for AD-interop. v2: per-NC Raft sharding (Tier-2 ORQ-024/025), RocksDB engine for air-gapped edge, multi-tenancy hardening.

## 2. KDC (Kerberos Key Distribution Center) (13 ADRs)

The KDC issues TGTs and service tickets, builds and signs MS-KILE-conformant PACs, supports FAST armoring, PKINIT, kpasswd, cross-realm referral, gMSA KDS root key rotation, and S4U2Self/S4U2Proxy constrained delegation. It is the second-most-critical capability — every AD-aware service (IIS, SQL Server, SMB, COM+) reads authorization data from the PAC, so a byte-non-identical PAC breaks the entire downstream service ecosystem. The capability carries 13 ADRs (ADR-011–020, ADR-082–084) and resolves 3 blockers (PC-023 MS-KILE profile, PC-024 RC4 default, PC-030 krbtgt rotation).

**Key ADRs.**
- **ADR-082** — Fresh Rust KDC PAC builder in `crates/adrian-kdc/src/pac.rs` (~3K lines) emitting 9 MS-KILE buffer types including `PAC_FULL_CHECKSUM` (0x13), `PAC_REQUESTOR` (0x12), and `PAC_BUFFER_TICKET_CHECKSUM` (0x0E, silver-ticket mitigation); byte-identity invariant vs Windows Server 2022+.
- **ADR-011** — AES-256-CTS-HMAC-SHA1-96 (etype 0x12) as default; RC4-HMAC (0x17) disabled by default; per-ADR-014 etype 0x13 (AES-SHA384) preferred when both client and server support.
- **ADR-015** — HSM-bound krbtgt key via PKCS#11 (`cryptoki`); 30-day auto-rotation with 2-key 24-hour overlap; identical mechanism for gMSA KDS root key (ADR-020).
- **ADR-012** — FAST (RFC 6806) armoring required by default; anonymous PKINIT armor TGT (RFC 6112) per ADR-084 unblocks `fast_mode="required"` flip in Phase 3.
- **ADR-083** — Two-layer PAC validation: local Ed25519 signature verification (≤50 µs, zero DC roundtrip) using HSM-derived krbtgt public key, plus legacy `NetrLogonSamLogonEx` (MS-NRPC opnum 45) RPC path for AD-interop services that opt in.

**Rust crates.** `adrian-kdc`, `adrian-kdc-interop`, `adrian-pkinit-bridge` (per ADR-084), `adrian-pac-validator`. External: `rasn`, `rasn-kerberos`, `ring`, `aes`, `sha1`, `sha2`, `hmac`, `md4`, `cryptoki`, `x509-cert`, `webauthn-rs`, `proptest`.

**Key design decisions.** Workshop Decision 5 chose a fresh Rust KDC over Samba's GPLv3 Heimdal fork and MIT-krb5-plus-plugin, justifying the ~30K-line investment on license cleanliness and PAC correctness. The KDC is horizontally scalable (ADR-018) behind a load balancer with sticky affinity for `krb5_nonce`-bearing AS-REQs; each KDC instance holds an HSM-derived krbtgt key handle (not the key material), so all instances emit byte-identical PACs for the same input principal. The `PAC_BUFFER_TICKET_CHECKSUM` mitigation (ADR-123) closes the silver-ticket window for services that opt in. PKINIT (ADR-084) is dual-mode: FIDO2/WebAuthn primary for ordinary users via `adrian-pkinit-bridge` (~4K lines, PA-FIDO2-AS-REQ vendor padata type 0xAB), and RFC 4556 smart-card PKINIT for HSPD-12 / eIDAS compliance. kpasswd (RFC 3244, ADR-019) is the primary password-change protocol with a REST wrapper for self-service UIs. Cross-realm referral (ADR-013) follows RFC 4120 §3.3.3 with strict `Transited` field validation. SPN and UPN uniqueness (ADR-016/017) are enforced pre-commit by KDC/DSA check.

**Implementation priorities.** MVP: AS-REQ/TGS-REQ path, 9-buffer PAC, AES etypes, HSM krbtgt, FAST required, kpasswd. v1: PKINIT smart-card mode, S4U2Self/S4U2Proxy (ADR-087), cross-realm referral, gMSA KDS rotation, PAC validation RPC. v2: PKINIT FIDO2 bridge (Phase 3), etype 0x13 default flip (gated by client coverage), per-realm KDC sharding.

## 3. Auth Provider (NTLM, SASL, SSPI-equivalent) (7 ADRs)

The Auth Provider is the cross-protocol authentication surface: NTLM posture (drop server, client-only), LDAP signing/channel binding, NTP time-sync, structured Kerberos audit events, the SSPI-equivalent unified `AuthModule` abstraction, the unified `Principal` token type, S4U constrained delegation, and pass-the-hash defense. It carries 7 ADRs (ADR-021–023, ADR-085–088) and resolves 2 blockers (PC-037 NTLM relay, PC-038 PtH defense).

**Key ADRs.**
- **ADR-021** — LDAP signing + TLS channel binding (RFC 5929) + EPA mandatory by default; eliminates LDAP-relay and PetitPotam coercion against framework DCs.
- **ADR-085** — NTLM server-side NOT SUPPORTED (rejected with `strongAuthRequired`/`401`); NTLM client-only via `adrian-ntlm-client` (~3K lines, NTLMv2 only, RFC 5929 channel binding, EPA EPHEMERAL flag, platform-secure-credential-store via `keyring`).
- **ADR-086** — Three-layer PtH defense: server-side elimination (no PtH target), HSM-bound PEK encryption for AD-interop users' NT hashes, platform isolation (Linux kernel keyring / systemd-creds, macOS Keychain / Secure Enclave, Windows DPAPI / Credential Guard); `zeroize` wraps all NT hash memory.
- **ADR-087** — S4U2Self (PA-FOR-USER padata 129) + S4U2Proxy (constrained_delegation KDC option bit 14); both classic and RBCD; CVE-2020-17049 (Bronze Bit) mitigation via strict forwardable flag validation.
- **ADR-088** — Unified `Principal` type in `adrian-sdk` `AuthModule` with `sid`, `upn`, `group_sids`, `primary_group_sid`, `privileges`, `logon_type`, `credential_handle` (KerberosTgt / NtlmHash / Certificate / OAuth2Token); platform adapters wrap `LsaLogonUser`, `pam_sm_authenticate`, `ODNodeCopyRecord`.

**Rust crates.** `adrian-ntlm-client`, `adrian-auth-core` (trait + Principal), `adrian-sdk` (`AuthModule`). External: `md4`, `hmac`, `sha2`, `rasn`, `rasn-pkix`, `keyring`, `windows`, `gss-api`, `pam-bindings`, `core-foundation`, `objc2`, `zeroize`, `cryptoki`, `systemd`.

**Key design decisions.** Workshop Decision 6 took the sharp NTLM posture: framework infrastructure accepts zero NTLM (no PetitPotam, no PtH surface against framework services), while framework-managed clients can still authenticate outbound to legacy services via the isolated `adrian-ntlm-client` crate. The unified `Principal` (ADR-088) is the single authorization token type across all platforms — `pam_adrian.so`, `adrianlsa.dll`, and `AdrianOpenDirectory.bundle` all delegate to the same Rust core, eliminating the cross-platform drift that plagues AD's SSPI/PAM/OpenDirectory split. LDAP signing and channel binding (ADR-021) are on by default with no opt-out — the framework's LDAP server refuses unsigned binds from the first day. NTP standardises on chrony (ADR-022), dropping MS-SNTP entirely; Kerberos audit events (ADR-023) emit OpenTelemetry log format with MITRE ATT&CK mapping. The `AuthModule` SSPI-equivalent (ADR-108) exposes `acquire_kerberos` / `acquire_ntlm_client` / `acquire_cert` / `acquire_oauth2` returning `CredentialHandle`, with `init_security_context` / `accept_security_context` mirroring SSPI semantics for ported Windows applications.

**Implementation priorities.** MVP: LDAP signing+channel binding mandatory, NTLM client-only crate, `Principal` type, Kerberos audit OTel events, chrony NTP. v1: S4U2Self/S4U2Proxy, HSM-bound PEK for AD-interop NT hashes, RBCD ACL audit, full `AuthModule` SSPI-equivalent. v2: FIDO2 credential handle, OAuth2 token exchange to Kerberos cross-token flow.

## 4. Policy Engine (GPO-equivalent) (14 ADRs)

The Policy Engine replaces GPO with a hybrid declarative model: a canonical JSON policy format compiled from ADMX templates, distributed via WebSocket push or Git-backed pull, applied by per-platform `PolicyExecutor` implementations (PReg on Windows, MDM Configuration Profile on macOS, `authselect` + `audit.rules` on Linux), with transactional rollback, role-based binding, and Git-backed history with PR review. It carries 14 ADRs (ADR-024–031, ADR-089–094) and resolves 2 blockers (PC-045 GPP cross-platform, PC-055 SYSVOL DFS-R replacement).

**Key ADRs.**
- **ADR-089** — Declarative canonical JSON policy format with INI/`Registry.pol` AD-interop adapter; single source of truth in Git, GPC/GPT views generated for AD-interop.
- **ADR-090** — `admx2adrian` Rust compiler: ingests ADMX+ADML, emits canonical JSON `PolicyTemplate` + JSON Schema + category tree + presentation layout; one-way, deterministic, byte-identical output for reproducible Git diffs.
- **ADR-091** — GPO Preferences (GPP) cross-platform compilation: `PolicyArea::Preferences.{Files,DriveMaps,LocalUsersGroups,ScheduledTasks,Environment,Printers}` compiles to platform-native formats; `cPassword` antipattern eliminated via `secret_ref` type (MS14-025).
- **ADR-094** — SYSVOL-equivalent replication via Git-backed policy repository + SMB read surface (`adrian-smb-server` honours `\\<domain>\SYSVOL\...` UNC paths); eliminates DFS-R Windows-only dependency.
- **ADR-092** — `PolicyExecutor` trait with `WindowsPolicyExecutor` (PReg + GptTmpl.inf + synthetic CSE JSON), `MacOsPolicyExecutor` (Configuration Profile payloads), `LinuxPolicyExecutor` (`authselect` fragments + `/etc/security/limits.conf.d/` + `firewalld`/`nftables` + atomic `rename(2)` writes).

**Rust crates.** `adrian-policy-core`, `adrian-policy-executor`, `adrian-admx-compiler`, `adrian-policy-cel`, `adrian-policy-preg`, `adrian-policy-distribution`, `adrian-policy-daemon`, `adrian-sssd-gpo`. External: `quick-xml`, `serde_json`, `cel`, `regorus`, `plist`, `rustls`, `tokio`, `git2`, `tokio-tungstenite`.

**Key design decisions.** Workshop Decision 7 chose hybrid: declarative JSON is canonical, ADMX is consumed by `admx2adrian` (one-way), and `preg2adrian`/`adrian2preg` adapters preserve Windows interop for the GPT distribution channel. CEL is the default selector language (Rego opt-in) for role-based binding (ADR-030) — `Claims.user.department == "Engineering" && Host.facts.os == "linux"`. Transactional rollback (ADR-025) uses a per-host `policy_state.db` (SQLite) with `BEGIN → apply → COMMIT` semantics; failed applies roll back via shadow-path `rename(2)`. Push distribution (ADR-028) uses WebSocket with mTLS auth, falling back to 90-second HTTP long-poll for hosts behind restrictive proxies. Slow-link detection (ADR-027) uses HTTP HEAD probe at policy refresh start. Git-backed history (ADR-031) means every policy change is a PR with diff review — operators get `git blame` on every registry key in `Registry.pol`. The `adrian-sssd-gpo` Rust library (~2K lines, ADR-093) extends SSSD's `[Privilege Rights]` coverage to the full `Security` PolicyArea (LogonHours, HostAccessControl, GroupPolicyAccessControl) via the `gpo_access_provider = adrian` directive.

**Implementation priorities.** MVP: canonical JSON, `admx2adrian` compiler for Microsoft built-in ADMX (~3,500 policies), `WindowsPolicyExecutor`, `LinuxPolicyExecutor`, Git-backed distribution, WebSocket push. v1: `MacOsPolicyExecutor` (full Configuration Profile coverage), GPP cross-platform, `preg2adrian` reverse adapter, transactional rollback, role-based binding. v2: DDM-first authoring for macOS 13+ payloads, Rego selector opt-in, synthetic CSE for legacy Windows apps.

## 5. Cert Service (PKI / CA / Enrollment) (11 ADRs)

The Cert Service replaces AD CS with a two-tier CA (offline HSM-bound root + online enterprise CA), ACME-primary enrollment (RFC 8555 + RFC 8737 + RFC 8823 ARI), MS-WCCE/MS-XCEP/MS-WSTEP bridge for Windows `autoenroll.dll` interop, OCSP responder per RFC 6960 with HA cluster, multi-CDP with CRL fallback, HSM-bound KRA keys with Shamir M-of-N secret sharing, and YAML-defined certificate profiles replacing `msPKI-*` templates. It carries 11 ADRs (ADR-032–037, ADR-095–099) and resolves 1 blocker (PC-057 no open-source MS-WCCE server).

**Key ADRs.**
- **ADR-095** — ACME-primary enrollment server (`adrian-acme-server`) + `adrian-wcce-bridge` translating MS-WCCE/MS-XCEP/MS-WSTEP to ACME orders; `adrian-attest-01` challenge type for framework-enrolled hosts with TPM2 / Apple Secure Enclave attestation; EAB required for all framework accounts.
- **ADR-037** — Two-tier CA: offline root (HSM-bound, 20-year validity), online enterprise CAs (HSM-bound, 5-year validity); trust-manager model (ADR-036) with cross-cert for AD-interop only.
- **ADR-032** — HSM-bound KRA keys with Shamir secret sharing (M-of-N, default M=3, N=5); key recovery requires quorum of N KRA officers.
- **ADR-033** — OCSP responder per RFC 6960 with nonce support; HA cluster behind load balancer; responder signs with delegated-issuance cert (not the CA key) for HSM-offload.
- **ADR-096** — YAML certificate profiles (`profile.yaml`) replace `msPKI-*` LDAP attributes; profile-versioned with migration path for template changes; subject-name pattern, SAN policy, EKU constraints, validity period, renewal window defined in YAML.

**Rust crates.** `adrian-ca`, `adrian-acme-server`, `adrian-wcce-bridge`, `adrian-est-bridge`, `adrian-scep-bridge`, `adrian-hsm` (uniform `Signer` trait over PKCS#11/CNG), `adrian-ocsp`, `adrian-ca-core`. External: `cryptoki = "0.5"`, `windows = "0.54"` (NCrypt CNG KSP), `x509-cert`, `ring`, `rustls`, `tokio`, `axum`, `serde_yaml`, `thiserror`.

**Key design decisions.** Workshop Decision 8 made ACME the primary protocol — modern, RFC-standard, and the only one with a mature Rust ecosystem (the framework's CA is the ACME server, not a client). The MS-WCCE bridge is a translation layer: Windows `autoenroll.dll` calls MS-WCCE opnum 36, the bridge extracts the PKCS#10 CSR, maps the template OID to a framework YAML profile via `template-map.yaml`, creates an ACME order with `adrian-attest-01` challenge (auto-fulfilled via the host's Kerberos-authenticated RPC context), and returns the issued cert as an MS-WCCE response. EST (RFC 7030) and SCEP (RFC 8894) bridges cover IoT/network devices. NTAuthCertificates (ADR-099) is redesigned as a per-tenant trust store (modernisation win over AD's global canonical list). The CA's PostgreSQL database stores issued certs, pending ACME orders, accounts, CRLs, OCSP responses, and KRA-archived private keys. Backup/restore coverage (ADR-059) extends to PostgreSQL via `pgBackRest` PITR.

**Implementation priorities.** MVP: two-tier CA, HSM-bound keys, ACME server, OCSP responder, YAML profiles, basic `autoenroll.dll` interop via MS-WCCE bridge. v1: full `adrian-wcce-bridge` for all 4 MS-WCCE opnums, KRA key recovery with Shamir quorum, multi-CDP HA, EST and SCEP bridges. v2: short-lived cert default (lifetime ≤ 24 hours, ARI-driven renewal), cross-forest CA trust via `adrian-cli trust establish`.

## 6. Federation Gateway (SAML / OIDC / WS-Fed) (10 ADRs)

The Federation Gateway replaces AD FS with Keycloak 25+ (Quarkus distribution) running as a Kubernetes StatefulSet with a Rust `adrian-federation-shim` sidecar that handles WS-Trust-to-OIDC bridging (ADR-039), claim-rule translation, JWKS rollover with webhook notification (ADR-038), strict OIDC by default with `resource=` compat opt-in (ADR-041), SAML replay detection with per-RP clock skew (ADR-040), and identity brokering / HRD (ADR-104). It carries 10 ADRs (ADR-038–042, ADR-100–104) and has zero blockers — modern IdP ecosystem covers the gap.

**Key ADRs.**
- **ADR-100** — Keycloak StatefulSet + Rust shim sidecar; replaces AD FS service host + WID/SQL + WAP; no MS-ADFSPIP; PostgreSQL backend with `synchronous_commit = on`.
- **ADR-101** — AD FS claim-rule language compatibility via Rust `adrian-claims-engine` crate; the shim translates AD FS CRL to Keycloak's native map/reducer or Rego plugin.
- **ADR-103** — Keycloak topology is StatefulSet with Infinispan distributed caches (owners=2 for sessions, owners=2 for auth sessions); no primary/secondary, no WID single-writer ceiling.
- **ADR-039** — WS-Trust-to-OIDC bridge for legacy RPs (SharePoint 2013/2016/2019, Office desktop WS-Trust, custom WIF apps); the shim accepts `wsignin1.0` requests and translates to OIDC code-flow.
- **ADR-104** — Identity brokering and HRD (Home Realm Discovery) via Keycloak-native; the shim adds the framework's host-identity context for framework-enrolled clients.

**Rust crates.** `adrian-federation-shim`, `adrian-claims-engine`. External: `axum`, `tokio`, `rustls`, `openidconnect`, `saml2`, `moka` (LRU cache), `serde_json`, `reqwest`, `jsonwebtoken`, `tokio-tungstenite`.

**Key design decisions.** Workshop Decision 9 chose wrap-Keycloak over re-implementing AD FS or building native. The Rust shim is stateless — all per-realm, per-client, per-rule configuration lives in Keycloak's PostgreSQL, and the shim loads on demand with a 5-minute `moka` LRU cache. This means the shim can be horizontally scaled independently of Keycloak; in a multi-replica StatefulSet, any shim instance can serve any request. The shim's perimeter-auth functions (pre-auth, relay-state storage, header injection) are implemented natively in Rust; relay state is stored in PostgreSQL (`adrian_relay_state` table keyed by an opaque 256-bit token). The WS-Trust bridge is the only piece that cannot be natively served by Keycloak — Keycloak 25+ dropped WS-Trust server support, so the shim re-implements the WS-Trust `wsignin1.0` flow as a translator to OIDC code-flow. JWKS rollover (ADR-038) is 15-day overlap with webhook notification to relying parties; SAML replay detection (ADR-040) is 60-minute window with per-RP clock skew policy. AD RMS is explicitly out of scope (ADR-042) — recommend Microsoft Azure Information Protection.

**Implementation priorities.** MVP: Keycloak StatefulSet with PostgreSQL, Rust shim with reverse proxy and JWKS rollover, SAML 2.0 + OIDC endpoints, basic AD FS claim-rule translation. v1: WS-Trust-to-OIDC bridge for legacy RPs, full claim-rule compatibility, identity brokering, SAML replay detection, `resource=` compat opt-in. v2: Rego-based claims engine opt-in, multi-region Keycloak clustering, AD FS management-plane compat (`Set-AdfsRelyingPartyTrust` equivalent CLI).

## 7. File Gateway (SMB / DFS / Print) (7 ADRs)

The File Gateway ships a fresh Rust SMB 3.1.1 server with SHA-512 preauth integrity and AES-256-GCM encryption (no Samba, no `srv2.sys`), DFS-N-equivalent via DNS SRV records, Access-Based Enumeration via pre-computed per-share index, IPP Everywhere for print (MS-RPRN dropped), and Offline Files out of scope. It carries 7 ADRs (ADR-043–047, ADR-105–106) and resolves 3 blockers (PC-078 SMB 3.1.1, PC-079 SMB1 drop, PC-083 PrintNightmare).

**Key ADRs.**
- **ADR-105** — Fresh Rust SMB 3.1.1 server (`adrian-smb-server`); dialects SMB 2.0.2/2.1/3.0/3.0.2/3.1.1; SHA-512 preauth integrity per MS-SMB2 §3.2.5.1; AES-256-GCM encryption mandatory for 3.1.1; AES-GMAC signing; TCP/445 only (no NetBIOS).
- **ADR-043** — SMB1 dropped entirely; `server min protocol = SMB2_02` equivalent; no fallback to LANMAN.
- **ADR-046** — MS-RPRN dropped (PrintNightmare CVE-2021-34527 mitigation); IPP Everywhere (RFC 8011) adopted for driverless printing; `cups` integration for legacy print queues.
- **ADR-044** — DFS-N-equivalent via DNS SRV records (`_smb._tcp.<domain>`); no DFS-R replication (Windows-only); framework-native Git-backed file distribution for roaming profiles.
- **ADR-045** — ABE via pre-computed per-share index in FDB subspace `0x0D`; index rebuilt on ACL change with 5-second eventual consistency; `FindFirst`/`FindNext` filtered server-side.
- **ADR-106** — SMB client (`adrian-smb-client`) in framework SDK with persistent handles for SYSVOL access during GPO refresh.

**Rust crates.** `adrian-smb-server`, `adrian-smb-core`, `adrian-smb-client`, `adrian-print-service`. External: `tokio`, `rustls`, `ring`, `aes`, `aes-gcm`, `sha2`, `hmac`, `rasn`, `rasn-kerberos`, `gss-api`, `pavao` (SMB client reference), `hickory-server` (DNS).

**Key design decisions.** Workshop Decision 10 rejected Samba (GPLv3 license conflict, embedding difficulty, memory-safety posture) and platform-native servers (Windows-only `srv2.sys`, closed-source macOS SMBX, no Linux equivalent). The fresh Rust implementation is ~15K lines targeting SMB 3.1.1 dialect with five fallback dialects for client compatibility. Pre-auth integrity hash (SHA-512 over the entire Negotiate exchange) is mixed into HKDF-SHA512 key derivation labeled `"SMBSigningKey"` / `"ServerIn"` / `"ServerOut"` per MS-SMB2 §3.2.5.2 — without it, a MITM can downgrade dialect negotiation. Authentication is Kerberos SPNEGO via GSSAPI preferred (SPN `cifs/<host-fqdn>@<realm>` registered at host enrollment), NTLM SPNEGO disabled by default per ADR-085 (operators can enable via `smb.auth.ntlm = "allowed"`). SMB Direct (RDMA) is opt-in via `rust-rdma` FFI, Linux-only in v1. Continuously Available (CA) shares use the framework's operator-managed quorum (ADR-058); persistent handles survive DC failover via Raft state machine replication. PrintNightmare is structurally eliminated — no `spoolsv.exe`, no MS-RPRN, no driver install path that runs as SYSTEM. IPP Everywhere (RFC 8011) is the only print protocol; `cups` integration provides legacy queue compat for clients that still need PostScript/PCL.

**Implementation priorities.** MVP: SMB 3.1.1 server with SHA-512 preauth integrity, AES-256-GCM encryption, Kerberos SPNEGO auth, ABE index, DFS-N via DNS SRV. v1: CA shares with persistent handles, SMB Direct (RDMA), IPP Everywhere print service, full `adrian-smb-client` for SYSVOL. v2: SMB multichannel, scale-out shares via FDB-backed metadata, macOS-specific SMBX interop testing.

## 8. Client SDK (cross-platform library) (9 ADRs)

The Client SDK is the unified Rust core (`adrian-sdk`) with platform-specific bindings (C ABI / JNI / Swift / pyo3 / cgo) exposing authentication, directory query, policy application, cert enrollment, file client, and federation token validation across Windows, macOS, and Linux from one API surface. It carries 9 ADRs (ADR-048–051, ADR-107–111) and resolves 2 blockers (PC-085 no universal SDK, PC-089 ID mapping).

**Key ADRs.**
- **ADR-107** — Unified Rust core SDK with platform-specific bindings; `AdrianClient` with `auth()`, `directory()`, `policy()`, `cert()`, `file()`, `federation()` modules; 30 person-weeks total per Decision 11.
- **ADR-108** — SSPI-equivalent `AuthModule` with `acquire_kerberos`/`acquire_ntlm_client`/`acquire_cert`/`acquire_oauth2` returning `CredentialHandle`; `init_security_context`/`accept_security_context` with RFC 5929 channel binding.
- **ADR-109** — Cross-platform LDAP client library (Wldap32 equivalent) built on `ldap3 = "0.11"`; AD-specific extended controls (DirSync, ASQ, cross-domain move, tree-delete-ex, get-stats, verify-name, quota-control); GSS-SPNEGO bind via `AuthModule`.
- **ADR-110** — SID-to-UID mapping via UUID-primary identity; algorithm `uuid_to_uid(uuid) = (uuid_to_u64(uuid) % (2^31 - 65536)) + 65536`; directory-stored mode for migrated deployments; collision handling via FDB atomic-add counter.
- **ADR-111** — Unified ticket cache abstraction (`TicketCache`) with KCM on Linux, `API:Initialdefaultcache` on macOS, LSA in-memory on Windows; `adrian-kerberos-renewd` daemon 50% TGT lifetime.

**Rust crates.** `adrian-sdk` (Rust core), `adrian-sdk-c` (C ABI via `cbindgen`), `adrian-sdk-jni` (JNI bindings), `adrian-sdk-swift` (Swift via `swift-bridge`), `adrian-sdk-python` (pyo3 + maturin), `adrian-kerberos-renewd`, `adrian-kerberos-sync`. External: `tokio`, `serde`, `ldap3`, `pavao`, `rustls`, `openidconnect`, `saml2`, `cbindgen`, `jni`, `swift-bridge`, `pyo3`, `maturin`, `pam-bindings`, `libc`, `windows`, `objc2`, `core-foundation`, `systemd`, `gss-api`, `kcm-client`, `security-framework`.

**Key design decisions.** Workshop Decision 11 rejected gRPC-based SDK (runtime dependency too heavy for edge/embedded) and per-platform wrappers (no API consistency). The Rust core exposes both `async` methods (for Rust consumers via `tokio`) and blocking methods (for FFI consumers via `tokio::runtime::Runtime::block_on`). Platform-native integrations are additive, not replacing: `pam_adrian.so` + `nss_adrian.so.2` on Linux (alongside SSSD), `adrianlsa.dll` LSA Authentication Package on Windows (alongside SSPI), `AdrianOpenDirectory.bundle` on macOS (alongside OpenDirectory). This means existing platform-native apps keep working; new apps use the SDK for cross-platform consistency. SID-to-UID mapping (ADR-110) uses the deterministic `uuid_to_uid` algorithm for greenfield deployments and directory-stored mode for migrated deployments preserving existing UIDs — `adrian-cli migrate from-{sssd,winbind,pbis,dsconfigad}` translates existing UIDs to directory-stored mappings. The unified ticket cache (ADR-111) eliminates the FILE:/KEYRING:/KCM/API: divergence — every platform sees the same `TicketCache` API.

**Implementation priorities.** MVP: Rust core with `AuthModule` + `DirectoryModule`, C ABI + Python bindings, PAM/NSS provider for Linux, SID-to-UID mapping. v1: JNI + Swift bindings, `PolicyModule` + `CertModule` + `FileModule` + `FederationModule`, LSA Authentication Package for Windows, OpenDirectory plugin for macOS, `adrian-kerberos-renewd` daemon. v2: Go bindings via cgo, full `adrian-cli` cross-platform CLI, offline mode with delta sync.

## 9. Cross-Platform Parity (12 ADRs)

The Cross-Platform Parity capability tracks platform-specific gaps and ensures a Windows client, a macOS client, and a Linux client all join the same framework domain, authenticate the same user, apply the same policy, mount the same shares, request the same certs, and federate to the same RPs without divergence. It carries 12 ADRs (ADR-052–056, ADR-112–118) and resolves 1 blocker (PC-095 unified policy authoring, ADR-113).

**Key ADRs.**
- **ADR-113** — GPP and cross-platform policy compilation: `PolicyModule` compiles canonical JSON to platform-native formats; `PolicyArea` enum with per-platform compilation targets; `cPassword` eliminated via `secret_ref`; `PolicyExecutor` trait with per-platform implementations.
- **ADR-114** — Linux identity stack: SSSD primary, Winbind deprecated, PBIS unsupported; `adrian-sssd-gpo` Rust library extends SSSD's GPO coverage; `adrian-with-sudo` authselect profile; container-native DaemonSet.
- **ADR-112** — macOS NTLM client gap closed by `adrian-ntlm-client` Rust crate (~3K lines, pure-Rust NTLMv2); NTLMv1 unconditionally disabled; RFC 5929 channel binding; EPA EPHEMERAL flag.
- **ADR-116** — Legacy macOS agents (NoMAD / Enterprise Connect / Jamf Connect / Centrify / PBIS) EOL; PSSO Extension first strategy; `adrian-cli migrate from-{enterprise-connect,nomad,jamf-connect,centrify,pbis,admitmac,dave}` migration tools.
- **ADR-117** — Apple Heimdal fork staleness mitigated by fresh Rust KDC + unified PAC validator (`libframework_pac_validator.dylib`); framework does NOT replace system Heimdal (would break PSSO); `pac_full_checksum_mode` setting (`required`/`supported`/`audit`/`disabled`).

**Rust crates.** `adrian-sssd-gpo`, `adrian-ntlm-client` (macOS/Linux client), `adrian-pac-validator`, `adrian-policy-executor` (per-platform), `adrian-authselect-profile`, `adrian-base-container`. External: `clap`, `tokio`, `serde`, `serde_json`, `plist`, `ini`, `tdb`, `objc2`, `core-foundation`, `md4`, `hmac`, `sha2`, `rasn`, `rasn-pkix`, `keyring`, `tracing`, `opentelemetry`.

**Key design decisions.** Workshop Decision 12 resolved ORQ-202/203 in favor of SSSD primary + FreeIPA alternative + Winbind deprecated + PBIS unsupported. The `adrian-sssd-gpo` library extends SSSD's `[Privilege Rights]` coverage to the full `Security` PolicyArea via `gpo_access_provider = adrian` directive; FreeIPA remains supported via cross-realm trust (ADR-115) with `adrian-cli trust establish --peer freeipa` creating the trust object and configuring `altSecurityIdentities`. macOS strategy (ADR-116) is PSSO Extension first per ADR-056 — `com.apple.configuration-ext.platform-sso` MDM profile with `Hardware_Bound` mode default for T2/Apple Silicon, `Password` fallback for Intel-without-T2; `adrian-cli migrate from-{enterprise-connect,nomad,jamf-connect,centrify,pbis,admitmac,dave}` detects each legacy agent's installation, translates config to PSSO + Client SDK config, schedules removal on next reboot. The Heimdal fork (ADR-117) is mitigated, not fixed — framework's Rust KDC produces modern PACs (PAC_FULL_CHECKSUM, PAC_REQUESTOR, compound identity, PAC_BUFFER_TICKET_CHECKSUM per MS-KILE §2.2) and the unified PAC validator bypasses macOS system Heimdal's stale PAC parser. MCX legacy (ADR-118) is migrated to MDM Configuration Profiles + DDM-first fallback for macOS 13+.

**Implementation priorities.** MVP: GPP cross-platform compilation, SSSD primary reference deployment, `adrian-sssd-gpo` library, `adrian-with-sudo` authselect profile, macOS NTLM client. v1: PSSO MDM profile template, `adrian-cli migrate from-{winbind,pbis,enterprise-connect,nomad,jamf-connect,centrify,pbis,admitmac,dave}`, FreeIPA cross-realm trust, MCX-to-MDM migration. v2: DDM-first authoring for macOS 14+ payloads, FreeIPA HBAC sync to framework `Security.PermitHosts`.

## 10. Operations (deploy / monitor / recover) (10 ADRs)

The Operations capability covers deployment (container-native DCs + Kubernetes operator), observability (Prometheus + OpenTelemetry), backup/DR (per-DC backup with PITR + operator-driven runbooks), audit (structured OTel logs + MITRE ATT&CK mapping), API surface (REST for CRUD + gRPC for streaming), trust password auto-rotation, multi-region replication topology, schema-as-code GitOps, functional levels as capability flags, and the unified cross-platform CLI. It carries 10 ADRs (ADR-057–063, ADR-119–121) and has zero individual blockers.

**Key ADRs.**
- **ADR-058** — Container-native DCs as StatefulSet with PVC-backed DIT; `DomainController` CRD driven by `adrian-operator`; operator implements promote/demote/backup/restore/schema-upgrade/fsmo-transfer/fsmo-seize lifecycle.
- **ADR-057** — Prometheus exporter + OpenTelemetry instrumentation; metrics for LDAP/Kerberos/SMB/replication; tracing for cross-component request flow; logs in OTel format.
- **ADR-059** — Per-DC backup with PITR; operator-driven DR runbooks; FDB `backup_agent` continuous to S3/GCS/Azure Blob/MinIO; `fastrestore` for restore-to-timestamp.
- **ADR-060** — Structured audit logs in OTel format with MITRE ATT&CK mapping; events include `4662`-equivalent (replication priv use), `4769`-equivalent (TGS-REQ with etype), `4624`-equivalent (logon), `4720`-equivalent (user create).
- **ADR-119** — Schema-as-code with GitOps: schema migrations are Git PRs with typed projection regeneration; reversible via `adrian-cli schema rollback`; `objectVersion` synthesized for AD-interop.
- **ADR-121** — Functional levels as capability flags, not forest-wide gates; per-DC capability advertisement via `msDS-IsParentCapability`-equivalent attributes; no irreversible forest-wide upgrade.

**Rust crates.** `adrian-operator`, `adrian-monitor`, `adrian-cli`, `adrian-migrate`. External: `kube` (Rust Kubernetes client), `tokio`, `axum`, `tonic` (gRPC), `prometheus`, `opentelemetry`, `opentelemetry-otlp`, `tracing`, `tracing-opentelemetry`, `clap`, `git2`, `serde_yaml`, `reqwest`.

**Key design decisions.** Container-native deployment is the primary deployment model — bare-metal/VM is documented but not the reference path. The `adrian-operator` (ADR-058) manages the full DC lifecycle via a `DomainController` CRD: `promote` (seeds new DC from existing DIT snapshot via IFM-equivalent path), `demote` (drains replication partners, removes `nTDSDSA` object), `backup` (triggers PVC snapshot or logical export), `restore` (PVC restore + USN-rollback-equivalent detection), `schema-upgrade` (atomic with rollback), `fsmo-transfer` (graceful) or `fsmo-seize` (forcible). Schema-as-code (ADR-119) replaces AD's irreversible `adprep /forestprep` with Git PRs — operators get `git revert` on schema changes, the typed projection regenerates on `schemaUpdateNow`, and `objectVersion` is synthesized for AD-interop. Functional levels (ADR-121) are per-DC capability flags rather than forest-wide gates — no more irreversible "raise forest functional level" operation. The unified CLI (ADR-063, deferred implementation language but locked to Rust in Decision 11) is `adrian-cli` with subcommands for every operational task: `adrian-cli join`, `adrian-cli klist`, `adrian-cli policy coverage`, `adrian-cli migrate from-{sssd,winbind,pbis,dsconfigad,enterprise-connect,nomad,jamf-connect,centrify}`, `adrian-cli audit-ntlm`, `adrian-cli trust establish`, `adrian-cli fdb provision`, `adrian-cli schema rollback`. REST API (ADR-061) is CRUD via `axum`; gRPC is streaming (replication health, audit tail) via `tonic`; GraphQL deferred (Tier-2 ORQ-226/227/228).

**Implementation priorities.** MVP: container-native DC StatefulSet, `adrian-operator` with promote/demote/backup/restore, Prometheus exporter, OTel instrumentation, basic audit logs. v1: full DR runbooks, schema-as-code GitOps, functional levels as capability flags, unified CLI with all migration subcommands, multi-region replication topology (ADR-120). v2: GraphQL API, predictive autoscaling based on auth rate, multi-cluster federation.

## 11. Security & Threat Model (8 ADRs)

The Security capability makes the framework's threat mitigations explicit and on-by-default rather than opt-in via GPO. It covers Kerberoasting mitigation (AES-only migration + detection), golden ticket mitigation (HSM-bound krbtgt + auto-rotation), silver ticket mitigation (mandatory `PAC_BUFFER_TICKET_CHECKSUM`), DCSync mitigation (per-principal audit + HSM-bound break-glass), sIDHistory abuse mitigation (per-trust filtering), AdminSDHolder replacement (declarative RBAC), selective authentication (FreeIPA HBAC-style), and supply-chain security (Sigstore + in-toto). It carries 8 ADRs (ADR-064–067, ADR-122–125) and resolves 3 blockers (PC-116 Kerberoasting, PC-117 DCSync, PC-118 golden ticket).

**Key ADRs.**
- **ADR-064** — Kerberoasting mitigation: AES-only migration path; RC4 disabled by default (per ADR-011); `4769`-equivalent audit event flagged when etype 0x17 appears in TGS-REQ; service-account migration tracker.
- **ADR-065** — Golden ticket mitigation: HSM-bound krbtgt key (per ADR-015); 30-day auto-rotation with 2-key 24-hour overlap; ticket-validation default (services validate TGT authenticity via KDC).
- **ADR-122** — DCSync mitigation: per-principal `DS-Replication-Get-Changes-All` audit (4662-equivalent); HSM-bound break-glass for full-sync operations; native Raft mode eliminates `EXOP_REPL_SECRETS` wire attack.
- **ADR-123** — Silver ticket mitigation: mandatory KDC-side `PAC_BUFFER_TICKET_CHECKSUM` generation (per ADR-082); default service-side validation; per-service opt-out; audit events `pac_validation.success/failed/skipped`.
- **ADR-124** — sIDHistory injection mitigation: per-trust filtering policy on identity mapping table (per Decision 3); within-forest trusts default to filtering ON (vs AD's default OFF); audit `sidhistory_write` events.
- **ADR-067** — Sigstore signing + in-toto attestations for supply-chain security; framework binaries signed via `cosign sign --key <kms>`; build provenance via in-toto attestations; verify via `cosign verify` at deploy time.

**Rust crates.** `adrian-pac-validator` (unified PAC validator), `adrian-monitor` (audit event ingestion), `adrian-policy-core` (declarative RBAC). External: `sigstore`, `cosign`, `in-toto`, `ring`, `rasn`, `rasn-kerberos`, `cryptoki`, `tracing`, `opentelemetry`, `prometheus`.

**Key design decisions.** Native Raft mode (per Decision 1) eliminates DCSync entirely — there is no `EXOP_REPL_SECRETS` opnum to call. AD-interop mode inherits the DCSync attack surface, mitigated by per-principal audit (every `DS-Replication-Get-Changes-All` invocation emits a 4662-equivalent event with the caller's identity, target NC head, and `ulExtendedOp` value) and HSM-bound break-glass (full-sync operations require an HSM-resident quorum key, not just the directory-level extended right). The HSM-bound krbtgt (ADR-065) closes the golden-ticket window — an attacker who exfiltrates the directory cannot forge TGTs because the krbtgt key never leaves the HSM. 30-day rotation with 2-key overlap means a stolen key is valid for at most ~60 days (current + previous). Silver ticket mitigation (ADR-123) makes `PAC_BUFFER_TICKET_CHECKSUM` mandatory on the KDC side and default-validating on the service side — a forged silver ticket lacks the correct krbtgt-signed ticket checksum, so validation fails. sIDHistory abuse (ADR-124) is mitigated by per-trust filtering on the identity mapping table; within-forest trusts default to filtering ON (vs AD's default OFF, the documented attack vector). AdminSDHolder (ADR-066) is replaced by declarative RBAC templates — no 60-minute SDPROP reset overriding delegated permissions. Supply-chain (ADR-067) uses Sigstore + in-toto independent of distribution channel — a compromised WSUS-equivalent cannot push arbitrary code.

**Implementation priorities.** MVP: AES-only default, HSM-bound krbtgt with auto-rotation, per-principal DCSync audit, mandatory `PAC_BUFFER_TICKET_CHECKSUM`, sIDHistory filtering default ON. v1: full Kerberoasting detection (4769 etype alerting), silver-ticket default service-side validation, AdminSDHolder replacement with declarative RBAC, Sigstore signing of all framework binaries. v2: in-toto attestation verification at deploy time, predictive threat detection via OTel log anomaly scoring, selective authentication HBAC.

## 12. Migration & Coexistence (7 ADRs)

The Migration capability covers the path from AD to the framework: sIDHistory migration via `DRSAddSidHistory` + time-limited passthrough + ACL rewrite plan, Kerberos cross-realm during parallel-run with per-SPN/per-user/per-host granularity, password hash migration, GPO translation via `admx2adrian` + `preg2adrian` with per-setting review workflow, DNS subdomain strategy, SYSVOL migration to SMB-served Git-backed policy share + HTTPS distribution + DFS-N referral, and auto-generated `capaths` + DNS SRV KDC discovery. It carries 7 ADRs (ADR-068–069, ADR-126–130) and has zero individual blockers.

**Key ADRs.**
- **ADR-126** — sIDHistory migration via `DRSAddSidHistory` (DRSUAPI opnum 20) with time-limited passthrough window (default 180 days) and mandatory ACL rewrite plan; `adrian-cli migrate sidhistory` orchestrates the workflow.
- **ADR-128** — Kerberos cross-realm during migration at three granularities: per-SPN (lowest-risk, slowest), per-user (medium), per-host (fastest, highest-risk); cross-realm TGT referral per RFC 4120 §3.3.3; `adrian-cli migrate parallel-run --granularity {per-spn,per-user,per-host}`.
- **ADR-129** — Password hash migration via ADMT-equivalent password copy (requires DCSync-equivalent source access) + alternative password-sync agent; `adrian-cli migrate passwords --source <dc>` orchestrates with audit trail.
- **ADR-127** — GPO translation via `admx2adrian` + `preg2adrian` with per-setting review workflow; coverage report flags settings with no clean 1:1 mapping (typically 15–25% of source GPOs).
- **ADR-130** — SYSVOL migration via SMB-served Git-backed policy share + HTTPS distribution + DFS-N referral; per-domain SYSVOL with DFS-N referral during coexistence; HTTP-based distribution as greenfield alternative.
- **ADR-068** — Subdomain-per-directory DNS strategy for migration (`ad.corp.example.com` for AD, `id.corp.example.com` for framework); SRV records scoped to subdomain.

**Rust crates.** `adrian-migrate`, `adrian-gpo-translate` (wraps `admx2adrian` + `preg2adrian`), `adrian-cli` (migration subcommands). External: `clap`, `tokio`, `serde`, `serde_json`, `ldap3`, `gss-api`, `reqwest`, `rand`, `tracing`, `quick-xml`, `plist`, `ini`, `tdb`.

**Key design decisions.** The framework's migration story is parallel-run, not big-bang. During the coexistence window (typically 30–180 days), the framework and AD run side-by-side with cross-realm Kerberos trust (per ADR-128) and LDAP referrals (per ADR-126). sIDHistory passthrough (ADR-126) preserves ACL continuity — the source-domain SID travels in the target user's `sIDHistory`, the source KDC preserves it in the PAC's `ExtraSids` array, and resources with ACLs referencing the source SID continue to grant access. The time-limited passthrough window (default 180 days, matching `tombstoneLifetime`) forces operators to plan ACL rewrites rather than leave sIDHistory as a permanent crutch — `adrian-cli migrate sidhistory audit` reports ACLs still referencing source SIDs as the window closes. Password hash migration (ADR-129) supports three modes: ADMT-equivalent password copy (requires DCSync-equivalent source access, preserves hashes byte-identical), password-sync agent (proprietary protocol, real-time sync during coexistence), and password-reset-at-next-login (operationally painful, last resort). GPO translation (ADR-127) is per-setting review — `admx2adrian` compiles ADMX to canonical JSON, `preg2adrian` extracts current values from `Registry.pol`, and a coverage report flags settings with no clean 1:1 mapping (typically 15–25% of source GPOs). SYSVOL migration (ADR-130) uses DFS-N referral during coexistence (`\\corp.example.com\SYSVOL` for AD, `\\corp.example.com\NEW-SYSVOL` for framework); cutover per-OU as framework-enrolled clients take over. DNS subdomain strategy (ADR-068) avoids SRV-record collision during coexistence — `ad.corp.example.com` for AD, `id.corp.example.com` for framework, with `adrian-cli trust establish --peer ad` creating the cross-realm trust.

**Implementation priorities.** MVP: sIDHistory migration via `DRSAddSidHistory`, cross-realm Kerberos trust, password hash migration via ADMT-equivalent copy, DNS subdomain strategy, basic `admx2adrian` + `preg2adrian` with coverage report. v1: per-SPN/per-user/per-host parallel-run granularities, full SYSVOL migration with DFS-N referral, `adrian-cli migrate from-{sssd,winbind,pbis,dsconfigad,enterprise-connect,nomad,jamf-connect,centrify}`, ACL rewrite plan generator. v2: claims-based migration for Server 2012+ forest functional level (replaces sIDHistory), automated cutover orchestration with rollback, multi-forest migration topology planner.

## Synthesis

The 12 capabilities resolve 130 problems via 130 ADRs spanning ~145K words. The dependency graph is: Core Directory → KDC → Auth Provider → {Policy, Cert, Federation, File, SDK}; Cross-Platform Parity → SDK + Policy; Operations → all; Security → all; Migration → all. The 23 blockers concentrate in Core Directory (4), KDC (3), Auth Provider (2), Policy (2), File Gateway (3), Client SDK (2), Security (3), Cert (1), Cross-Platform Parity (1) — Federation, Operations, and Migration have no individual blockers but define operability and adoption. Workshop Decisions 1–12 unblocked 61 deferred problems via 61 follow-up ADRs (ADR-070–130). The 9 cross-ADR clusters (Kerberos etype, krbtgt HSM, audit, policy, PKI, federation, time sync, migration, identity-mapping) cut across capability boundaries and must be implemented together. The Rust workspace in [`./04-rust-workspace-design.md`](./04-rust-workspace-design.md) translates this capability graph into ~30–40 crates organized in 5 dependency layers.
