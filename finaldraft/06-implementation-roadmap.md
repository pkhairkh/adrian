# Implementation Roadmap

## Roadmap philosophy

The Adrian framework is large: 130 cataloged problems ([`catalog/README.md`](../catalog/README.md)), 262 open research questions, 12 framework capabilities, 3 target platforms (Linux, macOS, Windows). A naive "design everything then build everything" sequence would take a decade and produce nothing usable. We sequence instead by *decision leverage* and *deliverable value*. The Tier-1 ORQ Resolution Workshop (12 decisions, [`workshop/CONTEXT.md`](../workshop/CONTEXT.md)) already locked the foundational architecture in Phase 0 — replication protocol (Decision 1: native Raft with hybrid DRSUAPI adapter), storage engine (Decision 2: FoundationDB 7.3+), identity model (Decision 3: UUID-primary + SID-as-attribute), schema model (Decision 4: typed schema projection over LDAP wire), KDC implementation (Decision 5: fresh Rust ~30K lines), NTLM posture (Decision 6: server-side dropped, client-only), policy format (Decision 7: hybrid declarative JSON + ADMX compiler), PKI enrollment (Decision 8: ACME primary + MS-WCCE bridge), federation layer (Decision 9: Keycloak-wrapped), SMB server (Decision 10: fresh Rust SMB 3.1.1), Client SDK (Decision 11: unified Rust core + platform bindings), Linux tier (Decision 12: SSSD primary + FreeIPA alt). Phase 0 produced 130 ADRs ([`adr/README.md`](../adr/README.md)) resolving the catalog; Phase 1+ implements them.

Severity tiers from the catalog drive phase scoping: **23 blocker-class problems** (architecture-spanning, MVP-blocking) define the MVP; **64 high-severity problems** define v1 (production hardening, security mitigations, full cross-platform parity, operational tooling); **33 medium-severity problems** define v2 (migration tools, advanced federation, advanced PKI, advanced file gateway, multi-region/DR); **10 low-severity problems** define v3 (legacy compat, polish, documentation). Total: 23 + 64 + 33 + 10 = 130. Phases are sequential, but cross-cutting workstreams (security review, interop testing, documentation, performance) run continuously across all phases. Acknowledged uncertainty: the workshop decisions resolved the Tier-1 ORQs, but Tier-2 ORQs (per-capability) may shift Phase 2+ scope by ±2 months each. The replication decision (Decision 1) and KDC decision (Decision 5) are the highest-cascade items; their implementation schedule determines whether Phase 1 MVP ships in 6 months (optimistic) or 12 months (realistic).

The roadmap below supersedes [`draft/06-roadmap.md`](../draft/06-roadmap.md), which was written before the workshop and treated Tier-1 ORQs as open questions. With 12 workshop decisions and 130 ADRs locked, the roadmap is now ADR-driven: each phase lists the ADRs that must be implemented to declare the phase done, grouped by capability, with explicit done-criteria. The roadmap is the *schedule* for delivering the contract established by the catalog and ADRs; it is not the contract itself. Slippage on the roadmap is acceptable; slippage on the contract (shipping a phase without meeting its criteria) is not.

## Phase 1: MVP (6-12 months)

The MVP delivers the smallest subset that demonstrates end-to-end value: a Linux host can join the framework as a member, authenticate via Kerberos, apply policy, request a cert via ACME, mount an SMB share — against both a framework DC and a Windows Server 2022 DC in mixed mode. Federation, migration, and PKI templates are out of scope. The 23 blocker-class ADRs are grouped by capability below.

**Core Directory (5 blockers: ADR-002, ADR-073, ADR-076, ADR-074, ADR-070).** MVP delivers a FoundationDB-backed directory service (ADR-073) with LDAPv3 read/write over `ldap3` crate, hybrid replication via `DrSuapiReplicator` + `RaftReplicator` (ADR-070/ADR-071, `openraft` for native mode, fresh Rust DRSUAPI server in `adrian-drsuapi` for AD-interop), `member`/`memberOf` back-link as DSA-computed linkID pair (ADR-002), tombstones and Recycle Bin (ADR-074), and FSMO-role emulated or eliminated per mode (ADR-076: Schema Master via FDB OCC, Domain Naming Master via FDB atomic tx, PDC Emulator via Raft leader + chrony, RID Master via per-DC local counter, Infrastructure Master eliminated by identity mapping table per Decision 3). MVP does *not* deliver: schema extension tooling (Phase 3), Global Catalog (Phase 3), AD-integrated DNS (Phase 3), RODC (Phase 4). Estimated 24 person-weeks (per Decision 1 implementation impact).

**KDC (3 blockers: ADR-011, ADR-015, ADR-082).** MVP delivers the fresh Rust KDC (Decision 5, `crates/adrian-kdc` ~30K lines, 42 person-weeks full v1) in **preview mode**: AS-REQ/TGS-REQ path working, MS-KILE PAC generation per ADR-082 (9 PAC buffer types including `PAC_BUFFER_TICKET_CHECKSUM` silver-ticket mitigation), AES-only etype enforced per ADR-011 (no RC4 fallback), krbtgt HSM-bound with 2-key overlap per ADR-015 (`cryptoki` crate, 30-day auto-rotation), kpasswd per ADR-019. MVP does *not* deliver: PKINIT (Phase 3, ADR-084), FAST-required mode (Phase 3 — `fast_mode = "supported"` in MVP, `"required"` flip gated on PKINIT per ADR-012), S4U2Self/S4U2Proxy (Phase 3, ADR-087), cross-realm referral (Phase 3, ADR-013). MVP preview: AS-REQ throughput ≥5K req/sec per instance; PAC byte-identity validated against Windows Server 2022 in interop test suite (`adrian-kdc-interop` crate).

**Auth Provider (2 blockers: ADR-021, ADR-085/ADR-086).** MVP delivers LDAP signing + TLS channel binding + EPA mandatory (ADR-021, `rustls` for TLS), NTLM server-side dropped per ADR-085 (rejected with `strongAuthRequired (8)`), NTLM client-only `crates/adrian-ntlm-client` ~3K lines (NTLMv2 only, RFC 5929 channel binding, EPA EPHEMERAL flag, platform-secure-credential-store integration via `keyring` crate), and PtH defense per ADR-086 (HSM-bound PEK for AD-interop NT hashes, `Zeroizing<Vec<u8>>` via `zeroize` crate, platform isolation). MVP does *not* deliver: S4U2Self/S4U2Proxy (Phase 3, ADR-087), full audit event taxonomy (Phase 3, ADR-060), time sync hardening (Phase 3, ADR-022). Estimated 15 person-weeks total (per Decision 6 implementation impact).

**Policy Engine (2 blockers: ADR-029, ADR-094).** MVP delivers the hybrid declarative JSON policy format with ADMX compiler (ADR-090) and PReg adapter (ADR-029), per-platform policy executors (ADR-024: Windows CSE-equivalent, macOS MDM Configuration Profile, Linux `authselect` profile + `firewalld`/`nftables`), and git-backed SYSVOL replication (ADR-094) — SYSVOL is a git repository, replication is via git push/pull, not DFS-R. MVP does *not* deliver: full GPO Preferences (Phase 3, ADR-091/ADR-113), ADMX schema coverage (Phase 3), WMI filter replacement (Phase 3, ADR-026), policy rollback transactions (Phase 3, ADR-025). MVP coverage: ~60% of GPO categories that have direct Configuration Profile/authselect equivalents.

**Cert Service (1 blocker: ADR-095).** MVP delivers a basic CA exposing ACME endpoint (RFC 8555, ADR-095) using the `acme` crate, with cert enrollment from macOS and Linux clients via the Client SDK's ACME module. Windows clients use MS-WCCE during AD interop via a translation bridge (`adrian-mswcce-bridge`). MVP does *not* deliver: certificate templates (Phase 3, ADR-096), autoenrollment (Phase 3, ADR-097), key archival (Phase 4, ADR-032), OCSP (Phase 4, ADR-033/ADR-035), NDES/SCEP (Phase 4, ADR-098).

**File Gateway (3 blockers: ADR-043, ADR-046, ADR-105).** MVP delivers a fresh Rust SMB 3.1.1 server (ADR-105, `crates/adrian-smb-server` ~15K lines, pre-auth integrity + AES-GCM, per Decision 10), SMB1 refused (ADR-043), MS-RPRN dropped and IPP Everywhere adopted (ADR-046, PrintNightmare mitigation). MVP does *not* deliver: DFS-N (Phase 3, ADR-044), Continuously Available shares (Phase 3), Access-Based Enumeration (Phase 3, ADR-045), offline files (out of scope, ADR-047).

**Client SDK (1 blocker: ADR-107).** MVP delivers the unified Rust core SDK (`crates/adrian-sdk`, ADR-107) with C ABI binding (other bindings — JNI, Swift, Python, Go — in Phase 3), covering authentication (Kerberos via MIT krb5 standardised per ADR-049, NTLM client via ADR-085), directory query (LDAP via `ldap3` crate per ADR-109), policy application (compiles unified DSL to per-platform format), file/print client (SMB client `pavao` crate), and cert enrollment (ACME). ID mapping via UUID-primary with `uuid_to_uid(uuid) = (uuid_to_u64(uuid) % (2^31 - 65536)) + 65536` per ADR-110. MVP does *not* deliver: federation client (Phase 3), smart-card logon (Phase 3, ADR-084), Swift/Python/Go bindings (Phase 3), PSSO Extension integration (Phase 3, ADR-056).

**Cross-Platform Parity (1 blocker: ADR-113).** MVP delivers the unified policy authoring format (ADR-113 PolicyModule) with documented coverage map per platform, and `adrian-cli` (ADR-063) cross-platform CLI binary for Windows/macOS/Linux (amd64 + arm64). MVP does *not* deliver: macOS DDM support (Phase 5), legacy macOS agent compat (Phase 5, ADR-116), RODC (Phase 4), FreeIPA cross-forest trust (Phase 3, ADR-115).

**Security (3 blockers: ADR-064, ADR-122, ADR-065).** MVP delivers Kerberoasting mitigation (ADR-064: AES-only default, gMSA with HSM-bound KDS root key per ADR-020, detection rules), DCSync mitigation (ADR-122: native Raft mode eliminates `EXOP_REPL_SECRETS`; AD-interop per-call audit + HSM-bound break-glass), and golden ticket mitigation (ADR-065/ADR-015: HSM-bound krbtgt with 30-day auto-rotation and 2-key overlap). MVP does *not* deliver: silver ticket mitigation (Phase 3, ADR-123), sIDHistory abuse prevention (Phase 3, ADR-124/ADR-126), AdminSDHolder replacement (Phase 3, ADR-066), supply-chain hardening (Phase 3, ADR-067).

**Operations (0 blockers; MVP ships minimum-viable tooling).** MVP delivers: `adrian-cli` (ADR-063, fresh Rust static binary), structured JSON logging per ADR-060 (OpenTelemetry log format), basic Prometheus exporter per ADR-057 (per-DC sidecar `adrian-observability-sidecar`), and the `DomainController` CRD + `adrian-operator` (ADR-058) for Kubernetes deployment. MVP does *not* deliver: full observability suite (Phase 3), DR runbooks (Phase 4, ADR-059), multi-region (Phase 4, ADR-120), REST/gRPC API (Phase 3, ADR-061).

**Migration (0 blockers).** MVP does not deliver migration tooling. Migration is Phase 4 scope (ADR-126 through ADR-130).

**MVP delivery summary**: FoundationDB-backed directory service with LDAP + hybrid replication (Raft native + DRSUAPI AD-interop); fresh Rust KDC with AES-only + FAST + PAC in preview mode; NTLM client-only; basic policy engine with declarative JSON format + ADMX compiler; ACME-based cert service; fresh Rust SMB 3.1.1 server; unified Rust SDK core with C ABI binding; minimum-viable operational tooling (`adrian-cli`, OTel audit, Prometheus exporter, Kubernetes operator); security mitigations for the top 3 threats (Kerberoasting, DCSync, golden ticket). No federation, no migration, no PKI templates, no advanced policy, no advanced file features, no PKINIT, no S4U.

## Cross-cutting workstreams

Four workstreams run continuously across all phases. Each has a dedicated lead and a quarterly review cadence.

**Security review (continuous).** STRIDE threat model updates per release, mapped to the 8 security threats in [`catalog/11-security-threat-model.md`](../catalog/11-security-threat-model.md) (PC-116 through PC-123). Penetration testing per release, focused on the 3 blocker-class threats (Kerberoasting, DCSync, golden ticket) plus the high-severity threats (silver ticket, sIDHistory injection, NTLM relay). External security audit at MVP, v1, v2. The threat model is updated quarterly against new MITRE ATT&CK techniques (currently T1558 Steal-or-Forge-Kerberos-Tickets, T1003.002 Security Account Manager, T1558.003 Kerberoasting, T1558.004 Silver Ticket, T1550.001 Pass-the-Hash, T1178 sIDHistory).

**Interop testing (continuous).** Matrix of interop tests against Windows Server 2022, Windows Server 2025 (when released), Samba 4.x, MIT Kerberos 1.21+, Heimdal 7.x, FreeIPA 4.10+, Jamf Pro 11.10+. Tests cover: DRSUAPI replication (mixed framework-DC + Windows-DC topology), Kerberos cross-realm (framework realm + AD realm with byte-identical PAC validation), LDAP controls (per [`docs/02-protocols/02-ldap-protocol.md`](../docs/02-protocols/02-ldap-protocol.md)), SMB 3.1.1 (framework client + Windows server, framework server + Windows client), GPO interop (framework-emitted GPO consumed by Windows client), Configuration Profile interop (framework-emitted profile consumed by macOS PSSO). The `adrian-kdc-interop` crate runs in CI on every KDC PR; regressions block merge. Fuzzing via `cargo fuzz` targets for the AS-REQ, TGS-REQ, PAC, NTLMSSP, and SMB parsers — minimum 100M iterations nightly.

**Documentation (continuous).** Every feature ships with a KB file update in [`docs/`](../docs/). The docs directory grows with the framework's surface. Every PC in the catalog has a corresponding KB section explaining the framework's resolution. Every ORQ has a decision record in the ADR repository. Documentation is reviewed at MVP, v1, v2, v3 — missing or stale documentation blocks release. The `finaldraft/` directory is the canonical customer-facing architecture document set.

**Performance (continuous).** 1M-object directory benchmark suite, run nightly. Benchmarks: directory write throughput (target 10,000 writes/sec on a single DC via FoundationDB), replication latency (target <5s p99 for a write to reach all DCs in a 5-DC topology via `openraft`), KDC AS-REQ throughput (target 5,000 AS-REQ/sec per instance per Decision 5), LDAP search latency (target <50ms p99 for a subtree search returning 1,000 entries), SMB read throughput (target 10 Gbps on a single SMB 3.1.1 connection). Performance regressions block release.

## Risks and mitigations

Seven risks identified from the ADRs and workshop decisions. Each is a Phase 1+ slip risk requiring explicit mitigation.

**Risk 1: Fresh Rust KDC is the long pole on the v1 critical path (~9 months to preview, ~12 months to full v1).** The fresh Rust KDC (Decision 5, `crates/adrian-kdc` ~30K lines) is the single largest engineering investment in the framework. 3 engineers full-time for ~9 months produce the "KDC preview" (AS-REQ/TGS-REQ, PAC builder, AES-only, HSM binding, FAST `supported` mode); full v1 (S4U2Self/S4U2Proxy, PKINIT, MS-KILE corner cases, FAST `required` flip) requires ~3 more months. *Mitigation*: Phase 1 MVP ships with the KDC preview; full v1 lands in Phase 2. Customers requiring v1-MVP Kerberos must use MIT krb5 in parallel during the preview window. The interop test suite (`adrian-kdc-interop`) is a Phase 1 deliverable that gates the KDC preview's GA. Property-based PAC bijectivity tests (`proptest`) validate byte-identity against Windows Server 2022.

**Risk 2: FoundationDB 7.3+ operational maturity in enterprise deployments.** FoundationDB is Apple-scale and battle-tested at Apple, but enterprise adoption outside Apple/Snowflake is limited. Operators may push back on FDB vs more familiar stores (PostgreSQL, CockroachDB). *Mitigation*: the framework's `DirectoryStore` trait (ADR-073) abstracts the storage backend; FDB is the v1 implementation but a PostgreSQL or CockroachDB backend is feasible in v2 if operator demand warrants. The framework's FDB deployment is containerised (ADR-058) and managed by the `adrian-operator`, reducing operational burden. The framework publishes FDB operations runbooks and supports FDB's native backup/PITR (`backup_agent` + `fastrestore`). Spike 2 (workshop Decision 2) benchmarked FDB at 1M-object directory with 10K writes/sec — meeting Phase 1 targets.

**Risk 3: MS-KILE corner-case interop with Windows Server 2022.** S4U2Self/S4U2Proxy, compound identity, `PAC_REQUESTOR` (Server 2019+), `PAC_FULL_CHECKSUM` (Server 2016+), `PAC_BUFFER_TICKET_CHECKSUM` (Server 2012+) are documented only in MS-KILE and third-party reverse-engineering (Mimikatz, Rubeus, Impacket). The framework's fresh Rust KDC may have v1 gaps. *Mitigation*: the interop test suite (`adrian-kdc-interop`) catches gaps before GA; the test suite is itself a Phase 1 deliverable. The KDC's PAC builder is conservative — only emits documented PAC fields, Windows accepts conservative PACs. The framework monitors MS-KILE spec updates and ports changes within 30 days.

**Risk 4: macOS PSSO Extension may not support all framework features.** PSSO is macOS 13+ only and Apple-controlled. If Apple changes PSSO's payload schema in a future macOS release, the framework's macOS client SDK may break. *Mitigation*: maintain a Jamf Connect fallback for macOS 12 and below (ADR-048/ADR-116), and monitor Apple's PSSO release notes for breaking changes. The framework's macOS SDK degrades gracefully — PSSO if available, Jamf Connect if not, basic Kerberos via system Heimdal as last resort. The unified PAC validator (`libframework_pac_validator.dylib` per ADR-049/ADR-117) bypasses macOS system Heimdal's stale PAC parser.

**Risk 5: SSSD's GPO access control subset insufficient for production.** SSSD enforces only 5 of the ~40 User Rights Assignment entries. Operators who depend on full URA enforcement will find the framework's Linux client less restrictive than Windows. *Mitigation*: the framework's `adrian-sssd-gpo` Rust library (ADR-093/ADR-114) extends SSSD's `[Privilege Rights]` coverage to the full `Security` PolicyArea in v1. A `pam_access.so`-based fallback covers any URA SSSD cannot parse. The `authselect select adrian-with-sudo` profile (ADR-050) is the reference deployment.

**Risk 6: ACME-to-MS-WCCE bridge may break Windows autoenroll.** The framework's cert service exposes ACME for cross-platform native enrollment, with an MS-WCCE bridge for Windows AD CS interop (ADR-095). If the bridge has translation gaps (cert template attributes that don't map cleanly from ACME to MS-WCCE), Windows autoenroll may fail in mixed mode. *Mitigation*: the bridge is tested against a Windows Server 2022 AD CS in mixed mode as part of Phase 1 interop testing. Translation gaps are documented and Windows clients fall back to native MS-WCCE during migration. The framework's cert profile YAML (ADR-096) is the canonical format; MS-WCCE templates are a projection.

**Risk 7: ID mapping migration from PBIS/Winbind may break NFS/SMB permissions.** Operators migrating from PBIS or Winbind to the framework's UUID-primary ID mapping (ADR-110) will see UID changes for the same AD user (different algorithms, different ranges). This breaks NFS file ownership (UIDs in inode metadata) and SMB file ownership (SIDs in `nTSecurityDescriptor` translated to UIDs at the client). *Mitigation*: the framework's `adrian-cli migrate from-{sssd,winbind,pbis,dsconfigad}` migration tooling preserves existing UIDs by storing them as directory attributes (`uidNumber`/`gidNumber`) that override the UUID-derived algorithm. Where preservation is impossible, the migration tooling documents the file-ownership re-chown procedure and provides a `find -uid <old> -exec chown <new>` automation.

## Success criteria

Each phase has explicit "done" criteria. A phase is not complete until every criterion is met.

**Phase 1 (MVP) succeeds when**: a Linux host can join the framework as a member via `adrian-cli join` (or `realm join`-equivalent), authenticate via Kerberos (`kinit` succeeds, `klist` shows a TGT issued by the framework's Rust KDC with etype 0x12), apply policy via the framework's Client SDK policy module (declarative JSON compiles to `sssd.conf` and `authselect` profile fragments and is applied), request a cert via ACME (`adrian-cli cert request` succeeds and the cert is valid against the framework's CA), mount an SMB share (`mount -t cifs` succeeds against the framework's Rust SMB 3.1.1 server with pre-auth integrity negotiated), and all of this works against both a framework DC and a Windows Server 2022 DC in mixed mode (mixed-mode interop test passes for LDAP bind, Kerberos AS-REQ/TGS-REQ with PAC byte-identity, SMB 3.1.1 negotiation). Bonus criterion: a macOS 14 host can do the same with PSSO Extension as the auth surface. The KDC preview passes the `adrian-kdc-interop` test suite against MIT krb5 1.21+, Heimdal 7.x+, and Windows Server 2022+. All 23 blocker-class ADRs are implemented and their concrete specifications are testable.

**Phase 2 (v1) succeeds when**: all 64 high-severity ADRs are implemented (per the catalog's severity classification), the 1M-object directory benchmark suite passes nightly with the targets in §Cross-cutting workstreams, the external security audit finds no Critical or High findings, the interop test matrix passes against Windows Server 2022/2025, Samba 4.x, MIT Kerberos 1.21+, Heimdal 7.x, FreeIPA 4.10+, and Jamf Pro 11.10+, and at least 3 design-partner operators have completed a production pilot with 10,000+ users. The Keycloak-wrapped federation gateway is in production at 2+ design-partner sites. The `adrian-cli` is Generally Available on all 6 platform/arch combinations (Windows amd64/arm64, macOS amd64/arm64, Linux amd64/arm64). The framework publishes a 5-year support policy per major release.

**Phase 3 (v2) succeeds when**: all 33 medium-severity ADRs are implemented, the migration tooling supports AD-to-framework migration for a 100,000-user forest (verified via a design-partner migration with cutover and rollback drill), advanced federation (claims rules, custom attribute stores via Keycloak) is in production at 2+ design-partner sites, advanced PKI (key archival, OCSP scaling, NDES/SCEP bridge) is in production at 2+ design-partner sites, and the disaster recovery runbook is tested via a full DC-loss drill at 1+ design-partner site (RTO 10 minutes for single-DC restore per ADR-059).

**Phase 4 (v3) succeeds when**: all 10 low-severity ADRs are implemented, legacy compat (NTLM client for legacy services, FRS support if needed for migration, legacy macOS agents via ADR-116 migration tooling) is opt-in and documented, the framework's documentation is complete (every PC has a corresponding KB section, every Phase 1-3 feature has an operator runbook), and the framework is Generally Available with a published support policy (5-year support per major release, 1-year overlap between major releases).

These criteria are deliberately concrete and testable. A phase that meets its criteria ships; a phase that does not, does not. The catalog's 130 problems and 130 ADRs are the framework's contract with itself; the roadmap is the schedule for delivering that contract.

## Staffing plan

Phase 1 (MVP, 6-12 months) requires ~10-15 engineers. Key roles: 1 storage engineer (FoundationDB backend, `adrian-fdb-directory` crate, ADR-073); 3 KDC engineers (fresh Rust KDC, `crates/adrian-kdc` ~30K lines per Decision 5 — the long pole, 9 months to preview); 1 replication engineer (`adrian-drsuapi` + `adrian-raft` + hybrid Replicator trait, ADR-070/ADR-071); 1 SMB engineer (fresh Rust SMB 3.1.1 server, ADR-105, ~15K lines); 2 SDK engineers (unified Rust core + C ABI binding, ADR-107); 1 policy engineer (declarative JSON + ADMX compiler, ADR-090/ADR-029); 1 cert engineer (ACME endpoint + MS-WCCE bridge, ADR-095); 1 security engineer (Kerberoasting/DCSync/golden ticket mitigations, ADR-064/ADR-122/ADR-065); 1 operator engineer (`adrian-operator` + `adrian-cli` + OTel sidecar, ADR-058/ADR-063/ADR-057); 1 test engineer (interop test suite, `adrian-kdc-interop`, fuzzing, property-based tests). Total ~13 engineers for Phase 1.

Phase 2 (v1, 12-18 months) grows to ~25-30 engineers. Phase 1 team continues; additions: 1 federation engineer (Keycloak-wrapped gateway, ADR-100 through ADR-104); 2 more KDC engineers (PKINIT, S4U2Self/S4U2Proxy, FAST-required flip — ADR-084/ADR-087/ADR-012); 1 more SMB engineer (DFS-N, ABE — ADR-044/ADR-045); 2 more SDK engineers (Swift/Python/Go bindings, PSSO Extension integration, ADR-056/ADR-111/ADR-112); 1 more policy engineer (full GPP cross-platform, ADR-091/ADR-113); 1 more cert engineer (OCSP, key archival, autoenroll — ADR-032/ADR-033/ADR-097); 2 more security engineers (silver ticket, sIDHistory, AdminSDHolder, supply chain — ADR-123/ADR-124/ADR-066/ADR-067); 2 more operator engineers (REST/gRPC API, structured audit, multi-region prep — ADR-061/ADR-060/ADR-120); 1 migration engineer (start of Phase 2 — ADR-126 through ADR-130 scoping); 1 documentation engineer (KB files, operator runbooks); 1 devops/SRE engineer (CI/CD, Sigstore signing, reproducible builds — ADR-067). Total ~28 engineers for Phase 2.

Phase 3 (v2) and Phase 4 (v3) sustain ~25-30 engineers with role shifts toward migration, advanced features, and documentation. The framework's open-source posture means community contributions supplement the core team in Phase 3+. The workshop decisions and ADRs provide the architectural contract; the staffing plan provides the execution capacity. Slippage on either dimension compounds; both are tracked monthly against the roadmap.
