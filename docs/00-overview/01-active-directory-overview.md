# Active Directory — What It Supplies

Active Directory is **a directory service, an authentication broker, a configuration distribution system, a PKI, a federation platform, and a file-services dependency**, all built on a shared **DIT + Kerberos + DNS + SMB + RPC** substrate. The five server roles share schema, naming, and replication but solve different problems. This file enumerates what each role supplies at the implementation level; subsequent files in `01-ad-core/` drill into each.

## The five server roles

| Role | Service binary | Listening ports | What it supplies |
|------|----------------|------------------|------------------|
| **AD DS** | `ntds.exe` (driver), `lsass.exe` (KDC, Netlogon, DSA) | TCP 389/636 (LDAP/LDAPS), 3268/3269 (GC), 88/464 (Kerberos), 135 (RPC-EPM), 49152-65535 (RPC), 53 (DNS), 445 (SMB/DRSR/SAMR) | Identity, auth, directory, replication, GPO distribution |
| **AD LDS** | `instance.exe` (per-instance) | Same as AD DS minus DNS, Netlogon | AD schema + LDAP for apps without domain-join requirements |
| **AD CS** | `certsvc.exe` | TCP 80/443 (HTTP enrollment), 135 + dynamic RPC (ICertPassage RPC), 445 (template publish) | X.509 PKI: CA, issuance, revocation, autoenroll |
| **AD FS** | `Microsoft.IdentityServer.ServiceHost.exe` | TCP 443 (HTTPS), 49152-65535 (WCF/SAML internal) | Federation, SSO, SAML/OIDC/WS-Fed endpoints |
| **AD RMS** | `rmssvc.exe` (Licensing + Account Cert) | TCP 443 (HTTPS activation/licensing), 80 (CRL fallback) | Information Rights Management; use-license issuance |

Plus the **transport roles** that AD depends on but are not AD themselves: **DNS Server** (`dns.exe`), **DHCP Server** (`tcpsvcs.exe` DHCP), **W32Time** (`w32time.dll` running under `svchost`).

## What AD DS specifically supplies

1. **A coherent, replicated, multi-master DIT.** Every DC owns a writable copy of its own Domain NC; read-only copies of the Configuration and Schema NCs; and optionally an Application NC (DNS, etc.). The DIT is stored as `C:\Windows\NTDS\ntds.dit` (a 16 KB-page ESE database) and is opened exclusively by `lsass.exe` via `esent.dll`. Replication is pull-based using DRSUAPI over DCE/RPC, typically over TCP dynamic ports but configurable to a single static port via `HKLM\SYSTEM\CurrentControlSet\Services\NTDS\Parameters\TCP/IP Port`.

2. **Kerberos-based authentication** for principals stored in the DIT. The KDC runs as part of LSASS (`kdcsvc.dll`) on every DC. Initial AS exchange can be encrypted with RC4-HMAC (`0x17`), AES-128 (`0x11`), or AES-256 (`0x12`); MS-KILE deprecates RC4 but it remains the default for backwards compat unless `network security: Configure encryption types allowed for Kerberos` policy forbids it.

3. **A central authorization store** via the `tokenGroupsGlobalAndUniversal` and `memberOf` attributes, and the SID-based PAC inside every Kerberos ticket. The PAC is signed with the KDC long-term key (krbtgt account, RC4 or AES per etype) and may be verified by member servers via `KerbVerifyPacMessage` IPC to LSASS.

4. **Group Policy distribution.** GPOs are split between the AD-side **GPC** (the `groupPolicyContainer` object under `CN=Policies,CN=System,DC=...`) and the SYSVOL-side **GPT** (`\\<domain>\SYSVOL\<domain>\Policies\{GUID}\`). Clients pull both halves; the GPC tells the client which CSE GUIDs to invoke and provides the version number; the GPT provides the actual policy payload. See [`../04-group-policy/01-gpo-architecture.md`](../04-group-policy/01-gpo-architecture.md).

5. **DNS as the locator substrate.** AD uses DNS exclusively for service discovery. Domain-joined clients resolve `_ldap._tcp.dc._msdcs.<domain>` SRV records to find a DC; the DC Locator in `netlogon.dll` caches the result in `DSGETDCW`-style cache. AD-integrated DNS zones are stored in the `DomainDnsZones` and `ForestDnsZones` application partitions and replicate using the same DRSR pipeline as the Domain NC. See [`../02-protocols/05-dns-dynamic-updates.md`](../02-protocols/05-dns-dynamic-updates.md).

6. **Replication topology that self-heals.** The KCC process runs in LSASS on every DC every 15 minutes (by default; configurable via `HKLM\SYSTEM\CurrentControlSet\Services\NTDS\Parameters\Repl topology update period (secs)`) and recomputes a least-cost spanning tree using site-link costs. Inter-site topology is generated by the **ISTG** (Inter-Site Topology Generator), the DC holding the role in each site.

7. **A consistent security model.** SIDs in `S-1-5-21-<domain>-<rid>` form. Default well-known SIDs (`S-1-5-32-544` = Administrators, `S-1-5-32-545` = Users, etc.) are local; domain SIDs are allocated at dcpromo time. Cross-domain group membership is handled by the GC and the `tokenGroupsGlobalAndUniversal` computed attribute.

8. **PKI hook points.** AD CS publishes CA certificates, CRLs, and templates into AD objects under `CN=Public Key Services,CN=Services,CN=Configuration,DC=...`. Autoenrollment reads the `pKICertificateTemplate` objects from there via LDAP.

9. **Federation hooks.** AD FS reads token-signing certificates and claims-provider trusts from its own SQL/WID config DB, not from AD directly; but it uses AD DS as the default claims provider via the "Active Directory" claim provider trust, calling LSASS for authentication via `LsaLogonUser` and using the KDC for Kerberos SSO when the client is domain-joined.

10. **File and print infrastructure dependencies.** SYSVOL is replicated by DFS-R (`dfsr.exe`) using the `CN=SYSVOL Subscription,CN=Domain System Volume,CN=DFSR-LocalConfig,...` AD object. Print services publish printers as `printQueue` objects in AD.

## What AD LDS supplies

- The same LDAP, schema, and replication engine as AD DS, but **without**:
  - Kerberos KDC (no krbtgt account, no AS-REQ handling).
  - NTLM domain controller functionality (no Netlogon secure channel).
  - GPO processing (no Group Policy Client service expected).
  - Computer accounts (a server can host AD LDS without being domain-joined, though typically it is).
- Runs as one or more **named instances** under `NTDS\$InstanceName` service. Each instance has its own `adamntds.dit`, schema, and ports. Multiple instances on one host share `adamsetup.exe` binaries but nothing else.
- Use cases: Active Directory Lightweight for apps that need a directory (SharePoint User Profile Service, half of the System Center family, certificate enrollment web services policy modules, etc.).

## What AD CS supplies

- An X.509v3 Certificate Authority implementation. Two flavours:
  - **Enterprise CA** — AD-integrated; reads templates from AD, supports autoenrollment, can issue certs based on AD account attributes.
  - **Standalone CA** — no AD dependency; operator approves every request; subject name is supplied by the requester.
- A **CA database** (jet-based, `%SystemRoot%\System32\CertLog\*.edb`) of every issued certificate plus request logs.
- **Policy modules** (`certpmod.dll`) decide whether a request satisfies template ACLs and constraints.
- **Exit modules** (`certxmod.dll`) run after issuance, e.g. to publish the cert to AD (`userCertificate` attribute) or to a CRL.
- HTTP enrollment endpoints via `CES` (Certificate Enrollment Service) and `CEP` (Certificate Enrollment Policy), implementing MS-WCCE and MS-XCEP SOAP over HTTPS.
- NDES (`SCEP.exe` service) for router/switch SCEP enrollment.

## What AD FS supplies

- A claims-based identity provider. Three relying-party-facing protocol families: **SAML 2.0** (passive profile, SP-initiated and IdP-initiated), **WS-Federation** (passive, legacy), **OAuth2/OIDC** (added in ADFS 2016).
- A **trust pipeline** with three stages: **Claims Provider Trust** (incoming claims from upstream IdP) → **Acceptance Transform Rules** (normalize incoming) → **Issuance Transform Rules** (map to relying-party claims).
- A **farm topology** with a shared config DB stored in either SQL Server or the internal WID (`%SystemRoot%\Windows\WID\Data\microsoft.identityserver.mdf`). Primary node writes; secondaries are read-only and sync every 5 minutes.
- A reverse proxy edge: **WAP** (Web Application Proxy, `WAPService.exe` under `svchost -k WAPServiceSvchost`). WAP pre-auths incoming requests using ADFS via MS-ADFSPIP protocol.

## What AD RMS supplies

- An IRM (Information Rights Management) service. Two roles:
  - **Root cluster** — issues **CLCs** (Client Licensor Certificates) and **RACs** (Rights Account Certificates) to users.
  - **Licensing-only cluster** — issues **Use Licenses** for protected content.
- Content is encrypted with a symmetric AES key (128 or 256, config-dependent); the symmetric key is itself encrypted with the **server licensor certificate** public key and embedded in the **Issuance License** (`IL`). The IL travels with the content.
- A user opening content presents their RAC and the IL to the licensing cluster; the cluster issues a **Use License** containing the AES key encrypted to the user's RAC public key.
- AD RMS clients are built into Office, Windows (RMS sharing app / AIP client), and Outlook; Microsoft exposes the SDK as MS-DRM and MS-RM.

A detailed per-feature map lives at [`../10-comparison-matrices/01-feature-os-matrix.md`](../10-comparison-matrices/01-feature-os-matrix.md). The headline view:

| AD supplies | macOS equivalent | Linux equivalent |
|-------------|------------------|------------------|
| LDAP directory | OpenDirectory / `opendirectoryd` | OpenLDAP / `slapd` |
| Kerberos KDC | Apple Heimdal KDC (`/usr/sbin/kdc`) bundled; rarely used as DC | MIT krb5 KDC / Heimdal KDC |
| Kerberos client | Heimdal client (`/usr/bin/kinit`) | MIT krb5 client (`/usr/bin/kinit`) |
| AD DS member client | OpenDirectory AD plug-in (`dsconfigad`) | SSSD `ad` provider / Winbind |
| GPO distribution | mcx (legacy) / Configuration Profiles (modern) | SSSD GPO access control (subset) |
| File shares (SMB) | Samba bundled (`/usr/sbin/smbd`) | Samba `smbd/nmbd` |
| PKI / CA | Apple Configurator + MDM for cert push | Dogtag / OpenSSL CA / FreeIPA CA |
| Federation client | Platform SSO Extension / Jamf Connect | SSSD with Kerberos + keytab; no native SAML client |

## Threat-model notes

- **Kerberoasting** — any domain user can request a TGS for any SPN; the TGS is encrypted with the service account's long-term key. RC4-HMAC TGS is offline-brute-forceable. Mitigation: gMSA + AES-only etypes, or disable RC4 via domain policy.
- **AS-REP roasting** — accounts with `DO_NOT_REQUIRE_PREAUTH` flag set in `userAccountControl` allow an attacker to obtain an AS-REP encrypted with the user's key, brute-forceable offline. Audit with `Get-ADUser -Filter {DoesNotRequirePreAuth -eq $true}`.
- **DCSync** — any principal with `DS-Replication-Get-Changes` + `DS-Replication-Get-Changes-All` on the domain NC can issue `DRSGetNCChanges` and pull the password hashes. Members of `Domain Admins`, `Enterprise Admins`, and explicit grantees only. Audit with `Get-ADObject -Filter * -SearchBase "DC=domain,DC=tld" -Properties nTSecurityDescriptor | ...` looking for non-default grantees on `DC=domain,DC=tld`.
- **Golden ticket** — attacker who has the `krbtgt` hash can forge TGTs. Detection: monitor for TGS-REQs whose TGT was issued by a non-current krbtgt (` krbtgt` password rotation invalidates old tickets).
- **Silver ticket** — attacker with a service account's hash forges TGS for that service. Detection requires service-side ticket anomaly detection.
- **PrintNightmare** — MS-RPRN `RpcAddPrinterDriverEx` allows SYSTEM code execution by any `PrintOp` member. Patched in CVE-2021-34527; further hardening: `RestrictDriverInstallationToAdministrators` registry key.
