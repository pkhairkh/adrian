# Cross-Platform Parity Analysis

## The parity problem

Active Directory is Windows-only. Every protocol, every binary, every operational assumption is Windows-shaped: LSASS holds the KDC; `ntdsa.dll` is the DSA; ESE/JET Blue is the database; SSPI is the auth surface; Wldap32 is the LDAP client; NetAPI is the join/share surface; Group Policy Client (`gpsvc.dll`) is the policy engine; AD CS (`certsvc.exe`) is the PKI; AD FS (`Microsoft.IdentityServer.dll` in IIS) is the federation gateway; SMB server is `srv2.sys`; DFS is `dfsr.exe`; the print spooler is `spoolsv.exe`. None of these binaries exist on macOS or Linux. The framework inherits none of this. If the framework is to be a credible cross-platform successor, it must reproduce the *semantics* on three platforms while picking a fresh implementation stack for each one.

Parity means two things. First, **runtime parity**: a framework DC running on Linux must be a wire-compatible peer of a Windows Server DC running AD DS — same LDAP controls, same Kerberos etypes, same DRSUAPI replication, same SMB dialects, same DRSUAPI `DRSBind`/`DRSGetNCChanges` opnums, same `MS-ADTS` schema semantics, same `MS-KILE` PAC structure. Second, **client parity**: a Windows client, a macOS client, and a Linux client must all join the same framework domain, authenticate the same user, apply the same policy, mount the same shares, request the same certs, and federate to the same RPs — without platform-specific divergence in behavior. Runtime parity is the protocol question; client parity is the SDK question. Both are cataloged as problems PC-094 through PC-105 in [`catalog/09-cross-platform-parity.md`](../catalog/09-cross-platform-parity.md), and the per-platform impact of every one of the 130 problems is enumerated in [`catalog/14-cross-platform-parity-matrix.md`](../catalog/14-cross-platform-parity-matrix.md).

The matrix is unambiguous about scope. **117 of 130 problems affect Windows**, **118 affect macOS**, **118 affect Linux**, and **114 affect cross-platform consistency** (the framework must produce identical semantics regardless of which platform hosts the DC or client). Six problems are Windows-only (PC-006 schema cache reload, PC-025 PAC validation RPC, PC-049 WMI filters, PC-050 slow-link detection, PC-107 schema upgrades, PC-113 functional level upgrades) — these are intrinsic to the Windows implementation and need not be reproduced. Six problems are macOS-only (PC-086 PSSO Extension, PC-087 Jamf Connect ROPG, PC-096 DDM, PC-100 OpenDirectory AD plug-in gaps, PC-104 legacy third-party agents, PC-105 Heimdal fork). Four are Linux-only (PC-088 SSSD GPO subset, PC-092 PAM distro variance, PC-099 three-stack migration, PC-103 roll-your-own OpenLDAP). Five are partial-coverage (△): PC-057 (AD CS is Windows-only; macOS has no native CA), PC-080 (DFS-N/DFS-R), PC-089 (SID↔UID mapping), PC-090 (Heimdal vs MIT), PC-094 (NTLM on macOS/Linux). The partial-coverage set is the highest-leverage parity gap — each forces the framework to design a cross-platform primitive that does not exist today in any single platform.

The 21 blocker-severity problems are uniformly cross-platform. Every one of them — from PC-001 (DRSUAPI replication) to PC-118 (golden ticket) — applies to all three platforms plus the cross-platform consistency column. This is not a coincidence: blocker-class problems are architectural, and architectural decisions cascade across every platform. There is no "Windows-only blocker" in the catalog.

## Windows as the reference platform

Windows is the reference platform because Windows *is* AD. The framework's wire compatibility target is a Windows Server 2022/2025 DC, and the framework's client compatibility target is a Windows 10/11 client joined to a Windows AD domain. Every protocol the framework speaks must be byte-compatible with a Windows peer. Approximately 117 of the 130 problems — including all Core Directory (PC-001 through PC-022), KDC (PC-023 through PC-035), Auth Provider (PC-036 through PC-042), Policy Engine (PC-043 through PC-056), Cert Service (PC-057 through PC-067), Federation Gateway (PC-068 through PC-077), File Gateway (PC-078 through PC-084), Client SDK (PC-085 through PC-093), Operations (PC-106 through PC-115), Security (PC-116 through PC-123), and Migration (PC-124 through PC-130) problems — apply to Windows. The framework's Windows implementation is the floor against which macOS and Linux parity is measured.

The Windows reference surface includes the seven native primitives the framework must reproduce as abstracted APIs: (1) **SSPI** (`secur32.dll` — `InitializeSecurityContext`/`AcceptSecurityContext`/`EncryptMessage`) for authentication; (2) **Wldap32** (`wldap32.dll` — `ldap_bind_s`/`ldap_search_ext_s`) for LDAP directory access; (3) **NetAPI** (`netapi32.dll` — `NetJoinDomain`/`NetShareEnum`) for join and share enumeration; (4) **Group Policy Client** (`gpsvc.dll`) for policy application; (5) **AD CS client** (`certcli.dll` + `certreq.exe` driving MS-WCCE/MS-XCEP/MS-WSTEP) for cert enrollment; (6) **AD FS WAP** (`Microsoft.IdentityServer.WebApplicationProxy` in IIS) for reverse-proxy federation; (7) **native SMB client** (`mrxsmb.sys`) plus **Kerberos CNG** (`ksecdd.sys` driving the LSA's Kerberos SSP) for file access and ticket management. None of these are cross-platform — the framework's client SDK (PC-085) must wrap all seven on Windows and provide equivalents on macOS and Linux.

The framework's Windows implementation must also address the six Windows-only problems (PC-006, PC-025, PC-049, PC-050, PC-107, PC-113). These are inherent to AD's Windows-shaped implementation and need not be reproduced *on macOS or Linux*, but they shape what the framework's Windows DC implementation must do if it is to be a drop-in replacement for AD on Windows. PC-006 (schema cache reload lock) is a real performance problem during schema upgrades; PC-025 (PAC validation RPC) is a real protocol surface (`NetrLogonSamLogonEx` opnum 45 in MS-NRPC); PC-049 (WMI filters) and PC-050 (slow-link detection via ICMP to PDC) are real client behaviors; PC-107 (schema `objectVersion` is irreversible) and PC-113 (functional level upgrades are one-way) are real operations constraints. The framework can pick fresh designs that avoid each, but it must document the migration impact.

## macOS parity gaps

macOS is the platform with the largest *unmanaged* parity surface. Apple ships a partial directory integration stack — OpenDirectory (`opendirectoryd`) with Heimdal Kerberos, plus the Authorization framework — but it is not a domain controller (macOS hosts always join, never serve) and it has no native NTLM, no native GPO engine, no native AD CS client, and no native ADFS-equivalent WAP. The gaps are cataloged as PC-094 through PC-105 in [`catalog/09-cross-platform-parity.md`](../catalog/09-cross-platform-parity.md). The framework's macOS implementation must close each.

**No native NTLM client.** macOS has zero NTLMSSP support in the kernel or in user space. SMBX will fall back to guest or refuse the connection if NTLM is the only option; legacy applications that hard-require NTLM (old SQL Server drivers, old IIS-integrated apps) simply fail. The framework must either bundle Samba winbind as an NTLM provider (heavyweight; brings Samba's `winbindd` daemon and `libnss_winbind.so.2` NSS shim) or implement a fresh NTLMSSP module in the client SDK. The PC-094 recommendation is to drop NTLM by default (see PC-036) and maintain a hardened opt-in NTLMSSP module only for migration scenarios — this avoids shipping winbind to every macOS client. See [`docs/02-protocols/04-ntlm-internals.md`](../docs/02-protocols/04-ntlm-internals.md) for the NTLMSSP wire format and [`docs/08-macos-equivalents/07-third-party-agents-mac.md`](../docs/08-macos-equivalents/07-third-party-agents-mac.md) for the third-party NTLM provider history (Centrify DirectControl, Admit, BeyondTrust PBIS).

**No native GPO Preferences equivalent.** macOS Configuration Profiles cover approximately 60% of GPO categories — password policy, account lockout, restricted groups (admin list), firewall, AirPrint, NTP, screensaver, application restrictions — but they do not cover GPO Preferences (drive maps, file copy, registry mods, scheduled tasks, folder redirection, environment variables, local users and groups, printers). The PC-095 gap is the blocker: there is no unified policy authoring format that compiles to Windows GPO, macOS Configuration Profile, and Linux SSSD-conf. The framework must either build a unified policy DSL that compiles to all three native formats, or accept that the macOS surface is permanently smaller. The recommendation in [`docs/10-comparison-matrices/05-gpo-equivalents-matrix.md`](../docs/10-comparison-matrices/05-gpo-equivalents-matrix.md) is to adopt the unified DSL approach and document the coverage map explicitly.

**OpenDirectory is not a DC.** macOS hosts always join a directory, never serve one. `opendirectoryd` runs locally and proxies to a real DC (AD or OpenLDAP). The framework's macOS implementation is therefore a client-only target — no macOS DCs. This is a parity constraint the framework must document and not fight: any operator asking "can I run a DC on macOS?" must be told "no, run it on Linux or Windows." See PC-100 for OpenDirectory's specific gaps (no GPO, no ABE, no full DFS-N).

**PSSO Extension is macOS 13+ only.** Apple's Platform SSO Extension (`com.apple.applesso` Authentication_SSO endpoint security extension) is the modern SSO surface, replacing Enterprise Connect and NoMAD — but it requires macOS 13 Ventura or later. Older macOS fleets (Monterey, Big Sur, Catalina) need Jamf Connect (PC-087) or NoMAD (PC-104, EOL after Jamf's 2021 acquisition of Orchard & Grove). The framework must support both PSSO (new macOS) and a fallback path for older macOS — or it must declare macOS 13 as the floor. The recommendation is to declare macOS 13 as the floor and document the migration path for older fleets via Jamf Connect's ROPG password sync (PC-087) during the transition window. See [`docs/08-macos-equivalents/04-platform-sso-extension.md`](../docs/08-macos-equivalents/04-platform-sso-extension.md) and [`docs/08-macos-equivalents/05-kerberos-sso-extension.md`](../docs/08-macos-equivalents/05-kerberos-sso-extension.md).

**Three EOL third-party agents.** NoMAD, Enterprise Connect, and AdmitMac are all end-of-life. NoMAD was EOL'd after Jamf acquired Orchard & Grove in May 2021. Enterprise Connect was deprecated in macOS 10.15 alongside the Kerberos SSO Extension introduction. AdmitMac (Centrify's macOS AD integration product) was retired in favor of DirectControl, which is itself being phased out. Any operator still running these agents is on borrowed time. The framework must not depend on them and must provide a documented migration path off them. PC-104 catalogues the legacy landscape; PC-086 documents PSSO as the replacement.

**Apple's Heimdal fork is stale.** Apple ships a Heimdal Kerberos fork in `/usr/lib/libkerberos.dylib` that has not tracked upstream Heimdal since approximately 2014. Known gaps: PAC_FULL_CHECKSUM (Server 2016+), claims-based Kerberos (compound identity), and partial FAST armoring behavior. This affects every macOS client that uses the system Heimdal, including the PSSO Extension. PC-105 catalogues the fork staleness. The framework's macOS client SDK must either bundle a current Heimdal or MIT krb5 build (overriding the system library via `DYLD_LIBRARY_PATH` or a framework-embedded copy) or accept the system fork's limitations. The recommendation is to bundle MIT krb5 inside the SDK and document the override — this also resolves PC-090 (Heimdal vs MIT) on macOS by making the framework's choice explicit.

**mcx legacy still required.** macOS's legacy MCX (Managed Client for OS X) preference management — deprecated since 10.7 Lion — is still required for some preference management scenarios that Configuration Profiles do not cover (Folder Redirection via `MCXRedirector`, some per-app preferences). The framework's policy engine must either reproduce MCX or accept the gap. Reproducing MCX means writing to OpenDirectory's local node (`/Local/Default`) with `com.apple.MCX` payloads; this is fragile and Apple-unsupported. The recommendation is to accept the gap and document it.

**Disk encryption recovery key escrow is MDM-only.** macOS FileVault recovery keys escrow to Apple or to an MDM server (Jamf, Intune) — never to AD. PC-097 catalogues this gap. The framework's directory cannot be the recovery-key escrow target on macOS without an MDM intermediary. The recommendation is to adopt a per-computer `msFVE-RecoveryInformation`-equivalent attribute in the framework directory (matching the Windows BitLocker model from PC-097) and provide an MDM-side plugin (Jamf Extension, Intune custom compliance script) that writes the FileVault recovery key to that attribute. This gives operators a unified recovery-key retrieval surface across Windows, macOS, and (with LUKS + Clevis/Tang) Linux.

**Print queue deployment is MDM-only.** macOS print queue deployment uses the `com.apple.mobileconfig.airprint` payload (AirPrint only) or `lpadmin` via a `scripts` MDM payload. There is no Group Policy Preferences equivalent for printer deployment. PC-045 catalogues the GPO Preferences gap; PC-095 catalogues the unified policy gap. The framework's policy engine must compile "deploy printer" intent to either an AirPrint profile (AirPrint-capable printers) or a `scripts` payload invoking `lpadmin` (raw SMB/IP printers). The framework's policy DSL must model both paths.

**LAPS equivalent only on macOS 14+.** Apple introduced Platform SSO device password rotation in macOS 14 Sonoma — a LAPS-equivalent for the local admin password synced to the framework directory via PSSO. Older macOS (13 and below) has no native LAPS equivalent. The framework must support macOS 14+ native rotation as the preferred path and fall back to Jamf Connect's local admin password rotation for macOS 13. PC-098 catalogues the LAPS gap. See [`docs/08-macos-equivalents/04-platform-sso-extension.md`](../docs/08-macos-equivalents/04-platform-sso-extension.md) for the PSSO device password rotation payload.

## Linux parity gaps

Linux is the platform with the most fragmentation. Three competing AD integration stacks — SSSD, Winbind, and PBIS — each provide a different subset of AD functionality with different trade-offs. SSSD is the modern default (`sssd-ad` provider with `realmd`/`adcli` join); Winbind is the Samba-bundled option (`winbindd` with `idmap_rid`); PBIS (BeyondTrust PowerBroker Identity Services, formerly Likewise Open) is commercial-EOL — last release 2014, deprecated 2023, still deployed but no updates. PC-099 catalogues the three-stack migration pain. The framework must pick one as the baseline (recommendation: SSSD) and document the migration path from the other two.

**Three competing AD integration stacks.** Each stack makes different choices. SSSD: MIT krb5, `KEYRING:persistent:<uid>` ticket cache, GPO access control subset (only the `[Privilege Rights]` logon rights — 5 URA: SeInteractiveLogonRight, SeRemoteInteractiveLogonRight, SeNetworkLogonRight, SeBatchLogonRight, SeServiceLogonRight), algorithmic ID mapping (`sss_idmap.c:gen_slice` slice algorithm). Winbind: Heimdal (Samba's build choice), `/var/cache/samba/krb5cc_<uid>` ticket cache, no GPO consumption, `idmap_rid` RID-based mapping. PBIS: MIT krb5 with custom patches, `FILE:/tmp/krb5cc_<uid>` cache, GPO engine for Linux (the only one), PBIS-own ID mapping algorithm. Migration between them requires UID remap planning because the three ID mapping algorithms produce different UIDs for the same SID. The framework's client SDK (PC-085) must hide this by adopting one algorithm and providing a migration tool for the other two.

**SSSD's GPO access control only parses `[Privilege Rights]`.** SSSD reads only the `[Privilege Rights]` section of `GptTmpl.inf` (the Security CSE) — 5 user rights, not Registry.pol, not GP Preferences, not User Configuration, not Scripts, not Folder Redirection, not Drive Maps, not Printers, not Scheduled Tasks, not Environment, not Local Users and Groups, not any of the ~40 other CSEs in the Windows GPO model. PC-053 catalogues this gap. The framework's policy engine on Linux must extend SSSD's GPO parser to cover the full CSE surface, or write a fresh policy application layer that does not depend on SSSD's GPO access control. The recommendation is the latter — write a fresh policy application layer in the client SDK, and use SSSD's GPO access control only for logon-rights enforcement as a defense-in-depth measure. See [`docs/09-linux-equivalents/03-sssd-gpo-access.md`](../docs/09-linux-equivalents/03-sssd-gpo-access.md) for SSSD's parser internals.

**No native AD CS client.** Linux has no native MS-WCCE/MS-XCEP/MS-WSTEP client. Certmonger (`certmonger` daemon with `getcert` CLI) supports SCEP and the IPA-CA (Dogtag) protocol, but not MS-WCCE directly. SSSD's `certmap` plugin maps certs to users but does not enroll. PC-057 catalogues the AD CS gap; PC-059 catalogues the autoenrollment gap. The framework's Linux client SDK must either bundle a MS-WCCE client (the Samba team has partial code; the FreeIPA team has none) or adopt ACME as the cross-platform enrollment protocol and maintain a Windows-side shim that translates ACME to MS-WCCE for AD interop. The recommendation is ACME as the framework-native protocol with an MS-WCCE bridge for AD CS interop during migration.

**No native ADFS WAP equivalent.** Linux has no native reverse-proxy federation gateway. The framework must compose one from existing components: nginx + oauth2-proxy for OIDC, Envoy + ext-authz for pluggable auth, or mod_auth_mellon for SAML. PC-073 catalogues the WAP gap. The framework's federation gateway must ship a reference deployment of one of these stacks and document the trade-offs. The recommendation is Envoy + ext-authz (modern, pluggable, observable) with an nginx + oauth2-proxy fallback for operators who prefer the simpler stack. See [`catalog/06-federation-gateway.md`](../catalog/06-federation-gateway.md) for the full WAP replacement analysis.

**FreeIPA is a separate platform, not a peer DC.** FreeIPA (Linux IdM with 389-DS + MIT krb5 + Dogtag CA + SSSD client) is a Linux-native identity platform that integrates with AD via a one-way cross-forest trust. FreeIPA is not a peer DC to AD — it cannot hold a domain NC, cannot replicate via DRSUAPI, cannot serve as a global catalog peer. PC-101 catalogues this gap. The framework must decide: build a native Linux DC (the recommendation; the framework's Core Directory implementation runs natively on Linux) or adopt FreeIPA as the Linux identity tier and use the framework only as a federation/coordination layer above FreeIPA. The recommendation is the former — the framework's Core Directory must be a native Linux DC, not a wrapper around FreeIPA. FreeIPA remains a migration source, not a deployment target.

**PBIS is commercial-EOL.** BeyondTrust PBIS Open's last release was 2014; BeyondTrust deprecated it in 2023. PBIS is still deployed in production at many sites (it was the only Linux stack with a real GPO engine), but it receives no updates and has known security gaps (PC-099). The framework must provide a documented migration path off PBIS to the framework's own client SDK. This is a migration concern (PC-124 through PC-130) more than a parity concern, but it shapes the parity recommendation: the framework's Linux client SDK must be at feature parity with PBIS on the GPO engine, because PBIS-to-framework migration is the highest-volume migration path.

**No native smart-card logon equivalent.** Windows smart-card logon uses the CryptoAPI + `scardsvr.dll` + the Kerberos PKINIT SSP, all native. Linux smart-card logon requires manual configuration of `pcscd` (PCSClite smart-card daemon), `pam_pkcs11` (PAM module for smart-card auth), `krb5` PKINIT configuration in `/etc/krb5.conf` `[libdefaults] pkinit_anchors = FILE:...`, and `opensc` (OpenSC smart-card framework). There is no single `pkinit --enable` switch. PC-027 catalogues the PKINIT gap. The framework's Linux client SDK must bundle a pkinit configuration helper and document the smart-card flow end-to-end. See [`docs/02-protocols/01-kerberos-internals.md`](../docs/02-protocols/01-kerberos-internals.md) for PKINIT wire details.

**Heimdal vs MIT Kerberos choice affects PKINIT and FAST behavior.** Linux distributions ship either MIT krb5 (Red Hat, Debian, Ubuntu default) or Heimdal (SUSE tradition, embedded in Samba). The two implementations differ subtly in PKINIT (Heimdal supports PKINIT RFC 4556 but with different `pkinit_id` syntax), FAST (RFC 6806 — both support but with different armor-key derivation), and anonymous PKINIT (different `anon_reply` semantics). PC-090 catalogues the divergence. The framework's Linux client SDK must standardize on one — the recommendation is MIT krb5 (the more widely deployed default) — and bundle it inside the SDK to override any distro Heimdal. PC-105 is the macOS analog (Apple's Heimdal fork); the framework's macOS SDK must also bundle MIT krb5 to ensure consistent behavior across the two UNIX platforms.

**ID mapping is non-deterministic across stacks.** SSSD uses algorithmic slice mapping (`sss_idmap.c:gen_slice` — domain SID + RID → UID via slice ranges). Winbind uses `idmap_rid` (SID + RID → UID via single linear range). PBIS uses its own algorithm (also linear range, different default range). The three produce different UIDs for the same AD user on different hosts unless the operator pins the same algorithm and the same range on every host. PC-089 catalogues this as a blocker. The framework's client SDK must standardize on one algorithm — the recommendation is SSSD's slice algorithm (the modern default, with the broadest deployment) — and provide a migration tool that reads existing `idmap` configs (Samba, PBIS) and emits equivalent SSSD `ldap_idmap_range`/`ldap_idmap_default_range` settings. See [`docs/09-linux-equivalents/02-sssd-id-mapping.md`](../docs/09-linux-equivalents/02-sssd-id-mapping.md) for SSSD's ID mapping internals.

**No native offline-files equivalent.** Windows Client-Side Caching (CSC, `cscsvc` + `cscdll.dll`) provides transparent offline access to SMB shares — files are cached locally on read/write and synchronized on reconnect. macOS has no native equivalent (a partial Docs To Go implementation exists but is consumer-grade). Linux has no native equivalent — `cachefilesd` (FS-Cache front-end) can cache NFS and some SMB mounts but does not provide Windows-CSC-style transparent write-back. PC-084 catalogues the gap. The framework's file gateway must either bundle a fresh CSC-equivalent implementation (significant engineering effort — write-back cache, conflict resolution, sync-on-reconnect) or accept that offline files are a Windows-only feature with a documented gap on macOS/Linux. The recommendation is the latter for v1, with a fresh CSC-equivalent in v2 if operator demand is strong.

## Cross-platform consistency problems

114 of 130 problems affect cross-platform consistency — the framework must produce identical semantics regardless of which platform hosts the DC or client. The five biggest consistency axes, where divergence is most likely and most consequential:

**Ticket cache type.** Windows uses in-process LSA memory (`LsaCallAuthenticationPackage(KerbRetrieveEncodedTicketMessage)`); macOS uses `API:Initialdefaultcache` (keychain-backed); Linux uses `KEYRING:persistent:<uid>` (default), `KCM:` (systemd-style, system daemon-managed), or `FILE:/tmp/krb5cc_<uid>` (legacy). PC-093 catalogues the divergence. The framework's client SDK must abstract the cache behind a `TicketCache` trait with `get`/`put`/`renew`/`destroy` operations, and the SDK's per-platform backend selects the cache type. The recommendation is: LSA on Windows, keychain `API:` on macOS, KCM on Linux (modern, system-managed, survives logout).

**ID mapping determinism.** PC-089 (blocker): SID↔UID mapping must produce the same UID on every host for the same user. Without this, NFS, SMB, and POSIX file permissions break. The framework's client SDK must adopt a single algorithm (SSSD slice) and a single range (`ldap_idmap_range = 200000-2000200000` is the SSSD default) across all hosts.

**Kerberos etype negotiation.** PC-024 (blocker, RC4) and PC-029 (low, AES-SHA384 etype 0x13): the framework's KDC must support the same etype set on every platform, with the same defaults (AES-256 only by default, RC4 opt-in for migration, AES-SHA384 opt-in for v2+). Etype negotiation is governed by `msDS-SupportedEncryptionTypes` on the service account; the framework's directory must enforce this attribute consistently.

**NTLM fallback behavior.** PC-036 (high) and PC-094 (high): the framework must define a single NTLM fallback policy (drop by default, opt-in for migration, audit when used) and apply it uniformly across Windows, macOS, and Linux clients. Per-platform divergence here is the most common operational surprise.

**Audit log format.** PC-042 (Kerberos audit events) and PC-111 (audit log format): the framework must produce identical audit events (Kerberos 4768/4769/4771 equivalents, logon 4624/4625 equivalents, replication 4662 equivalents) on every platform, in a structured format (JSON or OTel) rather than Windows Event Log XML. Per-platform divergence in audit log format breaks SIEM correlation.

## The unified client SDK problem

The single biggest parity blocker is PC-085: there is no universal AD client SDK. Windows applications use SSPI + Wldap32 + NetAPI. macOS applications use the OpenDirectory framework + Authorization framework + PSSO Extension. Linux applications use SSSD's PAM/NSS responders + OpenLDAP client libraries (or Winbind's equivalents). The four stacks differ in every dimension — authentication primitive (SSPI vs Authorization vs PAM), ticket cache location (LSA in-memory vs keychain `API:` vs `KEYRING:persistent:<uid>`), group resolution protocol (`LsaLookupSids3` vs `NetrSamLogon` opnum 45 vs LDAP `tokenGroups` vs PAC `GroupIds`), NSS source (none on Windows — LSASS handles name resolution internally; `libnss_sss` on Linux; `opendirectoryd` on macOS), and PAM model (none on Windows — LSASS handles auth phases internally; Linux-PAM with `auth`/`account`/`password`/`session` phases; macOS PAM with `pam_odl.so`). See [`catalog/08-client-sdk.md`](../catalog/08-client-sdk.md) for the full per-platform breakdown.

A new framework cannot solve this by wrapping all four stacks. The result would be a leaky abstraction with per-platform behavior drift — a `sdk.get_user_groups("alice@corp.example.com")` call would return a SID list on Windows, an `ODRecordRef` list on macOS, and a struct passwd list on Linux, and the caller would have to normalize. The framework must instead provide a unified SDK (Rust core + C bindings for Windows, Swift bindings for macOS, Python/Go/Rust bindings for Linux) that abstracts authentication (Kerberos AS/TGS, NTLM [if maintained], OAuth2 token cache, smart-card), directory query (LDAP wrapper with idiomatic language bindings), policy application (subscribe to policy, apply, report), file/print client (SMB client wrapper), certificate enrollment (autoenroll-equivalent), and federation client (token cache, refresh). The SDK must hide platform-specific Kerberos implementations (MS-KILE on Windows, Heimdal on macOS, MIT krb5 on Linux), ticket cache types, and PAM/NSS/SSPI differences behind one API surface.

The framework's Client SDK is the universal client surface for every server-side capability — Core Directory, KDC, Auth Provider, Policy Engine, Cert Service, Federation Gateway, File Gateway. PC-086 through PC-093 catalog the sub-problems: PC-086 (PSSO Extension is macOS 13+ only), PC-087 (Jamf Connect ROPG password sync is fragile), PC-088 (SSSD's GPO subset), PC-089 (ID mapping determinism, blocker), PC-090 (Heimdal vs MIT), PC-091 (domain join fragmentation), PC-092 (PAM distro variance), PC-093 (ticket cache type variance). All eight sub-problems must be addressed inside the SDK's design. The blocker-class PC-089 (ID mapping) is the highest-leverage sub-problem — getting it wrong means NFS, SMB, and POSIX file permissions break across hosts. The SDK's ID mapping abstraction is the single most important API in the entire framework.

The SDK design recommendation is: Rust core (zero-cost abstractions, memory safety, single-codebase compilation to Windows/macOS/Linux), with C ABI exported via `cbindgen`, Swift bindings via `swift-bridge`, Python bindings via `pyo3`, and Go bindings via `cgo`. The SDK wraps platform-native primitives on Windows (SSPI/Wldap32/NetAPI via FFI to `secur32.dll`/`wldap32.dll`/`netapi32.dll`) but uses the Rust core's directory/Kerberos/policy logic on macOS and Linux (overriding the system Heimdal fork on macOS, bundling MIT krb5 on Linux). This is the design documented in [`catalog/08-client-sdk.md`](../catalog/08-client-sdk.md) under PC-085's open questions.

## Recommendations for parity

The framework should adopt the following parity posture. Each recommendation maps to a specific PC-ID and is decision-ready for Phase 1 architecture work.

- **Adopt SSSD as the Linux integration baseline (PC-099, PC-088).** SSSD is the modern default, has the broadest deployment, and supports the GPO access control subset. The framework's Linux client SDK wraps SSSD's NSS/PAM responders via `/var/lib/sss/pipes/nss` and `/var/lib/sss/pipes/pam` rather than running a parallel stack. Winbind is supported only for Samba-DC-mode interop; PBIS is migration-source-only.

- **Adopt Jamf Connect + PSSO Extension as the macOS integration baseline (PC-086, PC-099).** PSSO Extension (macOS 13+) is the modern SSO surface with hardware-bound keys (SEP-backed ECDSA P-256). Jamf Connect provides ROPG password sync for older macOS (12 and below) and for IdP password change scenarios. The framework's macOS client SDK wraps PSSO via `sso_util` and `Authentication_SSO.appex`.

- **Build a unified Rust client SDK with C bindings for all platforms (PC-085).** Single codebase, single test matrix, per-platform FFI to SSPI/Wldap32 (Windows), OpenDirectory/Authorization (macOS), SSSD PAM/NSS responders (Linux). Bundles MIT krb5 on macOS and Linux to override the stale system Heimdal fork. See [`catalog/08-client-sdk.md`](../catalog/08-client-sdk.md) PC-085 for the API surface and open questions.

- **Drop NTLM by default; maintain as opt-in with hardening (PC-036, PC-094).** NTLM is a security liability (PtH, relay, no mutual auth). The framework's default is NTLM-off; operators enable it per-service with audit logging, channel binding, and EPA enforcement. The macOS client SDK bundles a fresh NTLMSSP module (not winbind) for migration scenarios only.

- **Use Configuration Profiles as the macOS GPO equivalent; document the mapping (PC-095, PC-045).** The framework's policy DSL compiles to GPO (Windows), Configuration Profile (macOS), and `sssd.conf`/`pam_access.so` rules (Linux). Coverage map: ~60% of GPO categories have a direct Configuration Profile payload; the remainder are documented gaps with operator workarounds. See [`docs/10-comparison-matrices/05-gpo-equivalents-matrix.md`](../docs/10-comparison-matrices/05-gpo-equivalents-matrix.md).

- **Use SSSD's GPO access control for Linux logon rights; document the supported subset (PC-053, PC-088).** SSSD enforces 5 of the ~40 User Rights Assignment entries (`SeInteractiveLogonRight`, `SeRemoteInteractiveLogonRight`, `SeNetworkLogonRight`, `SeBatchLogonRight`, `SeServiceLogonRight`). The framework's policy engine emits these 5 to the Linux client via SSSD's `ad_gpo_map_*` keys; all other URA are enforced via `pam_access.so` + `/etc/security/access.conf` generated by the client SDK.

- **Adopt ACME for cert enrollment on non-Windows; maintain MS-WCCE for Windows interop (PC-057, PC-059).** ACME (RFC 8555) is the modern cross-platform enrollment protocol. The framework's cert service exposes an ACME endpoint; the macOS and Linux client SDKs use ACME natively. The Windows client SDK uses MS-WCCE during AD interop (migration mode) and ACME after migration completes. The cert service translates ACME orders to MS-WCCE requests internally for the Windows-side bridge.

- **Use OAuth2-Proxy + nginx as the WAP equivalent (PC-073).** Envoy + ext-authz is the modern alternative for operators who want a pluggable auth pipeline. The framework's federation gateway ships a reference Helm chart for both deployments. AD FS WAP is Windows-only; no macOS or Linux equivalent exists natively.

- **Standardize on MIT Kerberos for client; Heimdal for KDC — or vice versa (PC-090, PC-105).** This is a research spike (Phase 0). MIT krb5 has broader client deployment; Heimdal has a KDC that more closely tracks MS-KILE semantics (Samba's Heimdal fork is the basis for Samba AD-DC). The framework's standardization must be evidence-based, not preference-based — the spike must measure PKINIT interop, FAST behavior, and PAC_FULL_CHECKSUM support for both. Recommendation pending spike outcome: MIT for client (Rust SDK bundles MIT krb5); Samba's Heimdal fork for KDC (reuse Samba's MS-KILE implementation).

- **Use keychain (macOS), KCM (Linux), LSA credential cache (Windows) for unified ticket storage (PC-093).** The framework's client SDK abstracts the ticket cache behind a `TicketCache` trait. Per-platform backend: LSA in-process on Windows (`LsaCallAuthenticationPackage`), `API:Initialdefaultcache` keychain-backed on macOS, `KCM:` system daemon on Linux (modern, survives logout, system-managed). The SDK does not use `FILE:` caches anywhere by default; legacy applications that hard-require `FILE:` get a bridge from KCM/keychain/LSA.

These ten recommendations close the highest-leverage parity gaps. They are not exhaustive — the catalog's 114 cross-platform consistency problems each require a per-problem parity decision — but they address the architectural questions where platform divergence is most consequential. Phase 1 of the roadmap ([`06-roadmap.md`](./06-roadmap.md)) locks each of these recommendations into a Tier-1 architecture decision with a deadline and a cascading-impact analysis.
