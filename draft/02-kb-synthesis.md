# KB Synthesis — Distilled Findings from the 72-File Knowledge Base

This file is a curated synthesis of the 72-file implementation-level knowledge base under [`docs/`](../docs/README.md). It is not a replacement for the KB — every claim is sourced; specific OID identifiers, source-file paths, registry keys, opnums, and protocol offsets are cited back to the file that documents them. The synthesis is written for senior engineers and architects who need the technical narrative in one readable document rather than 72.

## What AD actually is

Active Directory is **a directory service, an authentication broker, a configuration distribution system, a PKI, a federation platform, and a file-services dependency**, all built on a shared DIT + Kerberos + DNS + SMB + RPC substrate. The five server roles — AD DS, AD CS, AD FS, AD LDS, AD RMS — share schema, naming, and replication but solve different problems ([`docs/00-overview/01-active-directory-overview.md`](../docs/00-overview/01-active-directory-overview.md)). AD DS is the foundation: it provides a replicated multi-master directory (`ntds.dit`, an ESE/Jet Blue database) opened exclusively by `lsass.exe` via `esent.dll`, a Kerberos KDC running in-process as `kdcsvc.dll`, Netlogon for the secure channel, an LDAP server on TCP 389/636, a Global Catalog on 3268/3269, and AD-integrated DNS. AD LDS is AD DS minus Kerberos, minus Netlogon, minus GPO processing — a directory-only role for applications that need LDAP+schema without domain join. AD CS is an X.509v3 Certificate Authority implementation with Enterprise (AD-integrated, autoenroll-capable) and Standalone (no AD dependency) flavors. AD FS is a claims-based identity provider with SAML 2.0, WS-Federation, and OAuth2/OIDC endpoints. AD RMS is an Information Rights Management service issuing use licenses for protected content.

The implementation substrate is **LSASS + ESE + DRSUAPI**. LSASS (`lsass.exe`) hosts the DSA (`ntdsa.dll`), the KDC (`kdcsvc.dll`), the NTLM provider (`msv1_0.dll`), the Kerberos SSPI provider (`kerberos.dll`), Netlogon (`netlogon.dll`), LSA core (`lsasrv.dll`), and ESE (`esent.dll`). The DIT is a 16 KB-page ESE database with ~50 tables (`datatable`, `linktable`, `sdtable`, `cursor`, `msysobjects`); page-level SHA-1 checksums (post-Server 2012); security-descriptor deduplication via `sdtable`; and Linked Value Replication for multi-valued attributes since Server 2003 SP1. The schema cache lives in LSASS process memory and is rebuilt on `schemaUpdateNow` (5–30 second LDAP write block). Replication is pull-based, layered on DRSUAPI's `DRSGetNCChanges` (opnum 3), using USN/InvocationID/UTD-vector/high-watermark cursors with per-attribute `PROPERTY_META_DATA_EXT` for conflict resolution. See [`docs/00-overview/02-ad-architecture.md`](../docs/00-overview/02-ad-architecture.md) and [`docs/03-directory-schema/05-replication-internals.md`](../docs/03-directory-schema/05-replication-internals.md).

The transport dependencies are **DNS, Kerberos, LDAP, SMB, and DCE/RPC**. DNS is the locator substrate: clients resolve `_ldap._tcp.dc._msdcs.<domain>` SRV records and issue CLDAP pings on UDP 389 to discover DCs. AD-integrated DNS zones live in `DomainDnsZones` and `ForestDnsZones` application partitions and replicate via DRSR. Kerberos (TCP/UDP 88, kpasswd on 464) handles authentication; LDAP (389/636) and the Global Catalog (3268/3269) handle directory queries; SMB (445) handles SYSVOL GPO distribution and DRSR-over-named-pipe fallback; DCE/RPC (TCP 135 + dynamic, or `\pipe\drsuapi` over SMB) handles replication, SAMR, LSA, and Netlogon. W32Time (MS-SNTP) maintains the 5-minute Kerberos clock-skew window. The whole stack is documented in [`docs/02-protocols/`](../docs/README.md).

## Protocol-level architecture

The KB's `02-protocols/` directory contains 8 files, each a wire-level deep dive. The table below synthesizes the role and key implementation detail of each.

| **SMB** | File shares, named pipes (DRSR, SAMR, LSA, Netlogon), SYSVOL distribution. | SMB 1/2/3 dialects, dialect 0x311 = SMB 3.1.1; pre-auth integrity, AES-GCM encryption, multichannel, persistent handles, CA shares. | **DNS** | Service discovery (SRV, A, AAAA), AD-integrated zones, dynamic updates. | RFC 2136 + MS-DNSP; zones stored in `DomainDnsZones`/`ForestDnsZones` application partitions; secure dynamic updates via GSS-TSIG; `_msdcs` forest-wide forwarding zone; scavenging and aging. | [`docs/02-protocols/05-dns-dynamic-updates.md`](../docs/02-protocols/05-dns-dynamic-updates.md) |
| **DRSR (DCE/RPC)** | Replication, FSMO ops, name resolution, SPN writes, KCC execution. | DRSUAPI interface `[uuid(E3514235-8B63-11D0-A26C-00A0C92B955C), version(4.0)]`; `DRSGetNCChanges` opnum 3 is the replication workhorse; `DRSBind` negotiates `DRS_EXTENSIONS_INT` capability flags (BASE, ASYNCREPL, GETCHG_DEFLATE, GETCHG_REQ_V6/V8/V10/V11, CRYPTO_BIND, STRONG_ENCRYPTION, RECYCLE_BIN); LZ-Express compression. | [`docs/02-protocols/06-rpc-dcerpc-ms-drsr.md`](../docs/02-protocols/06-rpc-dcerpc-ms-drsr.md) |
| **W32Time / NTP** | Time sync; maintains the 5-minute Kerberos skew window. | MS-SNTP; PDC emulator of forest root syncs to external source; chain of sync flows down; auth'd NTP using the domain's `dcdns` key; `MaxPosPhaseCorrection`, `MaxNegPhaseCorrection` cap drift. | [`docs/02-protocols/07-ntp-time-sync.md`](../docs/02-protocols/07-ntp-time-sync.md) |
| **SPN / UPN / PAC** | Service principal naming, user principal routing, authorization data. | SPN uniqueness enforced via `DRSWriteSPN` opnum 13; UPN routing resolves to a domain via the Config NC `Partitions` container; PAC carries `KERB_VALIDATION_INFO` (RID, `GroupIds[]`, `ExtraSids`, UAC), signed by KDC and (Server 2016+) ticket-level checksum. | [`docs/02-protocols/08-spn-upn-pac.md`](../docs/02-protocols/08-spn-upn-pac.md) |

Three cross-protocol observations matter. First, **the NT hash is the master secret** — it is the RC4 Kerberos key, the NTLMv2 challenge-response key, and the value extracted from LSASS by Mimikatz. Removing NTLM does not by itself stop pass-the-hash if RC4 Kerberos remains enabled. Second, **the PAC is the authorization substrate** — every Kerberos service ticket carries a PAC signed by the KDC; services that skip PAC validation (most services, for perf) trust the issue-time signature and are vulnerable to silver-ticket attacks unless the Server 2016+ ticket checksum is enforced. Third, **DRSR is the dual-use protocol** — the same `DRSGetNCChanges` that performs replication is exploited by `impacket/secretsdump.py` for DCSync (any principal with `DS-Replication-Get-Changes` + `DS-Replication-Get-Changes-All` can pull all password hashes).

## Schema, replication, and GPO

The `03-directory-schema/` directory covers the logical directory model in 5 files. AD's schema is **dynamic and LDAP-defined** — `attributeSchema` and `classSchema` objects in the Schema NC (`CN=Schema,CN=Configuration,...`), each with an OID (e.g. `userPrincipalName` = `1.2.840.113556.1.4.666`), `systemFlags` bitmask, `searchFlags` (controlling index/ambiguous-name-resolution/tombstone), and `linkID` pairing for back-links (`member` ↔ `memberOf`). Schema changes are single-master: only the Schema Master FSMO holder can write; reload blocks LDAP writes for 5–30 seconds. The Global Catalog (`docs/03-directory-schema/03-global-catalog.md`) is a partial-attribute-set replica on port 3268/3269 — attributes marked `isMemberOfPartialAttributeSet` replicate forest-wide for cross-domain group membership resolution. Trusts (`04-trusts-topology.md`) are encoded as `trustedDomain` objects with `trustDirection`, `trustType`, and `trustAttributes` bitmasks (e.g. `0x4` = quarantined/SID filtering, `0x8` = forest-transitive, `0x10` = cross-organization/selective auth, `0x20` = within-forest, `0x200` = no TGT delegation post-CVE-2020-1472). See [`docs/03-directory-schema/01-schema-attributes.md`](../docs/03-directory-schema/01-schema-attributes.md) through [`docs/03-directory-schema/05-replication-internals.md`](../docs/03-directory-schema/05-replication-internals.md).

Replication (`05-replication-internals.md`) is the most consequential design choice. AD uses **state-based pull** layered on `DRSGetNCChanges`. Every DC tracks a per-database `usnChanged` counter (allocated inside the ESE transaction in `ntdsa.dll!DBUpdateRecUsn`, persisted at `DBHEADER.usnLast` offset 0x118 of `ntds.dit`), a per-DC `invocationId` UUID (regenerated on USN-rollback detection), a per-NC up-to-dateness (UTD) vector (highest-seen USN per originating DSA), and a per-NC high-watermark cursor (`{InvocationID, USN}` last pulled from each partner). Each attribute carries `PROPERTY_META_DATA_EXT` (`dwVersion`, `uuidLastOriginatingDsa`, `usnOriginatingChange`, `ftimeLastOriginatingChange`); conflict resolution picks higher `dwVersion`, then higher `usnOriginatingChange`, then later `ftimeLastOriginatingChange`. Linked Value Replication (Server 2003 SP1) replicates large multi-valued attributes (group memberships >5000 members) as individual `REPLVALINF_V3` records rather than full-attribute rewrites. Strict replication consistency (`HKLM\SYSTEM\CurrentControlSet\Services\NTDS\Parameters\Strict Replication Consistency = 1`) quarantines stale partners rather than re-seeding. USN rollback detection: when a partner's advertised high-watermark is lower than the stored cursor, `ntdsa.dll!CheckUsnRollback` quarantines and logs event 2095.

GPO (`04-group-policy/`, 5 files) is a **two-part entity**: the Group Policy Container (GPC) in AD at `CN=Policies,CN=System,<domain-dn>` (a `groupPolicyContainer` object with `gPCFileSysPath`, `gPCMachineExtensionNames`, `gPCUserExtensionNames`, `versionNumber`), and the Group Policy Template (GPT) in SYSVOL at `\\<domain>\SYSVOL\<domain>\Policies\{<GUID>}\` (carrying `GPT.INI`, `Machine\Registry.pol`, `User\Registry.pol`, `Scripts\`, `Preferences\` XML files). Clients pull both halves; the GPC tells the client which CSE GUIDs to invoke, the GPT provides the payload. Processing order is **LSDOU** (Local, Site, Domain, OU) with `gPOptions` block-inheritance and `gPLink` enforcement-order semantics, WMI filters, security filtering, slow-link detection, and async reboot. ADMX templates (`03-admx-templates.md`) replaced ADM in Vista; the central store lives at `\\<domain>\sysvol\<domain>\Policies\PolicyDefinitions\`. CSEs (`04-cse-client-side-extensions.md`) are COM DLLs registered under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\GPExtensions\{GUID}` — one per policy type (Registry `{35378EAC-683F-11D2-A89A-00C04FBBCFA2}`, Security `{827D319E-6EAC-11D2-A4EA-00C04FB937DC}`, Scripts `{42B5FAAE-6536-11D1-AE59-0000FED75982}`, Folder Redirection `{D02B1F72-3407-48AE-BA88-E8213C6761F1}`, AppLocker, etc.). `Registry.pol` is a PReg binary format with UTF-16LE strings and bracketed value lists. See [`docs/04-group-policy/01-gpo-architecture.md`](../docs/04-group-policy/01-gpo-architecture.md) through [`docs/04-group-policy/05-gpt-gpc-structure.md`](../docs/04-group-policy/05-gpt-gpc-structure.md).

## PKI, federation, file/print

AD CS (`05-pki-certs/`, 4 files) runs as `certsvc.exe` (a standalone process, not svchost-hosted), hosting one or more CA instances each backed by an ESE database at `%SystemRoot%\System32\CertLog\<CAName>.edb`. The reference topology is **two-tier**: an offline root CA (Standalone, hardware-protected, air-gapped) signs one or more Policy CAs (optional intermediate); an Enterprise Subordinate CA (AD-integrated, online, supports autoenroll) issues end-entity certs. Policy modules (`certpmod.dll`) decide whether a request satisfies template ACLs and constraints; exit modules (`certxmod.dll`) run after issuance (publish cert to AD `userCertificate`, publish CRL to CDP). Certificate templates (`02-certificate-templates.md`) are version 1/2/3 objects in `CN=Certificate Templates,CN=Public Key Services,CN=Services,CN=Configuration,...` with ACLs, application policies, subject-name rules, and key-archival flags. Autoenrollment (`03-autoenrollment.md`) uses GRP-Autoenroll (Group Policy), MS-XCEP (Certificate Enrollment Policy Service, SOAP over HTTPS), and MS-WCCE (Windows Client Certificate Enrollment, SOAP over HTTPS); key archival uses RSA-OAEP-wrapped blobs recoverable via Key Recovery Agent (KRA) certs. CRL/OCSP (`04-ocsp-crl.md`) publishes full and delta CRLs to CDP/AIA URLs; the Online Responder (`ocsp.exe`) serves RFC 6960 OCSP responses with the `ID-PKIX-OCSP-NoCheck` extension for responder cert pinning. See [`docs/05-pki-certs/01-ad-cs-architecture.md`](../docs/05-pki-certs/01-ad-cs-architecture.md) through [`docs/05-pki-certs/04-ocsp-crl.md`](../docs/05-pki-certs/04-ocsp-crl.md).

AD FS (`06-federation-sso/`, 4 files) runs as `Microsoft.IdentityServer.ServiceHost.exe`, a WCF service host registered with `HTTP.SYS` on `https://+:443/adfs/` and `http://+:80/adfs/`. The config DB lives in either the Windows Internal Database (`%SystemRoot%\Windows\WID\Data\microsoft.identityserver.mdf`) or SQL Server; primary node writes, secondaries read-only and sync every 5 minutes. The trust pipeline has three stages: **Claims Provider Trust** (incoming claims from upstream IdP) → **Acceptance Transform Rules** (normalize) → **Issuance Transform Rules** (map to relying-party claims). Protocol families: SAML 2.0 (passive profile, `/adfs/ls/`), WS-Federation (passive, legacy), OAuth2/OIDC (ADFS 2016+, `/adfs/oauth2/authorize`, `/adfs/oauth2/token`, `/.well-known/openid-configuration`). The claims rule language (`03-claims-rules.md`) is a proprietary DSL — `c:[Type == "..."] => issue(Type = "...", Value = c.Value);` — with regex, lookup, custom attribute store (SQL, AD, LDAP) support. The Web Application Proxy (`WAPService.exe` under `svchost -k WAPServiceSvchost`) is the edge reverse proxy, performing MS-ADFSPIP-based pre-authentication for external clients. See [`docs/06-federation-sso/01-adfs-architecture.md`](../docs/06-federation-sso/01-adfs-architecture.md) through [`docs/06-federation-sso/04-oidc-oauth.md`](../docs/06-federation-sso/04-oidc-oauth.md).

File and print (`07-file-print/`, 4 files) is built on `srv2.sys`/`srv.sys`/`srvnet.sys` (SMB server) and the redirector `mrxsmb20.sys` (client). DFS Namespaces (`dfssvc.exe`) resolve `\\domain\share\path` UNC paths into per-site target referrals using the Path Knowledge Table (pKT) cached in registry and stored authoritatively as `fTDfs` / `msDFS-Link` objects in `CN=Dfs-Configuration,CN=System,DC=...`. DFS Replication (`dfsr.exe`) is the multi-master replicator that replaced FRS for SYSVOL replication in Server 2008 R2+; it uses Remote Differential Compression (RDC) over the wire and the USN journal (`$Extend\$UsnJrnl:$J`) for change detection, with version vectors per replication group. Print services (`spoolsv.exe`) speak MS-RPRN over named pipes; PrintNightmare (CVE-2021-34527) is the `RpcAddPrinterDriverEx` SYSTEM-code-execution flaw mitigated by `RestrictDriverInstallationToAdministrators`. Offline Files (CSC, `cscsvc.dll` + `csc.sys`) provides transparent caching and conflict resolution for offline SMB access. The production floor is SMB 3.1.1 (pre-auth integrity + AES-GCM), and CA shares require persistent handles. See [`docs/07-file-print/01-smb-shares-internals.md`](../docs/07-file-print/01-smb-shares-internals.md) through [`docs/07-file-print/04-offline-files.md`](../docs/07-file-print/04-offline-files.md).

## macOS equivalents

The `08-macos-equivalents/` directory (8 files) documents how macOS integrates with AD. The substrate is **OpenDirectory** (`01-opendirectory-internals.md`): a single daemon `opendirectoryd` (launchd label `com.apple.opendirectoryd`) routing every identity lookup, authentication, and directory-mutation call through a plug-in registry — `DSP.local` (Berkeley-DB-style `dslocal` store), `DSP.LDAPv3`, `DSP.ActiveDirectory` (the bundled AD plug-in), `DSP.Bonjour`, `DSP.XML`. Higher-level clients (`id`, `groups`, `loginwindow`, Security framework, Authorization framework, SSO extensions, MDM profiles) call through `OpenDirectory.framework` (CFType-refcounted `ODSessionRef`/`ODNodeRef`/`ODRecordRef`), which serializes to the daemon via XPC. The AD plug-in (`dsconfigad` configuration, `02-dscl-dsconfigad.md`) handles binding, Kerberos, LDAP queries, and CLDAP DC location; it does **not** consume GPOs natively.

What macOS has natively: **Kerberos client via an ancient Heimdal fork** (`/usr/bin/kinit`, `/System/Library/Kerberos`); **OpenDirectory LDAP** (read-only access to AD); **SMBX/SMB client** (`/usr/sbin/smbd` bundled, mount_smbfs); **CUPS for print**; **Kerberos SSO Extension** (`05-kerberos-sso-extension.md`) since macOS 13 — an MDM-deployed extension that auto-renews TGTs and stores them in the keychain; **Platform SSO Extension** (`04-platform-sso-extension.md`) since macOS 13 — Device Registration with SEP key storage, Hardware_Bound mode; **Configuration Profiles as GPO equivalent** (`09-mac-mdm-gpo-equivalents.md`) — `.mobileconfig` payloads deployed via MDM (Jamf, Workspace ONE, Intune, Kandji). What macOS lacks: **GPO Preferences** (drive maps, file copy, registry tweaks, scheduled tasks — no native equivalent, partial via Configuration Profile payloads); **NTLM** (no native NTLMSSP client; Samba's `libsmbclient` works but is not the default; apps that hard-require NTLM fail); **AD-integrated DNS** (macOS hosts consume DNS but cannot host AD-integrated zones); **DFS-R** (no replication; client can resolve DFS-N referrals via `mount_smbfs` but cannot be a DFS-R member); **PAC validation** (no native mechanism — the framework's macOS services would need a custom validation path).

Third-party agents (`06-enterprise-connect-nomad.md`, `07-third-party-agents-mac.md`) fill gaps but are EOL or deprecated: **Enterprise Connect** (Apple internal, deprecated), **NoMAD/NoLoAD** (open source, maintenance mode), **Centrify DirectControl** (now Delinea, commercial), **BeyondTrust PBIS for Mac** (deprecated 2023), **AdmitMac** (Thursby, commercial), **DAVE** (Thursby, commercial). **Jamf Connect** (`03-jamf-connect-pro.md`) is the modern commercial solution — it provides ROPG (Resource Owner Password Grant) password sync to Jamf IDP, Kerberos extension hooks, and PSSO integration. The PSSO Extension + Jamf Connect + MDM is the modern enterprise macOS stack. See [`docs/08-macos-equivalents/01-opendirectory-internals.md`](../docs/08-macos-equivalents/01-opendirectory-internals.md) through [`docs/08-macos-equivalents/09-mac-mdm-gpo-equivalents.md`](../docs/08-macos-equivalents/09-mac-mdm-gpo-equivalents.md).

## Linux equivalents

The `09-linux-equivalents/` directory (10 files) is the most fragmented — there is no single "Linux AD stack." The five viable approaches:

**SSSD** (`01-sssd-ad-provider.md`) is the modern default on Red Hat, SUSE, and most enterprise distros. A single `sssd` daemon forks one monitor process, one responder per enabled service (`sssd_nss`, `sssd_pam`, `sssd_sudo`, `sssd_ifp`, `sssd_pac`, `sssd_ssh`), and one backend per domain (`sssd_be --domain <name>`). The `ad` provider (`src/providers/ad/ad_id.c:ad_domain_init`) is a thin wrapper that pre-binds the `ldap` identity provider, the `krb5` auth provider, and the `ad` access checker behind a single `[domain/ad]` config block, with sensible defaults injected (`ldap_schema = ad`, `ldap_sasl_mech = GSS-SPNEGO`, `ldap_id_mapping = true`). ID mapping (`02-sssd-id-mapping.md`) uses range allocation: each AD domain gets a slice of POSIX UID/GID space (`ldap_idmap_range` default 200000–2000200000), with RID-based mapping inside the slice. SSSD GPO access control (`03-sssd-gpo-access.md`) consumes a subset of GPO — security filtering for logon rights only (`ad_gpo_access_control = enforced`), parses `Machine\Windows Settings\Security Settings\Local Policies\User Rights Assignment`, and applies `Allow log on locally` / `Deny log on` / `Allow log on through Remote Desktop Services`. See [`docs/09-linux-equivalents/01-sssd-ad-provider.md`](../docs/09-linux-equivalents/01-sssd-ad-provider.md) through [`docs/09-linux-equivalents/03-sssd-gpo-access.md`](../docs/09-linux-equivalents/03-sssd-gpo-access.md).

**Winbind** (`04-winbind-internals.md`, `05-samba-tool-net-ads.md`) is Samba's AD integration. `winbindd` runs alongside `smbd`/`nmbd`; idmap backends (`idmap_rid`, `idmap_ad`, `idmap_autorid`) allocate POSIX IDs. Winbind is the legacy default (RHEL 5/6 era) and is still the only option when the host is a Samba file server or print server. `net ads join` and `samba-tool domain` are the join commands; `samba-tool` is also a DRSUAPI client (`samba-tool drs replicate`) and the only open-source MS-DRSR server. **realmd** (`06-realmd-join-flow.md`) is a DBus service that automates the join flow — detects the realm, picks SSSD or Winbind, writes the config, joins via `adcli` or `net ads join`, generates the keytab, configures PAM/NSS. **PBIS** (`07-pbis-powerbroker.md`) is BeyondTrust's commercial stack (formerly Likewise Open) — `lwsmd`, `domainjoin-cli`, `lwreg`, an eventlog shim, and a GPO engine for Linux. Deprecated 2023; existing deployments should migrate to SSSD. **FreeIPA** (`08-freeipa-trust.md`) is an alternative domain controller built on 389-DS, MIT krb5, Dogtag PKI, and SSSD — it does not implement DRSUAPI but supports a two-way cross-forest trust with AD via Samba's `samba-tool domain trust create`. **OpenLDAP + MIT Kerberos** (`09-openldap-mit-kerberos.md`) is the roll-your-own path: `slapd` + `krb5kdc` + `nslcd` + `pam_krb5` + manual schema extension — no AD-specific glue, no GPO, no autoenroll. The PAM/NSS stack (`10-pam-nss-stack.md`) is the universal Linux client surface — `pam_sss.so` / `pam_winbind.so` for auth, `libnss_sss.so.2` / `libnss_winbind.so` for identity, `nsswitch.conf` for ordering, `systemd-homed` for per-user portable home dirs (modern alternative).

The fragmentation problem is the headline: **three competing AD integration stacks** with different trade-offs, plus two alternative paths. SSSD is the modern default but only consumes a subset of GPO; Winbind is required for Samba file servers but lacks GPO; PBIS is deprecated; FreeIPA is a separate identity platform that requires a trust relationship with AD; the roll-your-own path lacks any AD-specific glue. The framework's Client SDK capability must standardize on SSSD (Linux) + PSSO (macOS) + native AD (Windows) with documented gaps. See [`docs/09-linux-equivalents/01-sssd-ad-provider.md`](../docs/09-linux-equivalents/01-sssd-ad-provider.md) through [`docs/09-linux-equivalents/10-pam-nss-stack.md`](../docs/09-linux-equivalents/10-pam-nss-stack.md).

## Cross-platform comparison

The `10-comparison-matrices/` directory (5 files) provides side-by-side lookups. The master **feature × OS matrix** (`01-feature-os-matrix.md`) covers every AD feature across 10 columns (Win10/11 native, Win Server DC, macOS Native OD, macOS Enterprise MDM, macOS 3rd-party agent, Linux SSSD, Linux Winbind, Linux PBIS, Linux FreeIPA, Linux Pure OSS). The **protocol × implementation matrix** (`02-protocol-implementation-matrix.md`) covers each protocol across Windows Heimdal, MIT, Apple Heimdal, Samba, and Microsoft. The **tool × function matrix** (`03-tool-function-matrix.md`) maps common functions (find user, reset password, join, query SPN, force replication, change GPO) to OS-specific tools. The **auth flow comparison** (`04-auth-flow-comparison.md`) walks step-by-step auth flows side-by-side. The **GPO equivalents matrix** (`05-gpo-equivalents-matrix.md`) maps each ADMX setting to mcx (legacy macOS), Configuration Profiles (modern macOS), SSSD GPO access, FreeIPA HBAC, and Ansible.

The headline gaps surfaced by these matrices: **no native GPO Preferences on Mac/Linux** — macOS uses Configuration Profiles (a different format, declarative not imperative, no script-CSE equivalent) and Linux has no equivalent at all (SSSD consumes only security filtering; Ansible is the typical workaround but is push-based, not pull). **No native NTLM client on macOS** — Samba's `libsmbclient` works for SMB but is not the default; apps that hard-require NTLM (old SQL Server drivers, old IIS-integrated apps) fail. **Three competing Linux stacks** — SSSD vs Winbind vs PBIS, each with different ID mapping algorithms (SSSD slice-based, Winbind `idmap_rid` linear, PBIS proprietary), different GPO consumption (only SSSD consumes any), different kerberos implementations (SSSD uses MIT, Winbind uses Samba's Heimdal fork). **No universal client SDK** — Windows uses SSPI+Wldap32+NetAPI+gpsvc; macOS uses OpenDirectory framework+Authorization+SSO Extensions; Linux uses SSSD+PAM+NSS+libkrb5+libldap. **DFS-R has no open-source equivalent** — SYSVOL replication strategy is a blocker decision. **AD-integrated DNS zones** are Windows-only — Linux BIND with `dlz` provides partial coverage but is not equivalent. **AD CS autoenrollment** is Windows-only — `certmonger` on Linux covers SCEP/ACME but not MS-WCCE. **PrintNightmare-equivalent hardening** is not portable — Linux CUPS has a different attack surface. See [`docs/10-comparison-matrices/01-feature-os-matrix.md`](../docs/10-comparison-matrices/01-feature-os-matrix.md) through [`docs/10-comparison-matrices/05-gpo-equivalents-matrix.md`](../docs/10-comparison-matrices/05-gpo-equivalents-matrix.md).
